## Correction №1 — календарно-корректное обнаружение пропусков

**Дефект.** `CandleSeries.detect_gaps()` сравнивал соседние свечи с
фиксированным интервалом и считал пропуском ЛЮБОЕ отклонение — выходные,
праздники, ночные перерывы и внутридневные паузы помечались как ложные
пропуски; STRICT отклонял корректные серии.

**Решение.** Отдельный компонент `TradingCalendar` (новый модуль
`calendar.py`):

* получает торговые интервалы ИСКЛЮЧИТЕЛЬНО из явно переданных сессий
  (`TradingSession`: open/close + внутридневные перерывы); сети и
  автозагрузки нет; отсутствующие календарные данные не подменяются
  предположениями;
* классифицирует каждый ожидаемый момент `prev + k*interval`:
  `IN_TRADING_TIME` / `IN_SESSION_BREAK` / `NON_TRADING_DAY` (дата
  покрыта, сессий нет — выходной/праздник) / `NON_TRADING_TIME` (вне окна
  сессии при наличии на дату сессии) / `OUTSIDE_CALENDAR_COVERAGE`
  (категория D — проверить невозможно);
* покрывает A/B/C/D ТЗ: подтверждённый пропуск ожидаемой торговой свечи,
  нормальный перерыв сессии, отсутствие торгов (выходной/праздник),
  невозможность проверки (календарь не передан или отклонение вне
  покрытого диапазона дат);
* STRICT отклоняет ТОЛЬКО подтверждённые пропуски ожидаемых торговых
  свечей и календарно-независимые аномалии хронологии (свеча раньше
  ожидаемого интервала — ни перерыв, ни выходной её не объясняют);
* без календаря — ЯВНО обозначенная ограниченная проверка хронологии
  (статус `LIMITED_NO_CALENDAR_CHRONOLOGY_ONLY`, категория D
  `UNVERIFIED_NO_CALENDAR...`): ложного подтверждения полноты данных нет;
  STRICT в этом режиме консервативен (отклоняет любое отклонение, как и
  прежде — поведение Stage E сохранено);
* при неполном календаре (отклонение вне покрытого диапазона дат) —
  статус `PERFORMED_PARTIAL_CALENDAR_COVERAGE_INSUFFICIENT`, инцидент
  `UNVERIFIED_OUTSIDE_CALENDAR_COVERAGE`; STRICT не отклоняет
  неподтверждённое;
* контракты календаря: tz-aware метки, один общий часовой пояс
  (смешение отклоняется), сессии упорядочены и не пересекаются, перерывы
  строго внутри сессии, торговое время — полуинтервал `[open; close)`,
  метка свечи — момент открытия. Всё проверяется fail-closed;
* соглашение о покрытии (задокументировано в докстринге): явно
  переданные сессии — полный авторитетный календарь внутри диапазона
  дат [дата первой сессии; дата закрытия последней]; даты вне диапазона
  НЕ оцениваются.

**Отчётность.** В отчёт прогона добавлены `gap_analysis` (полная
классификация инцидентов) и `gap_verification` (статус, наличие
календаря, `calendar_sha256`, счётчики по категориям). Обратная
совместимость: поле `gaps` сохранено — без календаря содержит все
отклонения интервала (как в Stage E), с календарём — только
подтверждённые пропуски (это и есть исправление: перерывы/выходные
больше не считаются пропущенными свечами).

## Correction №2 — раздельный учёт проскальзывания и улучшения цены

**Дефект.** При исполнении Take Profit после гэпа вверх вся свеча могла
находиться выше целевого уровня; ограничение исполнения диапазоном свечи
давало цену ВЫШЕ цели, и прежняя формула `raw - exec` записывала в
расходы на проскальзывание ОТРИЦАТЕЛЬНУЮ величину, смешивая два разных
экономических показателя: неблагоприятное проскальзывание и улучшение
цены исполнения.

**Решение.** Новая чистая детерминированная функция
`split_execution_deviation(side, reference_price, execution_price,
quantity, contract_multiplier)`:

* продажа: исполнение ниже reference — неблагоприятное проскальзывание;
  выше — улучшение цены; покупка — зеркально (формулы учитывают
  направление);
* `adverse_slippage_cost >= 0` и `favorable_price_improvement >= 0`
  всегда; ровно одна из величин ненулевая (или обе нулевые);
* суммы — с учётом quantity и contract_multiplier; порядок float-операций
  сохранён (`quantity * multiplier * delta`), поэтому во всех случаях, где
  прежняя модель была корректна, значения бит-в-бит совпадают с прежними;
* комиссия остаётся отдельным показателем и в split не входит;
* reference-цена операции задокументирована: open свечи исполнения
  (вход/стратегический выход), уровень стопа/цели (защитный выход),
  гэповое open (выход гэпом через стоп). Потери гэпа (стоп − open) —
  рыночный риск, в slippage НЕ включаются (аудиторская reference-цена
  добавлена в details каждой операции).

**Цена фактического исполнения НЕ изменена** (ТЗ §4.3): формулы
исполнения (следующий open, ограничение диапазоном свечи, гэп через
стоп, консервативный SL/TP в одной свече) остались прежними; изменён
только УЧЁТ отклонения. Модель исполнения и правила срабатывания
сигналов сохранены.

**Отчётность (обратная совместимость сохранена).** В блок `costs`:
прежние `total_commission`, `total_slippage_cost` (теперь строго >= 0,
смысл «суммарное неблагоприятное проскальзывание») + новые
`total_adverse_slippage_cost`, `total_favorable_price_improvement`,
`total_execution_cost` и документированное однозначное определение
`TOTAL_EXECUTION_COST = TOTAL_COMMISSION + TOTAL_ADVERSE_SLIPPAGE_COST`
(улучшение цены — не расход и в стоимость исполнения не входит).
В сделках: `entry/exit_price_improvement`; в событиях и details операций:
`reference_price`, раздельные adverse/improvement. Прежние имена полей
сохранены; семантика изменилась только там, где прежнее значение было
дефектным (отрицательный «слippage»).

## Correction №3 — согласованность конфигураций Feed/Engine

**Дефект.** `HistoricalDataFeed` и `BacktestEngine` могли быть созданы с
несовместимыми конфигурациями; интерпретация исторических данных была бы
непоследовательной.

**Решение.** При создании `BacktestEngine` выполняется явная проверка
`validate_feed_engine_config_consistency(feed.engine_config,
engine_config)`:

* сравниваются ТОЛЬКО параметры интерпретации данных:
  `expected_candle_interval_seconds`, `gap_policy`, конфигурация
  календаря (наличие + `calendar_sha256`, включающий представление
  часового пояса);
* часовой пояс: отдельной настройки tz в `EngineConfig` архитектурой не
  предусмотрено (метки свечей несут собственный tz); единственный
  tz-несущий элемент конфигурации — календарь, и он сравнивается по
  отпечатку, чувствительному к представлению пояса (одинаковые моменты в
  UTC и UTC+03:00 — РАЗНЫЕ конфигурации; неявной нормализации нет);
* несвязанные параметры (капитал, комиссии, риск-лимиты) сознательно не
  сравниваются;
* при несовместимости — fail-closed `EngineConfigError`, диагностика
  перечисляет КАЖДЫЙ различающийся параметр и ОБА значения; неявный
  выбор одной конфигурации вместо другой исключён;
* при полном совпадении — запуск разрешён.

Проверка выполняется в `__init__` до любых вычислений; отказ не имеет
побочных эффектов (фид и конфигурации неизменяемы — покрыто тестом).

## ФИНАЛЬНЫЕ ПРАВКИ — Correction 1: покрытие календарём ВСЕЙ серии

**Дефект.** `TradingCalendar.analyze_series()` классифицировал только
ожидаемые метки МЕЖДУ соседними свечами. Граничные свечи (первая и
последняя серии) не входят ни в один межсвечный интервал и не
классифицировались вовсе. В результате серия, все пары которой лежали
ровно через интервал (между свечами нет пропусков), получала статус
`PERFORMED_FULL_CALENDAR_VERIFIED` даже когда даты серии (полностью или
по краям) лежат ВНЕ покрытия календаря: проверка ограниченности
молча превращалась в ложное подтверждение полноты данных.

**Решение (в `analyze_series()`, после попарного анализа):**

* покрытие календаря проверяется для ВСЕЙ исследуемой серии
  НЕЗАВИСИМО от наличия обнаруженных отклонений;
* НАЧАЛО и КОНЕЦ серии (метки первой и последней свечей)
  классифицируются ОТДЕЛЬНО (`classify_moment`);
* граница вне покрытия даёт инцидент категории D
  `UNVERIFIED_OUTSIDE_CALENDAR_COVERAGE` с деталями:
  `reason=series_boundary_outside_calendar_coverage`,
  `series_boundary=series_start|series_end`, метка границы, даты
  покрытия календаря (`gap_seconds=0`, `missing_expected_count=0` —
  это НЕ пропуск, а ограниченность проверки);
* если хотя бы часть серии вне покрытия — инцидент категории D
  присутствует в `gap_incidents`, и статус проверки в data_feed НЕ
  МОЖЕТ быть `PERFORMED_FULL_CALENDAR_VERIFIED` (становится
  `PERFORMED_PARTIAL_CALENDAR_COVERAGE_INSUFFICIENT`) — существующий
  механизм статусов использован без изменений;
* непокрытые даты НЕ считаются выходными или праздниками
  (классификация невозможна — категория D, а не C);
* STRICT НЕ отклоняет неподтверждённые инциденты (граница вне
  покрытия — не подтверждённый пропуск; список
  `CONFIRMED_GAP_CATEGORIES` не менялся);
* достаточность граничной проверки (документирована в докстринге):
  покрытие — НЕПРЕРЫВНЫЙ диапазон дат в поясе календаря, метки серии
  строго возрастают, локальные даты свечей монотонны; если первая и
  последняя даты внутри диапазона — все промежуточные тоже;
  промежуточные окна дополнительно проверяются попарной логикой;
* полное подтверждение (`PERFORMED_FULL_CALENDAR_VERIFIED`) — только
  при действительном покрытии ВСЕЙ серии.

**Тесты (9 новых).** Обязательные: вся серия вне покрытия; начало
серии вне покрытия; конец серии вне покрытия; серия полностью покрыта
(FULL сохраняется); между свечами нет пропусков, но даты серии вне
покрытия (ключевой регрессионный: прежде ноль инцидентов и ложный
FULL); выходные и перерывы сессий обрабатываются как прежде. Доп.:
STRICT не отклоняет неподтверждённое; детерминизм граничных
инцидентов; статус PARTIAL доходит до отчёта прогона
(`gap_verification` + `gap_analysis`).

## ФИНАЛЬНЫЕ ПРАВКИ — Correction 2: валидация чисел (math.isfinite)

**Дефект.** Валидация `split_execution_deviation()` ловила NaN
сравнением `x != x` и отрицательные/нулевые значения знаком, но
**+Infinity проходил проверку** (`inf > 0` истинно, `inf != inf` ложно)
и заражал показатели Inf/NaN вместо отказа.

**Решение (в `split_execution_deviation()`):**

* конечность ВСЕХ числовых аргументов (`reference_price`,
  `execution_price`, `quantity`, `contract_multiplier`) проверяется
  через `math.isfinite()` ДО любых вычислений (fail-closed);
* отклоняются: NaN, +Infinity, -Infinity, нулевые и отрицательные
  значения там, где они недопустимы (все четыре аргумента — строго
  положительные), bool и нечисловые типы;
* `quantity` — строго int; целые, не представимые конечным float
  (переполнение), отклоняются с `ExecutionError`, а не с наружным
  `OverflowError`;
* **формулы adverse slippage и favorable price improvement НЕ
  изменены**: порядок float-операций `quantity * multiplier * delta`
  сохранён бит-в-бит (покрыто тестом на точное равенство);
* алгоритмы исполнения, PnL и комиссии не затронуты.

**Тесты (23 новых).** Отдельный тест на каждый случай: NaN / +Inf /
-Inf / ноль / отрицательное для reference_price, execution_price,
contract_multiplier (15); quantity — ноль, отрицательное, bool,
не-int float, NaN float, Inf float, переполнение int (7);
валидные конечные значения — формулы не изменены (1).
