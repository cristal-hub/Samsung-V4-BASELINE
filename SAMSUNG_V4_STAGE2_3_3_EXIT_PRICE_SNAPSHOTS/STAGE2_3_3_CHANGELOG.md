## 2. ДОПОЛНЕНИЕ №1 — трёхуровневая модель ценовых данных инцидента (§3 ТЗ Stage 2.3.3)

### 2.1. Что требовалось

Единая модель фиксации цен при закрытии позиции: (1) первоначальная
цена в момент возникновения Exit Incident; (2) отдельный снимок
рыночной цены непосредственно перед КАЖДОЙ попыткой отправки
закрывающей заявки; (3) фактические цены исполнения из подтверждений
брокера. Подмена значений одного уровня значениями другого запрещена.

### 2.2. Что сделано

- НОВЫЙ раздел §7а STAGE2_EMERGENCY_EXIT_ARCHITECTURE.md «Модель
  ценовых данных инцидента: три уровня»:
  - **§7а.1 Уровень 1 — `exit_decision_price`**: цена доступного
    рыночного снимка в момент возникновения решения о закрытии;
    записывается ОДИН раз при создании инцидента; НЕ изменяется при
    последующих попытках; НЕ перезаписывается после reconciliation; НЕ
    подменяется ценой LIMIT/MARKET-заявки; сохраняется после
    перезапуска; отсутствие/недостоверность фиксируются явно, без
    выдуманного значения (классы EP-1…EP-6; поведение при
    недоступности котировок — D-22).
  - **§7а.2 Уровень 2 — `exit_attempt_snapshot`**: отдельная запись
    перед КАЖДОЙ попыткой (поля: incident_id, attempt_id, attempt_number,
    attempt_type — LIMIT или MARKET, snapshot_timestamp, snapshot_price,
    price_source, price_valid, order_request_id — дополняется после
    создания идентификатора заявки и до сетевого вызова, snapshot_status);
    снимок получен и сохранён НЕПОСРЕДСТВЕННО перед отправкой; каждая
    новая попытка — новая запись с новым attempt_id; предыдущие снимки
    НЕИЗМЕНЯЕМЫ; первоначальная цена инцидента НЕ используется как
    снимок последующей попытки; при отсутствии/недостоверности/устаревании
    цены (правила свежести — будущая конфигурация этапа H, значения НЕ
    изобретаются) цена из предыдущего снимка НЕ подставляется —
    попытка НЕ отправляется (fail-closed); снимок НЕ заменяет
    INTENT-before-send и НЕ отменяет существующие проверки активных
    заявок, остатков, идемпотентности и reconciliation.
  - **§7а.3 Уровень 3 — фактические исполнения**: хранятся ОТДЕЛЬНО от
    снимков; для каждой подтверждённой части — append-only запись
    {incident_id, attempt_id, order_request_id, exchange_order_id,
    executed_lots, executed_quantity, execution_price,
    execution_timestamp, execution_confirmed}; источник фактической
    цены — ТОЛЬКО подтверждение брокера (avg_exec_price cursor'а —
    execution.py:788/830; exit_price_confirmed — execution.py:789-790,
    831-833); цена LIMIT-заявки, цена MARKET-снимка, цена решения и
    цена отменённой заявки НЕ являются фактической ценой исполнения;
    ранее подтверждённые исполнения не переписываются.
- Идемпотентность расширена правилами **I-13…I-16** (неизменяемость
  цены решения; собственный снимок каждой попытки; раздельное
  хранение исполнений; атрибуция без произвола — attempt_id=UNKNOWN при
  недостоверной связи).
- События (§10 EEA): НОВЫЕ `EXIT_DECISION_PRICE_RECORDED`,
  `EXIT_ATTEMPT_SNAPSHOT_RECORDED`, `EXIT_ATTEMPT_SNAPSHOT_UNAVAILABLE`;
  EMERGENCY_EXIT_LIMIT_SENT/MARKET_SENT дополнены
  attempt_id/attempt_number; EMERGENCY_EXIT_CONFIRMED дополнен
  exit_decision_price/total_exit_slippage_ps и attempt-метриками.
- Персистенция (FILE_CHANGE_MAP M-5): раздел `emergency_incidents`
  дополнен тремя уровнями — exit_decision_price, attempts[]
  (снимки), executions[] (исполнения, append-only); атомарная запись
  сохраняется (main.py:1164-1167).

## 3. ДОПОЛНЕНИЕ №2 — расчёт и разделение проскальзывания (§4 ТЗ Stage 2.3.3)

### 3.1. Что требовалось

Все расчёты — для LONG-позиции; разделение величин без смешивания и
без двойного учёта в REALIZED LOSS.

### 3.2. Что сделано (STAGE2_RISK_MODEL_FORMULAS.md §3, §5.5, §5.6, §6, §8, §9)

- **total_exit_slippage_ps = exit_decision_price - exit_exec_price**
  — общее отклонение от ПЕРВОНАЧАЛЬНОГО решения; положительное —
  неблагоприятное (исполнение хуже решения), отрицательное —
  исполнение лучше цены решения; для ВСЕХ типов выхода, после полного
  подтверждённого закрытия.
- **attempt_slippage_ps = attempt_snapshot_price -
  attempt_exit_exec_price** — отклонение по КОНКРЕТНОЙ попытке;
  `attempt_exit_exec_price` — средневзвешенная цена ТОЛЬКО подтверждённых
  исполнений данной попытки; попытка без исполнений —
  attempt_exit_exec_price = NOT_APPLICABLE и attempt_slippage_ps =
  NOT_APPLICABLE; проскальзывание по цене неисполненной или отменённой
  заявки НЕ рассчитывается.
- **exit_exec_price = SUM(execution_price_i × executed_quantity_i) /
  SUM(executed_quantity_i)** — средневзвешенная по ВСЕМ подтверждённым
  исполнениям инцидента; частичные исполнения LIMIT и последующие
  MARKET-исполнения включаются ТОЛЬКО после подтверждения брокером;
  количество соответствует фактически подтверждённым исполнениям.
- **stop_execution_slippage_ps = max(0, sl_price - exit_exec_price)** —
  сохранён БЕЗ изменений по формуле ред. 2.3.2; только для стоповых
  инцидентов; для остальных — NOT_APPLICABLE; stop_price_deviation_ps
  (знаковое) — без изменений.
- Термин ред. 2.3.2 `exit_slippage_ps` ВЫВЕДЕН ИЗ УПОТРЕБЛЕНИЯ на
  уровне контракта (семантика «цена перед заявкой → факт» сохранена в
  attempt_slippage_ps — снимок попытки и есть «цена перед заявкой»
  этой попытки); существующее ДЕНЕЖНОЕ CSV-поле `exit_slippage`
  (main.py:2466) сохраняет имя и единицы (NO PYTHON CODE CHANGES).
- Разложение стопового инцидента уточнено:
  `stop_price_deviation_ps = breach_depth_at_trigger +
  total_exit_slippage_ps`, где `breach_depth_at_trigger = sl_price -
  exit_decision_price` (>= 0 для защитного срабатывания).
- НОВЫЙ §5.6 RMF «Разделение величин проскальзывания выхода и запрет
  суммирования»: таблица четырёх величин (total/attempt/stop-поля/
  exit_exec_price) с точками сравнения и применимостью; суммирование
  total+attempt, attempt-попыток между собой и со stop-полями
  ЗАПРЕЩЕНО; единственная точная декомпозиция — через breach_depth +
  total.
- НОВОЕ правило **DC-8** (матрица §6 RMF): ни одна из величин
  total_exit_slippage_ps / attempt_slippage_ps / stop_price_deviation_ps /
  stop_execution_slippage_ps НЕ добавляется к realized_loss как член;
  общая статистика и пер-попытковая статистика НЕ приводят к двойному
  учёту одного и того же проскальзывания; DC-7 расширен новым списком
  полей (правило сохранено).
- Числовой пример §8 (шаги 6-8): сохранены ВСЕ числа; терминология
  обновлена (exit_decision_price = 97.90 — один раз; единственная
  попытка attempt_snapshot_price = 97.90; attempt_exit_exec_price =
  96.80; total_exit_slippage_ps = 1.10; attempt_slippage_ps = 1.10 —
  совпадает при одной попытке; разложение 1.17 = 0.07 + 1.10; контроль
  DC-8: «4.27912 + 1.10» не имеет смысла).
- §5.5 RMF дополнен пп. 8-9: атрибуция исполнений попыткам (связь
  attempt_id → order_request_id) и запрет произвольной атрибуции при
  недостоверной связи (attempt_id=UNKNOWN; инцидент-уровень — при
  подтверждённой связи с инцидентом и подтверждении брокером).
- §9 RMF: четыре новых краевых случая (попытка без исполнений;
  отсутствующий/устаревший снимок; неизвестная связь с попыткой;

## 4. ДОПОЛНЕНИЕ №3 — порядок работы и восстановление после перезапуска (§5–§6 ТЗ Stage 2.3.3)

### 4.1. Порядок работы с ценовыми данными (§7а.4 EEA — 14 шагов)

1. Создаётся Exit Incident. 2. Сохраняется первоначальный
exit_decision_price. 3. Reconciliation и подтверждение остатка. 4.
Перед первой LIMIT-попыткой — отдельный exit_attempt_snapshot. 5.
LIMIT INTENT. 6. Отправка LIMIT-заявки. 7. Частичные исполнения
сохраняются отдельно. 8. При отмене/завершении LIMIT — reconciliation.
9. Перед MARKET-эскалацией — НОВЫЙ снимок с НОВЫМ attempt_id. 10.
Проверка отсутствия активной закрывающей заявки и подтверждение
остатка. 11. MARKET INTENT. 12. Отправка MARKET-заявки. 13.
Подтверждённые исполнения сохраняются отдельно. 14. После полного
подтверждённого закрытия — расчёт итоговой средневзвешенной цены и
показателей проскальзывания.

Снимок перед попыткой НЕ заменяет INTENT-before-send и НЕ отменяет
существующие проверки активных заявок, остатков, идемпотентности и
reconciliation. Точки FSM T-05/T-16 дополнены снимком в «Сохраняемые
данные (до действия)».

### 4.2. Восстановление после перезапуска (§6.5 EEA — правило R-10)

- восстановление первоначальной цены решения (уровень 1);
- восстановление ВСЕХ снимков попыток (уровень 2, в порядке
  attempt_number);
- восстановление связей incident_id → attempt_id → order_request_id
  (и далее exchange_order_id — из реестра);
- восстановление ВСЕХ подтверждённых частичных исполнений (уровень 3,
  append-only);
- ЗАПРЕТ повторного создания уже отправленной попытки (попытка
  восстанавливается по записям INTENT/SENT — I-7);
- ЗАПРЕТ использования старого снимка для новой попытки (новая попытка
  — новый attempt_id и новый снимок);
- восстановление незавершённого инцидента БЕЗ потери истории;
- при невозможности достоверно восстановить связь исполнения с
  попыткой — исполнение НЕ приписывается произвольной попытке
  (attempt_id=UNKNOWN), неопределённость сохраняется, применяется
  существующая fail-closed модель (UNCERTAIN и сверка — I-6/I-11).

Правило R-9 сохранено без изменений; T-26 дополнен восстановлением
ценовой истории.

### 4.3. Fail-closed при невозможности получить цену (§7а.5 EEA)

Нет валидной цены для снимка попытки (EP-1…EP-6; устарела по правилам
будущей конфигурации) → запись INVALID, попытка НЕ отправляется,
событие EXIT_ATTEMPT_SNAPSHOT_UNAVAILABLE; НИКАКАЯ цена (цена решения,
снимок предыдущей попытки, цена предыдущей заявки) НЕ подставляется.
Противоречие между снимком и подтверждённым исполнением → фактом
считается ТОЛЬКО подтверждение брокера.
