## 2. Требование T-1: единый код расчёта сигналов

Один и тот же модуль стратегии должен использоваться и в live-цикле
(main.py:5260 `sm.get_signal(df, price, drop_incomplete=True)`), и в
лаборатории. Условия (все основаны на ФАКТАХ):

1. Сигнальная функция принимает **только** (candles_df, last_price,
   drop_incomplete) и внутреннее состояние — никакого прямого чтения
   часов/файлов/сети внутри стратегии (сегодня выполняется; ФАКТ strategy.py).
2. Все зависящие от времени решения выражаются через **входные данные**
   (время свечи — index DataFrame; сегодня гистерезис использует
   `candles_df.index[-1]` — strategy.py:100).
3. Источник времени движка инъектируется: сегодня `datetime.now(timezone.utc)`
   вызывается напрямую в main.py (645, 2258-2269, 2359, 3031-3033 и др.) —
   для backtest это главный «утечка времени» (ВЫВОД). Требование: все
   моменты (order_send_time, requested_at, hold_minutes) берутся из
   движка-обёртки `clock()`; стратегия — не исключение.

## 3. Требование T-2: сериализуемое состояние стратегии

Гистерезис ADX — состояние между вызовами (strategy.py:34-43):
`_last_regime`, `_regime_streak`, `_last_regime_candidate`,
`_last_regime_candle_time`. Сегодня:

- в live оно живёт в памяти и **не персистится** — после рестарта режим
  определяется немедленно (strategy.py:102-114);
- в CSV-событиях диагностик частично виден (`regime`,
  `regime_candidate`, `regime_streak` — main.py:1055-1064).

Требования:

1. Состояние стратегии — сериализуемый dict, сохраняемый в state.json и
   восстанавливаемый при старте (контракт `get_state()/set_state()`).
2. В backtest — либо точная реконструкция последовательностью свечей,
   либо тот же сериализованный формат для чекпоинтов.
   **ИСПРАВЛЕНО Stage 1.1:** прежняя формулировка «детерминированно,
   т.к. гистерезис — функция последовательности уникальных свечей»
   верна ТОЛЬКО при изолированном состоянии per-FIGI. Подтверждено
   (addendum §1): сегодня состояние гистерезиса — ОДНО на процесс,
   обслуживает все FIGI (main.py:5663, 5237, 5260), не сбрасывается
   между FIGI (strategy.py:188-190), а «та же свеча» распознаётся
   глобально (strategy.py:118-127) — при таком коде гистерезис является
   функцией ЧЕРЕДУЮЩЕЙСЯ последовательности вызовов по ВСЕМ инструментам,
   и реконструкция «свечи одного инструмента» не воспроизведёт
   live-поведение. Требование: после внедрения изоляции состояния
   per-(strategy_id, FIGI) (STRATEGY_SWITCH §3, исправленная
   версия) реконструкция по свечам отдельного инструмента становится
   валидной; до этого backtest обязан воспроизводить фактический
   порядок вызовов.
3. `min_candles_required` кэшируется при создании менеджера (strategy.py:32) —
   при централизованной конфигурации кэш недопустим: параметр должен читаться
   из замороженного снапшота (иначе тест с подменой параметра даст другой
   результат — ФАКТ подтверждается различием поведения до/после конструктора).

## 4. Требование T-3: отделимость расчёта SL/TP

`calculate_sl_tp` детерминирован от (entry_price, direction, candles_df)
(ФАКТ risk_manager.py:233-259). Требования:

1. Переезд в контракт стратегии (STRATEGY_SWITCH §3) с сохранением точной
   семантики (max(STOP_LOSS, MIN_STOP_LOSS), ATR-кап MAX_ATR_STOP_PERCENT,
   зеркальные ветки BUY/SELL, отбраковка sl<=0/tp<=0).
2. В backtest — тот же метод на том же окне свечей; окна и правила усечения
   (drop_incomplete: удаляется только свеча с явным False — strategy.py:412-425)
   должны воспроизводиться симулятором байт-в-байт.

## 5. Требование T-4: интерфейс исполнения и его две реализации

ФАКТ: движок вызывает у клиента ровно следующий набор операций
(PARAMETER_USAGE_MAP §5):

| Операция | Live-реализация | Требование к backtest-реализации |
|---|---|---|
| `get_last_prices(figis)` | tinkoff_client.py:253-268 | цена свечи на момент решения |
| `get_historical_candles(figi, days, interval)` | 240-251 | окно истории из симулируемой ленты |
| `get_instrument_info(figi)` | 270-301 | статическая таблица инструментов (lot, tick) |
| `get_positions()` | 315-435 | позиция симулятора (те же PositionData: лоты со знаком, direction) |
| `get_account_balance()` | 303-313 | баланс симулятора |

1. Возвратные значения обязаны сохранять **fail-closed семантику**:

   config.COMMISSION_PER_SIDE (main.py:2470, 2950); backtest обязан
   поддерживать ОБА источника, чтобы CSV-сравнение полей

## 6. Требование T-5: детерминизм и воспроизводимость

1. Один запуск = одна замороженная конфигурация (STRATEGY_SWITCH §6):
   config_hash в каждом событии/CSV-строке — обязательное условие
   сопоставимости backtest и live прогонов.
2. Асинхронность не должна влиять на решения: сегодня порядок вызовов внутри
   цикла фиксирован (§3 CURRENT_ARCHITECTURE_MAP), но события внутри цикла
   приходят от API в реальном времени. Backtest обязан воспроизводить
   **ту же последовательность обработки** (SL/TP → closing → poll → promote →
   reconcile → входы), иначе защитные механизмы ведут себя иначе.
3. Внутрибарные данные: live-поллинг 30 с пропускает внутрибарные экстремумы
   (осознанное решение — комментарий execution.py:884-888; MAE/MFE берутся
   ТОЛЬКО из 5-мин свечей high/low). Backtest, который подаёт
   тиковые данные, даст другие MAE/MFE → правило: симулятор работает
   на **5-мин свечах**, как live (иначе сравнение невалидно).
4. Событийный журнал: все решения логируются с временем свечи
   (main.py:1055-1064) — достаточная основа для по-шагового сравнения
   backtest/live.

## 7. Требование T-6: параметрическая гигиена

1. Категории A-E разделены (STRATEGY_SWITCH §2): backtest может менять
   только категорию A (+ сценарные B), не трогая движок D/C — иначе
   сравнение прогонов искажается.
2. «Тихие дефолты» запрещены (§6 ТЗ): в backtest отсутствие параметра =
   ошибка, а не getattr-fallback (ФАКТ сегодняшнего `getattr(config, ...)`
   — main.py:1952-1953, 5139; execution.py:923, 1003 — паттерн не
   воспроизводить).
3. Параметры-призраки (STARTING_BALANCE, POSITION_QUANTITY_IS_LOTS —
   HARDCODED §5.1) в новую схему не переносятся, чтобы лаборатория не
   «оптимизировала» несуществующие ручки.

## 8. Требование T-7: сохранение защит в исследовательском режиме

Мандаты этапов (RESEARCH ONLY / NO LIVE ORDERS) реализуются существующими
механизмами (ФАКТ): тройной запрет LIVE (config.validate config.py:162-163;
tinkoff_client.py:182-184; build_safety.py:78-83) и guard Режима A
(build_safety.py:86-113). Требование: backtest-сборка наследует те же
механизмы (guard включён по умолчанию; LIVE недостижим в любых ветках
архитектуры), чтобы исследовательский код физически не мог отправить ордер.

## 8а. Требование T-8: модель исполнения backtest и её допущения
(ДОБАВЛЕНО Stage 1.1, ТЗ 4.6 — ПРЕДЛОЖЕНИЕ)

### T-8.1. Отдельная детерминированная event-driven модель

Исторический симулятор НЕ должен притворяться точной копией асинхронной
брокерской инфраструктуры T-Invest. Предлагается отдельная
детерминированная event-driven модель исполнения:

- вход — зафиксированная лента 5-мин свечей (та же гранулярность, что и
  live: MAE/MFE и экстремумы live берутся из 5-мин свечей —
  execution.py:884-888, ФАКТ; T-5.3);
- фиксированный порядок обработки событий бара (открытие → внутрибарные
  уровни → закрытие) и та же последовательность шагов цикла, что и live
  (SL/TP → closing → poll → promote → reconcile → входы — T-5.2);
- решения — функции только от уже увиденных данных (без заглядывания
  в будущие бары).

### T-8.2. Обязательные документируемые допущения модели

Каждое допущение — явный параметр конфигурации симулятора, входящий в
config_hash (T-5/T-6):

| # | Допущение | Требование |
|---|---|---|
| A-1 | Комиссия | модельная ставка и источник (фактическая/модельная — T-4.2) |
| A-2 | Проскальзывание | модель; применяется к цене заполнения |
| A-3 | Bid/ask spread | модель спреда; заполнение по неблагоприятной стороне |
| A-4 | Гэпы | заполнение по цене открытия бара при уровне внутри гэпа |
| A-5 | Частичное исполнение | явная модель частичных заполнений и их учёта |
| A-6 | Ликвидность | ограничение объёма заполнения (или явное «не моделируется») |
| A-7 | Market impact | явное «не моделируется» либо модель |
| A-8 | Tick size | округление цен до тика инструмента |
| A-9 | Lot size | кратность лотов (инвариант лотов `get_positions`) |
| A-10 | Торговые сессии | календарь сессий; события вне сессии не обрабатываются |

### T-8.3. Консервативное правило внутри одной свечи (инвариант)

Если OHLC-свеча показывает, что внутри одной свечи достигнуты и SL, и TP,
но порядок событий неизвестен, backtest использует КОНСЕРВАТИВНОЕ
допущение: первым сработал неблагоприятный для стратегии уровень
(например, SL), если более точные данные не позволяют установить
реальную последовательность. Выбор более выгодного порядка событий
задним числом ЗАПРЕЩЁН. Правило — инвариант модели, не опция.

### T-8.4. Воспроизводимость

Одинаковые данные + параметры + настройки модели → байт-в-байт одинаковый
результат (события, заявки, CSV-строки). Версия модели исполнения входит
в config_hash и в шапку журналов (T-5, STRATEGY_SWITCH §6).
