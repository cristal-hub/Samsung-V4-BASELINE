# STRATEGY_SWITCH_ARCHITECTURE.md

## Целевая архитектура независимых стратегий и переключения одной настройкой

**Мандаты:**

```
STRATEGY LOGIC: UNCHANGED
RESEARCH ONLY
NO THRESHOLD IS OPTIMIZED
NO FILTER IS INSTALLED
NO LIVE ORDERS
```

**Статус документа:** всё содержимое разделов 2-9 — **ПРЕДЛОЖЕНИЕ**.
На этапе 1 ничего не реализовано и не изменено (ФАКТ: рабочее дерево
репозитория не модифицировалось; git status чист). Реализация — предмет
отдельного одобрения (§8 ТЗ, IMPLEMENTATION_ROADMAP.md).

---

## 1. Цель и принципы

Цель (§1 ТЗ): превратить Samsung V4 в исполнительную платформу, где активная
стратегия выбирается одной настройкой (`ACTIVE_STRATEGY = "strategy_001"`),
каждая стратегия несёт собственные логику входа/выхода и параметры, а общий
движок (риск, исполнение, учёт, сверка, восстановление) остаётся
стратегиенезависимым.

Принципы проектирования (следуют из ФАКТОВ текущего кода):

1. **Не изобретать заново то, что уже надёжно работает.** Десять защитных
   механизмов текущего кода (CURRENT_ARCHITECTURE_MAP.md §7) сохраняются как
   есть: INTENT-before-send, per-order cursor, fail-closed сверка,
   append-only реестр, тройной запрет LIVE, guard заявок, атомарные записи.
2. **Fail-closed везде** (§6 ТЗ): неизвестная стратегия, невалидный параметр,
   невалидная комбинация, изменённый хеш конфигурации при рестарте —
   старт запрещён или входы запрещены; подстановка значений по умолчанию
   запрещена (текущий `getattr(config, ..., default)`-паттерн —
   main.py:1952-1953, 5139 — в новом слое не воспроизводится).
3. **Переключение — только через рестарт процесса** (§3 ТЗ: «безопасно
   переключать стратегию при перезапуске»); hot-reload не проектируется.
4. **Единственный источник значений** — файлы конфигурации стратегий;
   `config.py` в предложенной архитектуре содержит только движок и
   подключение (категории C/D), без сигнальных констант.
5. Атрибутация: каждая позиция, заявка, CSV-строка и событие несут
   `strategy_id` + хеш конфигурации.

## 2. Разделение «движок / стратегия» (ПРЕДЛОЖЕНИЕ на основе ФАКТОВ §2)

**Остаётся общим движком (стратегиенезависимо):**

| Компонент | Основание (ФАКТ) |

| Исполнение ордеров и опрос статусов | tinkoff_client.py; poll_open_orders main.py:4254-4537 |
| Реестр заявок (INTENT/SENT/UNCERTAIN, блокировки FIGI) | order_ledger.py |
| Учёт позиций, per-order cursor, UNCERTAIN/RECOVERY-механика | execution.py |
| Reconcile, адопция, В2/В3, восстановление | main.py:2018-2223, 4831-5108 |
| Persistence (state.json), CSV, события | main.py:1144-1238; logger.py |
| Категория B риск-лимитов: экспозиция, лимиты на инструмент/день, размер партии по риску | risk_manager.py:87-207 |
| Безопасность сборки: Режим A/B, guard, sandbox-only | build_safety.py |
| Скринер/вселенная (параметризуется категорией E) | screener.py |

**Уходит в слой стратегии (сегодня смешано или захардкожено):**

| Компонент | Сегодня (ФАКТ) | Целевое размещение |
|---|---|---|
| Сигнальная логика (режим рынка, MA/BB+RSI, фильтры, объём) | strategy.py | `strategies/strategy_001/signal.py` — уже почти чистый контракт (без обращений к клиенту) |
| Расчёт SL/TP | risk_manager.py:233-259 (помечен «(стратегия)») | контракт стратегии: `compute_exit_levels(entry, direction, candles)`; движок вызывает его на тех же свечах (main.py:4072, 4808 — места вызова сохраняются) |
| Индикаторные параметры и пороги | config.py:63-87 + PROFILE-ветвление 78-119 | файл параметров стратегии + схема валидации |

| Безубыток/трейлинг (С1) | execution.py:872-976 (пока выключен, config.py:50) | опциональный модуль стратегии (политика переноса SL); движок предоставляет колбэк-точку после обновления экстремумов (execution.py:999-1004) |

**ПРЕДЛОЖЕНИЕ по границе риска:** категория B остаётся движком, но SL/TP —
стратегии. Движок сохраняет право последней инстанции: он не позволяет
стратегии задать уровни, нарушающие базовые инварианты риска (например,
`sl <= 0` уже отбрасывается risk_manager.py:257-258 — эта проверка
переносится в движок без изменения семантики).

## 3. Контракт стратегии (ПРЕДЛОЖЕНИЕ)

Имена методов подобраны по фактическим точкам вызова текущего кода
(§4 ТЗ: «не навязывать имена без анализа»). Минимальный контракт:

```python
class StrategyBase:                      # ПРЕДЛОЖЕНИЕ: интерфейс, не существует в коде
    strategy_id: str                     # стабильный идентификатор ("strategy_001")
    strategy_version: str                # версия логики
    params: dict                         # подтверждённые схемой значения

    def __init__(self, params: dict, context: EngineContext) -> None: ...
        # context: доступ к движку (леса/цены через движок, НЕ к клиенту напрямую)

    def on_start(self, candles_provider) -> None: ...
        # проверка готовности: достаточно ли данных; сегодня это MIN_CANDLES_FOR_SIGNAL
        # (strategy.py:32) и проверка len в get_signal/get_market_regime

    def get_signal(self, candles_df, last_price: float, drop_incomplete: bool) -> tuple[str, str]: ...
        # ТОЧНОЕ соответствие существующей сигнатуре strategy.py:177-182 —
        # движок вызывает её в main.py:5260; контракт сигнатуры сохраняется

    def compute_exit_levels(self, entry_price: float, direction: str,
                            candles_df) -> tuple[Optional[float], Optional[float]]: ...
        # соответствует rm.calculate_sl_tp (risk_manager.py:233-259) и местам
        # вызова main.py:4072, 4808

    def on_position_opened(self, pos) -> None: ...        # опционально: телеметрия С1
    def on_extremes(self, pos, candle_high, candle_low, atr) -> Optional[float]: ...
        # точка безубытка/трейлинга: сегодня _update_sl (execution.py:913-966);
        # стратегия может вернуть новый sl или None (не менять)

    def get_diagnostics(self) -> dict: ...
        # сегодня: last_adx_value/_last_regime/_regime_streak (strategy.py:42-43),
        # используются в _log_strategy_diagnostic (main.py:1055-1064)
```

**ПРЕДЛОЖЕНИЕ:** stateful-состояние стратегии (гистерезис ADX:
`_last_regime/_regime_streak/_last_regime_candidate/_last_regime_candle_time`,
strategy.py:34-43) объявляется частью стратегии и сериализуется в
state.json (`state.strategy[strategy_id].runtime_state`) — сейчас оно НЕ
персистится (после рестарта режим определяется немедленно заново,
strategy.py:102-114). Для совместимости с исторической лабораторией это
обязательно (BACKTEST_COMPATIBILITY_REQUIREMENTS.md §3).

## 4. Реестр стратегий и переключение одной настройкой (ПРЕДЛОЖЕНИЕ)

```
candidate/
  strategies/
    __init__.py              # STRATEGY_REGISTRY: dict[strategy_id -> модуль]
    strategy_001/
        strategy.py          # логика (перенос strategy.py без изменения логики)
        params.default.py    # значения по умолчанию категории A (база 9/21/100…)
        profiles.py          # FORCE_TRADE/SANDBOX_TEST/… как вариантные наборы
        schema.py            # схема: имя, тип, единицы, диапазон, зависимости
```

- **Регистрация:** явный словарь в `strategies/__init__.py` (импортируемый
  реестр; рефлексия/сканирование каталогов не используются — меньше
  сюрпризов). Новая стратегия = новый каталог + одна строка в реестре.
- **Выбор:** единственная настройка запуска:

  ```
  ACTIVE_STRATEGY = "strategy_001"     # ПРЕДЛОЖЕНИЕ: в non-code файле запуска
  ```

  ПРЕДЛОЖЕНИЕ: держать её в отдельном JSON/ENV (не в `.py`), т.к. требование
  §2.1 ТЗ — «можно ли менять его без изменения Python-кода»; сегодня единственный
  такой механизм — env (config.py:14-19). Неизвестное имя → отказ старта
  (fail-closed, аналог существующего `RuntimeError("Неизвестный PROFILE")`,
  config.py:118-119).
- **Загрузка параметров:** движок читает `params` выбранной стратегии,
  применяет вариант (profile), затем проходит валидацию схемы (§5).
- **Совместимость:** каждая стратегия объявляет требуемые возможности движка
  (напр. `requires: candles_5min, intraday_extremes`) — движок проверяет при
  старте; стратегия, требующая не подключённой возможности, не стартует.

## 5. Валидация параметров (ПРЕДЛОЖЕНИЕ; закрывает ФАКТ-пробелы INVENTORY §1, HARDCODED §6)

На каждый параметр схемы:

1. **Тип** (int/float/bool/str/enum) — жёстко; bool-ловушки отсекаются
   (сегодня `if getattr(config, "BE_TRAIL_ENABLED", False)` истинно для
   непустой строки — main.py:5139).
2. **Диапазон/множество** — только те границы, которые доказуемы из кода
   (примеры корректных схем: ADX_HYSTERESIS_CANDLES ≥ 1 — иначе `tail(0)`
   деградирует гистерезис, strategy.py:84-88; VOLUME_CONFIRMATION_WINDOW ≥ 3 —
   strategy.py:444-446; TAKE_PROFIT_RATIO > 0 — risk_manager.py:244-258).
   Диапазоны, не определённые в коде, в схему не вносятся «по вдохновению»
   (§2.1 ТЗ) — помечаются «не определён» и валидируются только типом/знаком.
3. **Кросс-проверки** (по списку HARDCODED_LOGIC_AND_DEPENDENCIES.md §6):
   MIN_CANDLES_FOR_SIGNAL ≥ max(MA_SLOW+2, BB+RSI, ADX+1, TREND_FILTER_MA);
   CANDLES_LOOKBACK_DAYS обеспечивает MIN_CANDLES_FOR_SIGNAL 5-мин свечей;
   RECONCILE_CONFIRM_MIN_AGE_SECONDS ≥ 1 (или производная от цикла);
   RSI_OVERSOLD < RSI_OVERBOUGHT; COMMISSION_PER_SIDE ≥ 0 и т.п.
4. **Запрет тихой подстановки:** любое невалидное значение → отказ старта с
   перечнем ошибок (по образцу config.validate() config.py:147-163), БЕЗ
   fallback-значений.
5. **Неиспользуемые параметры не переносятся** (STARTING_BALANCE,
   POSITION_QUANTITY_IS_LOTS — HARDCODED §5.1) — мёртвые объявления не
   «легализуются» в новой схеме.

## 6. Фиксация конфигурации и идентификация сделок (ПРЕДЛОЖЕНИЕ)

1. **Снапшот эффективной конфигурации при старте:** движок строит полный
   словарь фактических значений (движок + выбранная стратегия + вариант),
   вычисляет `config_hash` (SHA256 канонического JSON) и `strategy_id`,
   `strategy_version`, `params_version`.
2. **Заморозка:** словарь записывается в `state.json` (`state.config_snapshot`)
   и печатается в журнал при старте (полная распечатка параметров — §6 ТЗ).
   Изменение конфигурации в рантайме невозможно: объект иммутабелен
   (MappingProxyType / только чтение).
3. **Каждая сделка/заявка/событие** получает:
   - `research_events.jsonl`: расширение шапки log_event
     (сегодня profile/commission_mode/build_version — logger.py:183-189)
     полями `strategy_id`, `config_hash`;
   - `research_trades.csv`: добавить колонки `strategy_id`, `config_hash`
     (схема допускает добавление «в конец» — logger.py:6-15 описывает
     существующую авто-миграцию шапки);
   - `order_ledger.jsonl`: `strategy_id` в RECORD_FIELDS записи INTENT
     (append-only журнал это допускает — order_ledger.py:73-83);
   - `TrackedPosition.strategy_id` (state.json сохраняет автоматически через
     asdict — execution.py:303-306).
4. **Воспроизведение сделки с теми же настройками:** по CSV-строке
   (strategy_id + config_hash) → снапшот конфигурации восстанавливается из
   `state.config_snapshot` архива (state.json-ы хранятся оператором по
   BUILD_VERSION/config_hash; ПРЕДЛОЖЕНИЕ: движок копирует
   `config_snapshot_<hash>.json` рядом со state.json при каждом старте).
   Плюс журнал событий содержит все сигналы с временем свечи
   (main.py:1055-1064) — расчёт воспроизводим на исторических свечах.

## 7. Безопасное переключение при открытых позициях (ПРЕДЛОЖЕНИЕ; §3 ТЗ)

Требование ТЗ: «переключение стратегии не должно приводить к потере контроля
над уже открытыми позициями» и «не считать автоматическое закрытие всех
позиций правильным решением без обоснования».

**Предлагаемая политика (три режима, выбирается оператором в настройке
`strategy_switch_policy`):**

| Режим | Поведение | Обоснование |
|---|---|---|
| **A. BLOCK (по умолчанию)** | Старт с новой стратегией запрещён, пока в state.json есть позиции в ACTIVE_STATES (OPEN/CLOSING/UNCERTAIN/RECOVERY — execution.py:212-215) | Максимально безопасно: у новой стратегии другие SL/TP-правила; внезапная смена правил управления позицией меняет исход сделки, открывшейся по другой логике. Совпадает с существующей практикой: RECOVERY/UNCERTAIN и сегодня блокируют входы до разрешения (main.py:5186-5225) |
| **B. INHERIT (явное разрешение оператора)** | Загружаются ОБЕ стратегии: новая — активна для новых входов; старая — в режиме «сопровождения» только для СВОИХ позиций (позиции несут `strategy_id`, execution-слои вызывают exit-логику автора позиции). После закрытия последней позиции старой стратегии её экземпляр выгружается | Сохраняет контроль над позициями без автозакрытия; требует атрибутации позиций (§6.3) — технически достижимо: `check_all` сегодня итерирует позиции (execution.py:991-1022), источник exit-правил можно направлять по `pos.strategy_id` |
| **C. OPERATOR_CLOSE** | Как A, но с явным предложением оператору закрыть позиции штатными механизмами (ручная продажа уже поддержана В3-механикой двойного подтверждения, main.py:1932-2011) | Для случаев, когда оператор сознательно завершает работу старой стратегии |

**Автозакрытие всех позиций при переключении НЕ предлагается**: это меняет
результаты сделок, открывшихся по иной логике, и противоречит мандату
STRATEGY LOGIC: UNCHANGED по отношению к живым сделкам; кроме того, у робота
уже есть строгая механика закрытия (per-order cursor, запрет фиктивного P&L),
и массовая принудительная SELL добавила бы неопределённости без пользы.

**Синхронизация с существующими блокировками:**
- trading.flag остаётся отдельным разрешителем входов (main.py:847-868);
- при переключении с INHERIT блокировки BUY по FIGI/uncertain_state продолжают
  действовать глобально (order_ledger.py:577-590) — новая стратегия не может
  «влезть» в инструмент с неопределённостью старой;
- RECOVERY-позиции всегда остаются под контролем оператора (автозакрытие
  запрещено и сегодня — main.py:153, 4684-4686).

## 8. Защита от случайного смешивания настроек (ПРЕДЛОЖЕНИЕ)

1. Пространства имён изолированы: параметры стратегии живут только в её
   каталоге; движок не читает сигнальные константы из config.py (после
   переноса категория A исчезает из config.py).
2. Валидатор отклоняет неизвестные ключи (строгая схема; опечатка = ошибка
   старта, а не тихое игнорирование).
3. Снапшот-хеш: при рестарте движок сравнивает `config_hash` в state.json с
   текущим; несовпадение при наличии открытых позиций старой конфигурации →
   входы заблокированы до явного подтверждения оператора (аналог поведения
   «state.json отсутствует — входы запрещены», main.py:5691-5696).
4. Журналирование: каждое событие несёт strategy_id+config_hash (§6.3) —
   смешивание видно постфактум.
5. Версии: `strategy_version` меняется при изменении логики,
   `params_version` — при изменении значений; фиксируются в CSV/событиях.
