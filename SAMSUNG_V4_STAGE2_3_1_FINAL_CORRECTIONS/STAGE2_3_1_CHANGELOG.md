## 2. Коррекция №1 — точка интеграции EmergencyExitController (критическая)

### 2.1. Замечание аудита

В Stage 2.3 `EmergencyExitController` описан как механизм, запускаемый
ПОСЛЕ существующего защитного выхода `check_all()` (M-7 «интеграция в
торговый цикл ПОСЛЕ шага защитных выходов»; §11 EEA ред. 2.3 «контроллер
включается ПОСЛЕ него»). Аудит: архитектурная ошибка — фактическая
последовательность кода такова, что к моменту запуска контроллера первая
рыночная заявка УЖЕ отправлена, и гибридная последовательность
«лимитная попытка → рыночная эскалация» не выполняется.

### 2.2. Верификация замечания по исходному коду (Stage 2.3.1, самостоятельно)

| Шаг | Факт | Источник |
|---|---|---|
| 1 | `check_all()` обнаруживает `price <= sl_price` (для BUY), помечает позицию CLOSING и возвращает список; заявок НЕ отправляет | execution.py:1007, 1017-1022 (см. F-30) |
| 2 | Цикл получает список | main.py:5144 |
| 3 | Цикл сразу вызывает `close_position()` | main.py:5152 |
| 4 | `close_position()` отправляет рыночную SELL | main.py:2315 (`post_market_order`) |

Замечание подтверждено: M-7 «после» в ред. 2.3 исключал главный сценарий
механизма.

### 2.3. Исправление (единый контролируемый маршрут)

- Контроллер интегрируется ДО точки отправки первой закрывающей заявки:
  шаг 2г торгового цикла передаёт решения контроллеру (создание ОДНОГО
  Exit Incident + персистенция INTENT — БЕЗ заявок); НОВЫЙ шаг 2д
  `process_incidents` — ЕДИНСТВЕННАЯ точка отправки закрывающих заявок;
- прямой вызов `close_position` торговым циклом для защитных
  срабатываний УДАЛЁН из проекта; `close_position` сохраняется как
  исполнитель рыночной ноги ВНУТРИ контроллера и как механизм В3;
- запрещённые схемы зафиксированы явно: (1) рыночная SELL до контроллера;
  (2) два конкурирующих механизма SELL; (3) обход контроллера при обычном
  SL; (4) самостоятельная отправка заявок check_all(); (5) прямой вызов
  close_position циклом для to_close;
- единый контракт обработки Stop Loss: обычное пересечение / гэп /
  резкое движение через несколько уровней / повторное получение цены
  ниже стопа / восстановление цены выше стопа — ОДИН Exit Incident
  единым контроллером; гэп — АТРИБУТ (breach_kind/breach_depth из
  наблюдаемых данных), не отдельная заявка; числовой порог гэпа НЕ
  изобретён;
- конечный автомат инцидента: 13 состояний (список ТЗ + EXIT_DECIDED для
  не-стоповых причин), 27 допустимых переходов (T-01…T-27) с
  событиями/проверками/данными/действиями, 10 запрещённых переходов,
  правило перезапуска «сначала reconciliation»;
- идемпотентность I-1…I-12 (INTENT-before-send, incident_id, неизвестный
  результат отправки → reconciliation БЕЗ немедленного повторного SELL,
  запрет превышения подтверждённого остатка, запрет двух активных заявок
  инцидента);
- интеграция с check_all / close_position / execution.py / main.py /
  OrderLedger / B2 / В3 / механизмом SELL / reconciliation / состояниями
  OPEN-CLOSING-CLOSED-UNCERTAIN описана отдельно; несколько причин
  закрытия объединяются в один инцидент со сохранением ВСЕХ причин
  (защитное событие не теряется).

## 3. Коррекция №2 — модель риска: разделение проскальзываний и ценовых величин (критическая)

### 3.1. Замечание аудита

Stage 2.3 утверждал: «фактическое входное проскальзывание уже содержится
в |exec_price - sl|» (обоснование исключения SLIPPAGE_PERCENT из OPEN
ESTIMATED RISK). Аудит: утверждение некорректно, если Stop Loss
рассчитывается от фактической цены исполнения exec_price — в таком
случае расстояние до стопа характеризует риск ДВИЖЕНИЯ от фактической
цены входа до стопа, а НЕ отклонение цены исполнения от цены принятия
решения.

### 3.2. Верификация замечания по исходному коду (Stage 2.3.1, самостоятельно)

- SL действительно рассчитывается от exec_price: main.py:4072
  (`rm.calculate_sl_tp(exec_price, "BUY", df)`) → risk_manager.py:238,
  246 (`sl = entry_price - entry_price * max(...)`) — значит,
  `|exec - sl| = exec_price * max(...)` и от входного проскальзывания
  содержит только долю, пропорциональную стоп-проценту (пример: decision
  100 → exec 101, стоп 3% → расстояние 3.03 вместо плановых 3.00; внутри
  — только 0.03 из проскальзывания 1.00);
- sizing-база — decision_price: main.py:5278 → risk_manager.py:124;
  SLIPPAGE_PERCENT — единственный член friction (risk_manager.py:125);
- существующий учёт закрытия уже публикует ДЕНЕЖНЫЕ slippage-поля с той
  же семантикой знаков: main.py:2464-2466 (F-33).

Замечание подтверждено количественно.

### 3.3. Исправление (модель риска ред. 2.3.1)

- Введены ЧЕТЫРЕ ценовые величины: `decision_price`, `exec_price`,
  `sl_price`, `stop_exec_price` — с источниками (файл:строка), моментом
  появления и правилами обработки неизвестных значений;
- входное проскальзывание определено явно:
  `entry_slippage = exec_price - decision_price` (LONG: положительное =
  неблагоприятное; нормализация — цена/акцию; знаки согласованы с
  существующим CSV-учётом main.py:2464-2466);
- семь независимых составляющих риска (C1…C7) определены раздельно:
  плановое расстояние / фактическое расстояние / входное проскальзывание
  / комиссия входа / оценочная комиссия выхода / резерв исполнения стопа
  / фактическое проскальзывание выхода; смешение в одну величину
  запрещено;
- три модели риска с точными формулами, единицами, временными точками,
  источниками каждого параметра: ESTIMATED RISK (до входа), OPEN
  ESTIMATED RISK (после регистрации), REALIZED LOSS (после выхода);
- матрица недопущения двойного учёта DC-0…DC-6: SLIPPAGE_PERCENT —
  ТОЛЬКО в sizing-знаменателе (DC-1); entry_slippage НЕ добавляется в
  open_per_share_risk — прогноз убытка при стопе измеряется ОТ
  фактической цены входа (DC-2 — обоснование ред. 2.3 исправлено);
  резерв ≠ расстояние (DC-5); резерв НЕ входит в REALIZED (DC-4/DC-6);
- база оценочной комиссии выхода в OPEN ESTIMATED RISK ИЗМЕНЕНА:
  `exec_price * COMMISSION` (ред. 2.3) → `sl_price * COMMISSION` —
  сценарная цена выхода («исполнение по зарегистрированному стопу»);
  изменение задокументировано с обоснованием экономического смысла;
- согласование sizing ↔ risk reporting: контракт sizing не меняется
  (golden-защита); разница знаменателя sizing и прогноза модели
  публикуется (`risk_model_sizing_gap_ps`); вопрос включения резерва в
  sizing — D-28; RISK_BUDGET_EXCEEDED — отдельное событие при
  фактическом риске выше планового; реакция v1 — журналирование (D-15);
  автоматическая продажа/изменение позиции НЕ проектируется без решения
  владельца;
- STOP_SLIPPAGE_RESERVE сохранён как ОТДЕЛЬНЫЙ параметр (D-16); числовое
  значение НЕ установлено; до решения владельца резерв явно обозначен
  «unconfigured», и расчётный риск явно НЕ считается полным прогнозом
  гэп-риска;
- НОВЫЙ документ STAGE2_RISK_MODEL_FORMULAS.md: полная постановка +
  числовой пример (условные данные, просчитан программой; демонстрирует
  различие decision/exec/sl/stop_exec и декомпозицию
  realized↔open↔estimated).
