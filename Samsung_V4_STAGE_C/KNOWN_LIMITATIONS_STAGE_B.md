# KNOWN_LIMITATIONS_STAGE_B.md
# Известные ограничения Stage B

Дата: 2026-11-28. Пакет: `Samsung_V4_STAGE_B`.

## 1. Сознательные границы Stage B (по ТЗ — НЕ дефекты)

* **Торговый цикл не использует состояние.** Stage B — слой состояния
  (модель + хранилище + менеджер + тесты). Внедрение менеджера в
  торговую логику/стратегии выполняется на Stage C (явное внедрение
  зависимости при вызове контракта стратегии); сейчас торговая логика,
  параметры, сигналы и риск-менеджмент сознательно не тронуты.
* **evaluate_exit не реализован** (Stage C). Выход из позиции
  присутствует в состоянии только как данные (`data`), если их туда
  положит будущая логика Stage C.
* **Исторический симулятор и Sandbox-адаптер не реализованы** (запрет ТЗ).
* **engine.json не расширялся.** Явный ключ `STATE_STORE_PATH`
  задокументирован и проверяется `resolve_state_store_path`, но сам
  файл engine.json — конфигурация Stage A и не изменялся без прямой
  необходимости Stage B. Подключение ключа — этап интеграции (Stage C)
  вместе с решением владельца о фактическом пути.
* **Legacy Samsung V4 остаётся REGRESSION_ONLY** и не использует
  состояние Stage B (регресс-адаптер — regression-only по Stage A).

## 2. Технические ограничения подсистемы состояния

* **Набор символов ключей.** strategy_id и FIGI ограничены
  `^[A-Za-z0-9][A-Za-z0-9._-]*$` (лимиты 128/64 символа) — это защита
  изоляции (имена файлов, отсутствие path-обходов). Значения вне набора
  (в т.ч. юникод) отклоняются `StateValidationError`. Реальные FIGI
  (12 символов A-Z0-9) полностью совместимы.
* **Данные состояния — только JSON-совместимые значения.** Произвольные
  Python-объекты, Enum, NaN/Infinity отклоняются; set/frozenset
  нормализуются в отсортированные списки (обратное преобразование в set
  при чтении не выполняется — стратегия получает list).
* **Многопроцессный доступ не гарантируется.** Корректность при
  параллельных обращениях обеспечена для потоков ОДНОГО процесса
  (RLock хранилища + менеджера, атомарная запись tmp+os.replace).
  Доступ к одному каталогу хранилища из НЕСКОЛЬКИХ процессов
  одновременно не покрывается блокировками (нет межпроцессного
  файлового лока) — в новой архитектуре движка один процесс владеет
  одним каталогом состояния; при будущей многопроцессности потребуется
  файловый lock (вне Stage B). Отметим: `os.replace` атомарен, поэтому
  повреждения записи при межпроцессной записи не возникает, но
  «последний записавший выигрывает».
* **Каталог persistent-хранилища создаётся автоматически** при
  передаче пути (`os.makedirs(exist_ok=True)`) — сам путь при этом
  остаётся ЯВНЫМ (скрытого пути по умолчанию нет).
* **Ограничения fsync.** fsync каталога может не поддерживаться
  файловой системой — обрабатывается как не-фатальная ситуация
  (атомарность самой записи обеспечена os.replace).
* **Размер данных состояния не ограничивается** подсистемой (только
  валидность типов); ответственность за разумный объём — на логике
  стратегий (Stage C).
* **Метки времени** — ISO-8601 UTC фиксированного формата; используются
  для аудита (created_at/updated_at) и не участвуют в ключе изоляции.

## 3. Условия воспроизводимости тестов

* Тесты `strategy`/`screener` требуют реальной библиотеки
  `pandas_ta_classic` (0.9.0); при её отсутствии корневой conftest.py
  ставит заглушку и соответствующие тесты не могут исполняться
  (это поведение Stage A.2.1, сохранено как есть; сами тесты не
  ослаблялись).
* Прогон полностью offline: сети, брокера, Sandbox/LIVE-заявок нет.

## 4. Что НЕ гарантируется Stage B

* Stage B не гарантирует содержательную корректность данных, которые
  стратегия кладёт в `data` (структура данных состояния — решение
  стратегии Stage C); гарантируются изоляция, целостность схемы,
  детерминированная сериализация и fail-closed при несовместимости.
* Stage B не мигрирует какие-либо существующие данные: миграций нет,
  старые записи не переносились и не перегенерировались.
* Stage B не добавляет и не активирует торговые функции; FORCE_TRADE
  отсутствует; Stage C не начат.

# ДОПОЛНЕНИЕ STAGE B.1 — актуальные ограничения

## 5. Границы гарантии конкурентного обновления (ТЗ B.1 §5)

* **Гарантируется (один процесс):** атомарность read-modify-write для
  ВСЕХ менеджеров, работающих через ОДИН экземпляр StateStore (RLock
  хранилища), а также — усиление B.1 — для всех экземпляров StateStore
  одного процесса на одном реальном каталоге (разделяемый RLock из
  реестра по `os.path.realpath`).
* **НЕ поддерживается: несколько процессов.** Межпроцессная блокировка
  сознательно не добавлена (ТЗ B.1 §5: «не добавлять без необходимости»).
  При доступе нескольких процессов к одному каталогу хранилища файловая
  запись остаётся атомарной (tmp + `os.replace`), повреждения JSON не
  возникает, но read-modify-write между процессами НЕ сериализуется —
  возможна потеря обновления («последний записавший выигрывает»).
  Если в будущем потребуется многопроцессный доступ — понадобится
  файловый lock (например, fcntl/flock), это изменение вне Stage B.1.
* **Контракт updater.** updater вызывается ПОД замком хранилища; он
  обязан быть чистой быстрой функцией: не блокировать, не ждать другие
  потоки, чьи операции требуют тот же замок (иначе взаимное ожидание).
  Повторный вход в то же хранилище из updater того же потока разрешён
  (RLock реентерабелен) и покрыт тестом. Повторный вход через ДРУГОЙ
  менеджер того же хранилища тоже реентерабелен; через менеджер ДРУГОГО
  хранилища — допускается, но не рекомендуется (порядок замков должен
  быть согласованным; подсистема не сериализует разные замки).

## 6. Имена файлов записей (ТЗ B.1 §3)

* Имя записи — инъективное длинно-префиксное кодирование
  `{len(s1)}--{s1}--{len(s2)}--{s2}.json` (алгоритм и доказательство
  инъективности — STAGE_B_ARCHITECTURE_REPORT.md, раздел 11).
* **Скрытой миграции старого формата НЕТ** (Stage B не принят,
  пользовательские данные не мигрируются): записи, сохранённые пакетом
  Stage B со старым именем `strategy_id__figi.json`, НЕ читаются и НЕ
  переносятся автоматически. Для пары такое имя выглядит отсутствующей
  записью (создаётся новое независимое состояние при первом обращении);
  при `list_states()` неформатное имя даёт `StateCorruptionError`
  (fail-closed), файл не удаляется и не изменяется. Если старые записи
  Stage B нужно сохранить — владелец переносит их ЯВНО, осознанным
  решением (в Stage B.1 для этого не предусмотрено кода миграции
  сознательно).
* Набор символов ключей не изменился: `^[A-Za-z0-9][A-Za-z0-9._-]*$`
  (лимиты 128/64). Максимальная длина имени записи — 206 символов.

## 7. Что осталось неизменным из ограничений Stage B

Все ограничения разделов 1–4 (сознательные границы Stage B, набор
символов ключей, JSON-совместимость данных, условия воспроизводимости
тестов, отсутствие миграций) действуют без изменений; Stage B.1 не
расширяет торговую функциональность и не начинает Stage C.
