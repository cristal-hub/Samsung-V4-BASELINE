## 2. Доказательство №2 — в новом коде нет брокерских действий

`candidate/strategy_contracts.py` (единственный новый production-файл)
не содержит:

* сетевых вызовов: нет `requests`, `urllib`, `http`, socket-вызовов,
  gRPC, websockets;
* брокерского SDK: нет импортов tinkoff SDK / tinkoff_client;
* заявок: нет слов place/order/post/cancel в смысле брокерских
  действий; нет вызовов модулей execution.py / risk_manager.py;
* изменений режимов торговли: нет трогания торговых флагов,
  FORCE_TRADE, enable_sandbox_execution;
* обращения к старым runtime-файлам Samsung (state.json и т.п.).

Единственные импорты модуля: `strategy_api` (контракты Stage A.2.1),
`strategy_state` (StrategyStateManager Stage B.1, валидаторы),
`attribution` (AttributionContext), стандартная библиотека
(enum/math/re/dataclasses/datetime/typing). Координатор выполняет:
проверки контрактов, вызовы переданных ему оценщиков (функции без
сторонних эффектов в рамках контракта), объединение результатов и
запись сводки решения в состояние пары через АТОМАРНЫЙ API

(ключ `last_exit_evaluation`), а не исполнение: ордеров не существует
на этом слое.

## 5. Доказательство №4 — поведение координатора не доходит до исполнения

Каждый возможный исход `ExitDecisionCoordinator.evaluate_and_record`
завершается типизированным отчётом:

| Исход | Что происходит | Исполнение? |
|---|---|---|
| PROTECTIVE_EXIT / STRATEGIC_EXIT | отчёт + запись решения в состояние (контрактное поле) | НЕТ |
| NO_EXIT | отчёт + запись решения в состояние | НЕТ |
| INCOMPLETE_* (цена/ошибка слоя) | отчёт, состояние не тронуто | НЕТ |

Ни один путь не создаёт ордер, не вызывает брокера, не меняет
исполнение. Это подтверждено тестами §6.12/§6.13 (нет фиктивного
исполнения; состояние сохраняется при неудачной оценке).
