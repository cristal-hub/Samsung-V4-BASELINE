## 2. Замечание аудита Stage 2.3 (коррекция №2 ТЗ) — что было неверно

**Утверждение ред. 2.3 (Blueprint §7.4):** «фактическое входное
смещение уже внутри `|exec_price - sl|` (двойной учёт входного
проскальзывания запрещён)» — использовалось как обоснование того, что
член `SLIPPAGE_PERCENT` не добавляется в OPEN ESTIMATED RISK.

**Почему это неверно (аудит; подтверждено фактическим кодом):** SL
рассчитывается ОТ фактической цены исполнения: `sl = exec_price -
exec_price * max(STOP_LOSS_PERCENT, MIN_STOP_LOSS_PERCENT)`
(main.py:4072 → risk_manager.py:238, 246 — FACT). При таком способе
расстояние `|exec_price - sl| = exec_price * max(...)` характеризует
риск ДВИЖЕНИЯ от фактической цены входа до стопа и НЕ является
величиной отклонения цены исполнения от цены принятия решения
(`entry_slippage`). Количественно: в `|exec_price - sl|` от входного
проскальзывания попадает только доля, пропорциональная стоп-проценту
(`slippage * max(...)`), остальная часть проскальзывания в расстоянии
НЕ содержится (пример: decision=100, exec=101, стоп 3% →
`|exec - sl| = 3.03` при плановых 3.00 — внутри расстояния только 0.03
из проскальзывания 1.00).

**Что сохраняется, что исправлено:**

- СОХРАНЕНО: состав трёх моделей (до входа / после входа / после выхода)
  и структура формул ред. 2.3 — сама по себе формула OPEN ESTIMATED RISK
  `|exec - sl| + комиссии + резерв` ЭКОНОМИЧЕСКИ КОРРЕКТНА как прогноз
  убытка при исполнении стопа, потому что измеряется ОТ фактической цены
  входа;
- ИСПРАВЛЕНО ОБОСНОВАНИЕ: входное проскальзывание НЕ добавляется в OPEN
  ESTIMATED RISK не потому, что оно «уже внутри расстояния» (это неверно
  количественно), а потому, что прогноз убытка при исполнении стопа
  определяется ОТ фактической цены входа; входное проскальзывание —
  САМОСТОЯТЕЛЬНАЯ величина сравнения «исполнение vs решение», которая:
  (а) публикуется отдельным полем, (б) частично проявляется в расстоянии
  через масштабирование стоп-процента, (в) НЕ является дополнительным
  денежным членом сценария «исполнение по стопу» (добавление её в сумму
  — двойной учёт: убыток при продаже по стопу складывается из цен входа
  и выхода, а не из цен входа, выхода и «ещё раз входа»);
- ИСПРАВЛЕНА БАЗА ОЦЕНОЧНОЙ КОМИССИИ ВЫХОДА в OPEN ESTIMATED RISK:
  ред. 2.3 использовала `exec_price * COMMISSION_PER_SIDE`; ред. 2.3.1 —
  `sl_price * COMMISSION_PER_SIDE`: сценарий, риск которого оценивается —
  «исполнение по зарегистрированному стопу», значит и комиссия выхода
  должна считаться от цены этого сценария (зарегистрированного
  sl_price). База exec_price завышала оценку (для BUY exec_price > sl_price);
- ВВЕДЕНО ЯВНОЕ ПОЛЕ фактической цены исполнения выхода (ред. 2.3.1 —
  `stop_exec_price`; РЕД. 2.3.2 — переименовано в `exit_exec_price`,
  поскольку величина едина для ВСЕХ типов выхода, а не только стоповых:
  КОРРЕКЦИЯ №3) и `stop_execution_slippage` (насколько исполнение стопа
  хуже стоп-цены; ред. 2.3.2 — формула max(0, sl_price - exit_exec_price),
  применимость — ТОЛЬКО стоповые инциденты) — фактическое проскальзывание
  выхода существует ТОЛЬКО после исполнения и публикуется в REALIZED-модели.

## 3. Пять ценовых величин (§4.2 ТЗ; унифицировано ред. 2.3.2 — КОРРЕКЦИЯ №3)

Термин ред. 2.3.1 `stop_exec_price` ВЫВЕДЕН ИЗ УПОТРЕБЛЕНИЯ: он
использовался как УНИВЕРСАЛЬНАЯ фактическая цена закрытия, что
некорректно для выходов, не связанных со стопом (TP/BE/TRAIL/
стратегических). ЕДИНАЯ величина фактической цены исполнения выхода для
ВСЕХ типов выхода — `exit_exec_price`.

Замечание о существующем поле кода (FACT): `pos.execution_price`
используется кодом ДВУЗНАЧНО — при регистрации хранит цену входа
(main.py:4102), при закрытии учёта — цену выхода (main.py:2462
`exit_price = float(pos.execution_price)`, запись из avg_exec_price
cursor'а). Контракт разделяет эти фазы явными именами `exec_price`
(вход) и `exit_exec_price` (выход); переименование ПОЛЯ кода НЕ
проектируется (NO PYTHON CODE CHANGES) — публикуемые имена журнала/CSV
согласуются с ними (Blueprint §7.4). Термин `stop_exec_price` ред.
2.3.1 в публикуемых полях НЕ используется.

**Входное проскальзывание (определение, §4.2 ТЗ; НЕ изменено ред.
2.3.2):**

```
entry_slippage = exec_price - decision_price        # ценовые единицы на акцию
```

- Для LONG положительное значение = НЕБЛАГОПРИЯТНОЕ смещение (купили
  дороже решения). Движок long-only (F-02); для гипотетического SHORT
  знак инвертируется — правило зафиксировано в контракте заранее.
- Нормализация: величина в ЦЕНОВЫХ ЕДИНИЦАХ на ОДНУ акцию (шт.);
  денежные суммы — умножением на количество акций (шт.), итого рубли.
- Прецедент в существующем коде (FACT): CSV-учёт закрытия уже считает
  `entry_slippage = (entry_price - price_before_order) * shares` и
  `exit_slippage = (close_price_before_order - exit_price) * shares`
  (main.py:2464-2466) — ДЕНЕЖНЫЕ (на позицию) величины, где
  `price_before_order` — снимок цены перед заявкой. Контракт вводит
  ПЕР-ШАРНЫЕ поля с явными именами `decision_price`/`exec_price`/
  `exit_exec_price`; семантика знаков согласована с существующим
  CSV-учётом (положительное = неблагоприятное для LONG на обеих
  сторонах). СУЩЕСТВУЮЩЕЕ денежное CSV-поле `exit_slippage`
  (main.py:2466) сохраняет имя и единицы (руб. на позицию); пер-шарная
  величина контракта именуется `exit_slippage_ps` — конфликт имён
  исключён явным суффиксом.

**Выходные проскальзывания (две РАЗНЫЕ величины — не смешивать;
определения ред. 2.3.2 — КОРРЕКЦИЯ №3):**

```
exit_slippage_ps          = close_price_before_order - exit_exec_price
                          # общее проскальзывание выхода; ЛЮБОЙ тип выхода
                          # (SL/TP/BE/TRAIL/стратегический/аварийный);
                          # после выхода; LONG: >0 — неблагоприятное (продали
                          # дешевле цены на момент перед заявкой)

stop_execution_slippage_ps = max(0, sl_price - exit_exec_price)
                          # ТОЛЬКО для стоповых инцидентов (см. правило
                          # применимости ниже); дополнительное НЕБЛАГОПРИЯТНОЕ
                          # отклонение фактической цены исполнения стопового
                          # выхода от цены стопа; НЕОТРИЦАТЕЛЬНО по построению

stop_price_deviation_ps   = sl_price - exit_exec_price
                          # ЗНАКОВОЕ (сырое) отклонение исполнения от стопа
                          # для стоповых инцидентов: >0 — хуже стопа, <0 —
                          # лучше стопа; публикуется для наблюдаемости и
                          # разложения (см. ниже)
```

**Правило применимости `stop_execution_slippage_ps` (ред. 2.3.2):**
поле рассчитывается ТОЛЬКО для стоповых инцидентов — инцидентов,
триггером которых является защитное срабатывание Stop Loss
(FSM STOP_DETECTED, close_reason=SL), включая их эскалационные ноги
(рыночная/лимитная заявка того же инцидента). Для остальных типов
выхода — TP, BE, TRAIL, стратегический выход, а также не-стоповых
инцидентов (EXIT_DECIDED) — поле имеет значение **NOT_APPLICABLE**, а
НЕ искусственно рассчитанное значение (§5.2 ТЗ Stage 2.3.2). Основание:
для этих выходов цена стопа НЕ применима как точка сравнения (TP
сравнивается с tp_price; BE/TRAIL закрываются политикой; стратегический
выход — решением стратегии), и «проскальзывание стопа» для них не имеет
экономического смысла. `exit_slippage_ps` при этом публикуется для ВСЕХ
типов выхода.

- Знаки и единицы (явно, §5.1 ТЗ Stage 2.3.2): обе величины — ценовые
  единицы на ОДНУ акцию; для LONG положительное `exit_slippage_ps` =
  неблагоприятное (продали дешевле `close_price_before_order`);
  положительное `stop_execution_slippage_ps` = исполнение СТОПОВОГО
  выхода хуже зарегистрированного стопа. Для гипотетического SHORT знак
  инвертируется (зафиксировано заранее; движок long-only — F-02).
- `stop_execution_slippage_ps = max(0, ...)`: исполнение ЛУЧШЕ стопа
  (favorable fill) даёт 0 в этом поле, а НЕ отрицательное значение —
  величина определяется как «дополнительное неблагоприятное отклонение».
  Знаковый факт «лучше/хуже стопа» публикуется `stop_price_deviation_ps`
  (может быть отрицательным). Оба поля публикуются; подмена одного
  другим запрещена.
- Разложение (для стоповых инцидентов; через ЗНАКОВОЕ отклонение):
  `stop_price_deviation_ps = breach_depth_at_trigger + exit_slippage_ps`,
  где `breach_depth_at_trigger = sl_price - close_price_before_order`
  (цена детекции `<= sl_price` по семантике check_all — execution.py:1007,
  поэтому breach_depth_at_trigger >= 0), а `exit_slippage_ps` —
  проскальзывание закрывающей заявки относительно цены перед отправкой.
  Для `stop_execution_slippage_ps` (обрезанного) разложение точно ТОЛЬКО
  при `stop_price_deviation_ps >= 0`; при благоприятном исполнении
  (значение 0) фактическая компенсация видна через знаковые члены.
- Связь с существующим учётом (FACT): денежный аналог
  `exit_slippage_ps` — существующее CSV-поле `exit_slippage =
  (close_price_before_order - exit_price) * shares` (main.py:2466);
  денежный аналог `stop_price_deviation_ps` в коде НЕ существует
  (PROPOSAL). Двойной учёт исключён правилом DC-7 (§6).
- Переименования ред. 2.3.2 (КОРРЕКЦИЯ №3): термин ред. 2.3.1
  `exit_order_slippage` (= close_price_before_order - stop_exec_price)
  ЗАМЕНЁН `exit_slippage_ps` (= close_price_before_order -
  exit_exec_price) — та же экономическая величина (проскальзывание
  закрывающей заявки относительно цены перед отправкой), но определена
  для ВСЕХ типов выхода и от единой цены исполнения. Старый термин в
  публикуемых полях не используется.

**Обработка неизвестных значений:** величина, которой ещё не существует
(exec/exit_exec до исполнения), НЕ подменяется нулём, ценой решения
(decision_price / exit_decision_price), ценой заявки и не «оценивается
молча»: поле отсутствует в журнале до появления факта; использование
оценки вместо факта разрешено ТОЛЬКО в явно помеченных членах моделей
(§5) с источником «model» (прецедент: commission_source main.py:2484-2489).
NaN/±Inf трактуются как отсутствующее значение (прецедент
execution.py:1271-1288), в журнал не попадают. Правила частичных
исполнений и неизвестных цен выхода — §5.5 (прецедент В3:

| C2 | Фактическое расстояние exec_price → зарегистрированный sl_price | цена/акцию | при регистрации | `exec_price - sl_price` (LONG; = \|exec - sl\|) | PROPOSAL-поле (факты-источники есть) |
| C3 | Входное проскальзывание относительно decision_price | цена/акцию | при регистрации | `exec_price - decision_price` | PROPOSAL-поле; денежный прецедент main.py:2464 |
| C4 | Комиссия входа | руб./акцию | после входа (факт) / до входа (план) | факт: `pos.entry_actual_commission` / shares (main.py:4105; execution.py:1271-1288; 0.0 — достоверный факт); план: `decision_price * COMMISSION_PER_SIDE` | FACT-механика / PROPOSAL-поля |
| C5 | Оценочная комиссия выхода | руб./акцию | до фактического выхода | сценарная база: OPEN — `sl_price * COMMISSION_PER_SIDE` (ред. 2.3.1); ESTIMATED — `(decision_price - planned_stop_dist) * COMMISSION_PER_SIDE` | PROPOSAL (база изменена относительно ред. 2.3 — §2) |
| C6 | Резерв на неблагоприятное исполнение стопа (`STOP_SLIPPAGE_RESERVE`) | цена/акцию | конфигурация | ТОЛЬКО решение владельца D-16; до решения член = 0 с пометкой `slippage_reserve_source="unconfigured"` | PROPOSAL (D-16) |
| C7 | Фактическое проскальзывание выхода после исполнения | цена/акцию | после выхода | `exit_slippage_ps = close_price_before_order - exit_exec_price` (общее — для ВСЕХ типов выхода) и, для стоповых инцидентов, `stop_price_deviation_ps = sl_price - exit_exec_price` (знаковое) / `stop_execution_slippage_ps = max(0, sl_price - exit_exec_price)` (неблагоприятное; для не-стоповых — NOT_APPLICABLE) — ред. 2.3.2, КОРРЕКЦИЯ №3; денежный прецедент main.py:2465-2466 | PROPOSAL-поля / FACT-прецедент |

Плановый friction sizing (risk_manager.py:125 —
`last_price * (COMMISSION_PER_SIDE*2 + SLIPPAGE_PERCENT)`) НЕ является
составляющей моделей риска: это ЧЛЕН ЗНАМЕНАТЕЛЯ SIZING, в котором
`SLIPPAGE_PERCENT` — плановое ожидание входного проскальзывания (C3 до
факта) и плановые комиссии. В модели риска он не используется
напрямую — согласование sizing ↔ риск-модель описано в §8.

## 5. Три модели риска — три момента времени (§4.4 ТЗ)

### 5.1. ESTIMATED RISK — ДО ВХОДА

Прогнозируемый убыток на основании данных, доступных до исполнения:
плановая цена входа, плановый стоп, плановое количество, комиссии,
отдельно заданный резерв неблагоприятного исполнения стопа.

```
# Момент: до отправки входной заявки. База: decision_price (= last_price).
planned_stop_dist_ps     = planned_stop_distance                    # цена/акцию — стратегия (§7.2 blueprint)
planned_entry_comm_ps    = decision_price * COMMISSION_PER_SIDE    # руб./акцию
planned_exit_comm_ps     = (decision_price - planned_stop_dist_ps)
                           * COMMISSION_PER_SIDE                   # руб./акцию — база: плановая цена выхода у стопа
stop_slippage_reserve_ps = STOP_SLIPPAGE_RESERVE                   # цена/акцию — D-16; до решения = 0
                                                                   # с slippage_reserve_source="unconfigured"
estimated_per_share_risk = planned_stop_dist_ps
                         + planned_entry_comm_ps
                         + planned_exit_comm_ps
                         + stop_slippage_reserve_ps                # руб./акцию
estimated_risk_total     = estimated_per_share_risk * planned_shares   # руб.
```

- Единицы: пер-шарные члены — руб./акцию; total — рубли.
- Входные параметры: planned_stop_distance (стратегия, §4.1 blueprint),
  decision_price (main.py:5278), COMMISSION_PER_SIDE (config),
  STOP_SLIPPAGE_RESERVE (config, D-16), planned_shares (результат
  sizing, risk_manager.py:137 * lot_size).
- SLIPPAGE_PERCENT в estimated_risk НЕ входит: член входного
  проскальзывания учтён В SIZING-ЗНАМЕНАТЕЛЕ (risk_manager.py:125 —
  уменьшает размер позиции), повторное добавление в прогноз убытка —
  двойной учёт без математического обоснования (матрица §6, правило
  DC-1; согласование — §8).

### 5.2. OPEN ESTIMATED RISK — ПОСЛЕ ВХОДА (до выхода)

Прогнозируемый убыток ОТКРЫТОЙ позиции при исполнении её
зарегистрированного стопа. Точка расчёта: регистрация подтверждённого
исполнения (main.py:4091-4105; гейт `exec_price is not None and
exec_price > 0` — main.py:4066).

```
# Момент: после подтверждения исполнения входа; пересчёт — при каждом
# изменении подтверждённых фактов (частичное исполнение входа, приход
# фактической комиссии).
shares                = executed_lots * lot_size                # шт. (FACT: main.py:4103; lot_size — risk_manager.py:114-117)
actual_stop_dist_ps   = exec_price - sl_price                   # цена/акцию — ЗАРЕГИСТРИРОВАННЫЙ sl (тот, с которым
                                                                # сверяет check_all, execution.py:1007); LONG: exec > sl
entry_commission_ps   = entry_actual_commission / shares        # руб./акцию — ЕСЛИ факт получен (main.py:4105;
                                                                # execution.py:1271-1288; 0.0 — достоверный факт)
                      | exec_price * COMMISSION_PER_SIDE        # руб./акцию — ИНАЧЕ модельная оценка (НЕ ноль),
                                                                # risk_commission_source="model"
exit_commission_est_ps = sl_price * COMMISSION_PER_SIDE         # руб./акцию — ОЦЕНКА выходной стороны от
                                                                # СЦЕНАРНОЙ цены выхода (ред. 2.3.1; §2)
stop_slippage_reserve_ps = STOP_SLIPPAGE_RESERVE               # ТОТ ЖЕ резерв D-16, цена/акцию
open_per_share_risk   = actual_stop_dist_ps
                      + entry_commission_ps
                      + exit_commission_est_ps
                      + stop_slippage_reserve_ps                # руб./акцию
risk_budget           = balance * RISK_PER_TRADE                # руб. (FACT: risk_manager.py:104)
open_risk_total       = open_per_share_risk * shares            # руб.
```

- `entry_slippage = exec_price - decision_price` публикуется ОТОБЩЕСТВЕННО
  (поле `entry_slippage_ps`) и НЕ входит в сумму `open_per_share_risk`
  (матрица §6, правило DC-2). Математическая согласованность с
  фактическим расчётом SL: расстояние считается от ТОГО ЖЕ
  зарегистрированного sl_price (включая любое целевое округление до
  тика), которое использует защита — прогноз соответствует тому, что
  движок сам считал бы срабатыванием и сценарием исполнения.
- Если фактическая комиссия входа неизвестна — ЯВНО обозначенная
  модельная оценка (risk_commission_source="model"), НЕ ноль без
  объяснения (§4.4 ТЗ; прецедент классификации — main.py:2484-2489).
- При частичном исполнении входа расчёт — по подтверждённым лотам;
  приход новых частей пересчитывает модель (per-share величины — от
  средневзвешенной exec_price, total — от накопленных shares).

### 5.3. REALIZED LOSS — ПОСЛЕ ВЫХОДА

Основывается на реальных ценах исполнения ВСЕХ частей заявок и
фактических комиссиях. Не подменять фактический результат расчётным.

```
# Момент: после фактического (полного) закрытия; расчёт ведёт СУЩЕСТВУЮЩИЙ учёт.
gross_pnl_ps   = exit_exec_price - exec_price                     # цена/акцию (отрицательное = убыток LONG)
realized_loss_per_share = (exec_price - exit_exec_price)
                         + entry_commission_ps_actual
                         + exit_commission_ps_actual              # руб./акцию, >= 0 для убыточной сделки
realized_loss_total     = realized_loss_per_share * shares        # руб.
```

- Источники (FACT): `avg_exec_price` cursor'а закрывающей заявки —
  execution.py:788, 830 (несколько частей — накопительный cursor);
  фактические комиссии обеих сторон и классификация
  commission_source (actual/mixed/model) — main.py:2464-2489;
  существующие денежные поля slippage — main.py:2464-2466.
- Открытый расчётный риск заменяется фактическим результатом ровно на
  границе фактического закрытия; частичное исполнение выхода НЕ является
  закрытием — учёт продолжается для остатка (механики
  main.py:5369-5471 сохранены; инцидент — STAGE2_EMERGENCY_EXIT_ARCHITECTURE.md §7 этап E).
- Публикуемые факты выхода: `exit_exec_price` (avg по частям — ЕДИНАЯ цена для всех типов выхода; ред. 2.3.2),
  `exit_slippage_ps` (для всех типов выхода),
  `stop_price_deviation_ps` и `stop_execution_slippage_ps = max(0, sl_price - exit_exec_price)` — ТОЛЬКО для стоповых инцидентов; для TP/BE/TRAIL/стратегических — NOT_APPLICABLE (§3).

### 5.4. Терминологические запреты (сохранены из ред. 2.3)

- Прогнозы (до входа / после входа) НЕ называются «actual risk» —
  «actual» резервируется за фактически исполненными величинами;
  термин `actual_per_share_risk` выведен из употребления.
- Расчётный риск с резервом — ПРОГНОЗ для наблюдаемости, НЕ гарантированный
  предел убытка (гэп/остановка/отказ брокера могут дать убыток сверх
  любой оценки — STAGE2_EMERGENCY_EXIT_ARCHITECTURE.md §11).
- До решения D-16 резерв НЕ сконфигурирован: расчётный риск НЕ является
  полным прогнозом гэп-риска — это ограничение публикуется рядом с каждой
  оценкой (§4.7 ТЗ).

### 5.5. Частичные исполнения выхода и неизвестные цены (НОВОЕ ред. 2.3.2 — КОРРЕКЦИЯ №3; §5.3 ТЗ Stage 2.3.2)

Если позиция закрывается НЕСКОЛЬКИМИ исполнениями (частичные исполнения
одной заявки; несколько заявок инцидента — лимитная частями + рыночная
эскалация):

1. **Учитывать КАЖДОЕ подтверждённое исполнение**: исполнение считается
   подтверждённым ТОЛЬКО из отчёта брокера (статус FILL/PARTIALLYFILL
   с executed > 0 / avg_exec_price из отчёта исполненного ордера —
   FACT execution.py:788/830, 1248-1263; маркер `exit_price_confirmed`
   — ТЗ-5 v2.3.1-stage1).
2. **Хранить количество и цену КАЖДОГО исполнения** (append-only):
   per-execution запись {order_request_id, incident_id, executed_lots,
   exec_price, время, exchange_order_id}; ранее подтверждённые частичные
   исполнения НЕ теряются и НЕ пересчитываются задним числом (append-only
   реестр + cursor-механика FACT main.py:128-290, execution.py:656-861).
3. **Итоговая цена — СРЕДНЕВЗВЕШЕННАЯ** по всем подтверждённым частям:
   `exit_exec_price = Σ(price_i × qty_i) / Σ(qty_i)` (существующая
   механика avg_exec_price cursor'а — execution.py:788, 830).
4. **Цена отправленной заявки НЕ считается ценой исполнения**: лимитная
   цена (limit_price) — параметр заявки, НЕ факт заполнения; в
   exit_exec_price попадает ТОЛЬКО исполненная цена из отчёта брокера.
5. **Цена отменённой заявки НЕ считается исполнением**: заявка,
   отменённая с executed == 0, не вносит ни количества, ни цены; заявка,
   исполненная частично до отмены, вносит только подтверждённые лоты
   (T-13 механика cancel с фиксацией executed_so_far).
6. **Не терять ранее подтверждённые частичные исполнения**: при
   перезапуске и после reconciliation накопленные исполнения
   восстанавливаются из реестра/состояния инцидента (I-7, EE-16);
   пересчёт сумм — только ДОБАВЛЕНИЕМ новых подтверждённых частей.
7. **Неизвестные цены исполнения НЕ заменяются** ценой решения
   (decision_price / exit_decision_price), ценой заявки (limit_price),
   ценой перед заявкой (close_price_before_order) или любой «удобной»
   величиной. ПРЕЦЕДЕНТ (FACT, commit 884cefd): В3-закрытие при
   неизвестной цене исполнения ручной продажи пишет CSV-строку с
   `price_confirmed=False` и БЕЗ P&L — запрет фиктивного P&L
   (main.py:1975-2011, `_finalize_position_closed` main.py:1477-1492);
   приблизительная цена сохраняется только в error_note/событии и
   ИСПОЛНЕНИЕМ НЕ считается. Для инцидента: если цена части неизвестна
   (не подтверждена отчётом брокера) — part не включается в
   средневзвешенную до подтверждения; инцидент остаётся активным
   (UNCERTAIN при недостоверности — FSM T-21).

Следствие для отчётности: realized_loss рассчитывается ТОЛЬКО после
полного подтверждённого закрытия и ТОЛЬКО из подтверждённых цен; при
неполных данных — учёт продолжается для остатка (позиция не объявляется
закрытой — FSM T-11/T-19 требуют суммы исполнений == подтверждённый
остаток И get_positions ноль).

## 6. Матрица недопущения двойного учёта (§4.5–§4.6 ТЗ)

Каждая составляющая входит в каждую модель НЕ БОЛЕЕ ОДНОГО РАЗА и
только в той модели, где она имеет экономический смысл. «—» = член
запрещён в этой модели.

| Составляющая | ESTIMATED (до входа) | OPEN ESTIMATED (после входа) | REALIZED (после выхода) | Sizing-знаменатель (legacy) | Правило |
|---|---|---|---|---|---|
| C1 плановое расстояние | ЕСТЬ (член) | — (заменена фактической C2) | — | ЕСТЬ (base_risk — risk_manager.py:124) | DC-0 |
| C2 фактическое расстояние | — | ЕСТЬ (член) | ЕСТЬ (как `exec - exit_exec` в факте; C2+C7-компонент) | — | DC-0 |
| C3 входное проскальзывание | — (ожидание — В SIZING через SLIPPAGE_PERCENT) | ЗАПРЕЩЕНО как член (публикуется отдельным полем) | НЕ добавлять отдельно (уже внутри `exec - exit_exec`) | ЕСТЬ (SLIPPAGE_PERCENT — risk_manager.py:125) | DC-1, DC-2 |
| C4 комиссия входа | ЕСТЬ (план) | ЕСТЬ (факт/оценка с source) | ЕСТЬ (факт) | ЕСТЬ (план, 1 сторона) | DC-3 |
| C5 комиссия выхода (оценка) | ЕСТЬ (план, база плановый стоп) | ЕСТЬ (оценка, база sl_price — ред. 2.3.1) | — (заменена фактом) | ЕСТЬ (план, 1 сторона) | DC-3 |
| C6 резерв стоп-исполнения | ЕСТЬ (D-16) | ЕСТЬ (D-16) | — (после выхода есть ФАКТ C7 — резерв не добавляется к факту) | НЕТ (вопрос D-28) | DC-4, DC-5 |
| C7 фактическое проскальзывание выхода | — (не существует) | — (не существует до факта) | ЕСТЬ (публикуется; в realized_loss входит через `exec - exit_exec`) | — | DC-6, DC-7 |
| SLIPPAGE_PERCENT | — (НЕ добавлять повторно к оценке убытка) | — (ЗАПРЕЩЕНО вторым членом) | — | ЕСТЬ | DC-1 |

Правила:

- **DC-1 (SLIPPAGE_PERCENT):** используется ОДИН раз — в
  sizing-знаменателе (risk_manager.py:125). Не добавляется повторно ни
  в estimated_per_share_risk, ни в open_per_share_risk без нового
  математического обоснования владельца (§4.5 ТЗ: «Если SLIPPAGE_PERCENT
  уже используется для sizing, не добавлять его повторно в Estimated
  Risk без математического обоснования»).
- **DC-2 (входное проскальзывание в OPEN):** член
  `entry_slippage` НЕ добавляется к `open_per_share_risk`: прогноз
  убытка при стопе измеряется ОТ фактической цены входа; добавление
  проскальзывания к сумме, которая уже начинается с exec_price, —
  двойной учёт (демонстрация — §8, шаг 6).
- **DC-3 (комиссии):** по одному разу на каждую сторону; замена плановых
  фактическими — ровно на границах исполнения; классификация
  risk_commission_source (actual/mixed/model) обязательна в каждом
  расчёте.
- **DC-4 (резерв):** STOP_SLIPPAGE_RESERVE — член ТОЛЬКО прогнозных
  моделей; в REALIZED не входит (после выхода есть факт C7); в sizing
  по умолчанию НЕ входит (вопрос D-28).
- **DC-5 (резерв ≠ расстояние):** расстояние до стопа (C1/C2) и резерв
  (C6) — РАЗНЫЕ члены: расстояние — плановый убыток сценария «исполнение
  по стоп-цене», резерв — ожидание неблагоприятного исполнения хуже
  стоп-цены. Объединение в один член запрещено.
- **DC-6 (факт vs прогноз):** после фактического выхода прогнозные
  члены (C5, C6) НЕ суммируются с фактическими — модель REALIZED
  содержит только факты.
- **DC-7 (НОВОЕ ред. 2.3.2 — поля проскальзывания выхода — НЕ члены
  realized_loss):** `exit_slippage_ps`, `stop_price_deviation_ps`,
  `stop_execution_slippage_ps` — ОБОБЩЕСТВЕННЫЕ (наблюдаемые) величины;
  они НЕ добавляются к realized_loss как дополнительные члены — убыток
  уже содержит их через фактическую цену выхода: для стопового инцидента
  `exec_price - exit_exec_price = (exec_price - sl_price) +
  stop_price_deviation_ps` (фактическая дистанция + знаковое отклонение
  стоп-исполнения). Добавление любого из этих полей вторым членом к
  realized_loss — двойной учёт (демонстрация — §8, шаги 6-8; симметрично
  DC-2 для входной стороны). Двойной учёт проскальзывания в ЛЮБОЙ
  комбинации запрещён (§5.6 ТЗ Stage 2.3.2).

## 7. Согласование sizing и risk reporting (§4.5 ТЗ)

### 7.1. Как работает sizing сегодня (FACT — risk_manager.py:87-137)

```
risk_amount        = balance * RISK_PER_TRADE                                  # 104
base_risk          = last_price * max(STOP_LOSS_PERCENT, MIN_STOP_LOSS_PERCENT)  # 124 — база: decision_price
friction           = last_price * (COMMISSION_PER_SIDE*2 + SLIPPAGE_PERCENT)     # 125 — СЛАГАЕМЫЕ: обе комиссии + входное проскальзывание (ожидание)
per_share_risk     = base_risk + friction                                       # 126
ATR-ветка: atr_risk = min(ATR*ATR_STOP_MULTIPLIER, last_price*MAX_ATR_STOP_PERCENT)  # 128-131
           per_share_risk = max(per_share_risk, atr_risk + friction)             # 132
lots               = int(risk_amount / (per_share_risk * lot_size))             # 137 (округление ВНИЗ — ограничение риска)
```

- Базовый риск считается ОТ `last_price` (decision_price — main.py:5278);
- SLIPPAGE_PERCENT учитывается ТОЛЬКО здесь (grep: единственное
  использование в риск-контуре);
- SL определяется ОТ `exec_price` при регистрации (main.py:4072 →
  risk_manager.py:238/246) — то есть sizing планирует дистанцию от
  decision_price, а защита исполняет стоп, пересчитанный от факта.

### 7.2. Где возникает разница «расчётное количество ↔ фактический риск»

1. **Входное проскальзывание (C3):** exec_price ≠ decision_price →
   фактическая дистанция стопа `exec_price * max(...)` отличается от
   плановой (для LONG при неблагоприятном проскальзывании — больше);
2. **ATR-ветка:** ATR рассчитан на момент решения; SL фиксируется от
   exec_price → соотношение плановой/фактической дистанции меняется;
3. **Комиссии:** фактические (от exec_price) ≠ плановые (от
   decision_price);
4. **Частичное исполнение входа:** executed_lots ≠ requested lots →
   фактическая экспозиция и total-риск отличаются от плановых;
5. **Исполнение стопа (C7):** фактический выход может быть хуже
   sl_price (гэп/ликвидность) — НЕ покрыто никаким членом sizing и
   прогнозов, кроме резерва C6 (D-16).

Все эффекты существуют «молча» в текущем коде; контракт делает их
НАБЛЮДАЕМЫМИ: `stop_sizing_deviation = |C2 - C1| / C1` (переопределено
ред. 2.3.1 — делитель плановая дистанция; нулевой делитель исключён
инвариантом `planned_stop > 0`), поля `entry_slippage_ps`,
`risk_commission_source`, `slippage_reserve_source`, события
`STOP_SIZING_MISMATCH`, `RISK_BUDGET_EXCEEDED` (см. 7.4).

### 7.3. Согласованный контракт sizing ↔ risk reporting

1. Sizing работает от decision_price с плановой дистанцией стратегии
   (§7.2 blueprint) и legacy-членами friction — БЕЗ ИЗМЕНЕНИЙ
   (golden-защита торговой логики);
2. Регистрация: SL/TP от exec_price (семантика кода не меняется) →
   сразу после регистрации публикуются C1, C2, C3, `stop_sizing_deviation`
   и OPEN ESTIMATED RISK (§5.2);
3. Запрещено «подгонять» sizing к факту задним числом (изменять размер
   уже рассчитанной позиции по факту исполнения) — размер фиксируется
   до входа;
4. Если после исполнения фактический риск превышает допустимый бюджет
   (`open_risk_total > risk_budget`) — это ОТДЕЛЬНОЕ СОБЫТИЕ
   `RISK_BUDGET_EXCEEDED` с полями (estimated/open/planned/budget);
   реакция v1 — ЖУРНАЛИРОВАНИЕ (режим наблюдения D-15); усиление
   (предупреждение оператору / запрет новых входов по FIGI /
   сокращение позиции) — ТОЛЬКО решение владельца; автоматическая
   продажа или изменение позиции БЕЗ утверждённого решения НЕ
   проектируется (§4.5 ТЗ);
5. Расхождение плановой и фактической дистанций — событие
   `STOP_SIZING_MISMATCH` (не блокирует регистрацию подтверждённого
   исполнения — Дефект №7 main.py:4068-4084 сохраняется).

### 7.4. Связка знаменателя sizing и модели риска (честность отчётности)

Разница знаменателя sizing и прогноза модели (base-ветка, до резерва):

```
per_share_risk_sizing - estimated_per_share_risk
  = SLIPPAGE_PERCENT * decision_price                    # ожидание входного проскальзывания
  + (плановые комиссии sizing на decision_price
     - плановые комиссии модели с базами вход/плановый стоп)
  - stop_slippage_reserve_ps                             # резерв В sizing НЕ входит
```

Следствие: при положительном резерве прогноз модели МОЖЕТ превысить
sizing-знаменатель — движение намеренно НЕ «чинится» изменением sizing
(изменило бы размеры позиций = торговое поведение; golden-защита).
Вопрос «включать ли STOP_SLIPPAGE_RESERVE в sizing-знаменатель» —
ОТКРЫТОЕ РЕШЕНИЕ D-28 (варианты и последствия — STAGE2_OPEN_DECISIONS.md).
Числовая разница публикуется полем `risk_model_sizing_gap_ps`
для наблюдаемости.

### 7.5. Способ оценки входного проскальзывания (новое решение D-25)

Входное проскальзывание C3 до факта неизвестно. Способ ЕГО ПРОГНОЗА
(для калибровки наблюдаемости, не для изменения sizing) — решение
владельца D-25: (а) статистическое по фактическим журналам
(V-8-данные), (б) фиксированное допущение владельца, (в) не
прогнозировать (только факт). Значения НЕ изобретаются.

## 8. Числовой пример (УСЛОВНЫЕ данные; НЕ рекомендуемые торговые параметры)

**БАННЕР:** все значения ниже выбраны ТОЛЬКО для прозрачной арифметики.
Они не являются параметрами конфигурации, не тестируются как «правильные
значения» и не переносятся в engine.json/params.json.

Условные параметры примера: `STOP_LOSS_PERCENT=3%`,
`COMMISSION_PER_SIDE=0.04%`, `SLIPPAGE_PERCENT=0.10%`,
`RISK_PER_TRADE=1%`, `balance=3180.00`, `lot_size=1`.
Арифметика проверена программой (Decimal, без плавающей погрешности).

**Шаг 1 — решение (до входа).** `decision_price = 100.00`.
Плановая дистанция `C1 = 100.00 * 3% = 3.00`.
Sizing: `risk_amount = 31.80`; `friction = 100 * (0.0008 + 0.0010) = 0.18`;
`per_share_risk = 3.18`; `planned_shares = int(31.80 / 3.18) = 10`.

**Шаг 2 — ESTIMATED RISK (до входа).** `planned_entry_comm = 100 * 0.0004 = 0.04`;
`planned_exit_comm = (100 - 3.00) * 0.0004 = 0.0388`; резерв не
сконфигурирован (D-16 не решён) → член 0 с пометкой unconfigured.
`estimated_per_share_risk = 3.00 + 0.04 + 0.0388 + 0 = 3.0788`;
`estimated_risk_total = 30.788`.

**Шаг 3 — исполнение входа.** `exec_price = 101.00` (неблагоприятное
проскальзывание `C3 = +1.00` — купили на 1.00 дороже решения).
Комиссия входа подтверждена брокером: `101 * 10 * 0.0004 = 0.404` итого
→ `0.0404` руб./акцию (`risk_commission_source="actual"`).

**Шаг 4 — регистрация (SL от exec_price — семантика кода).**
`sl_price = 101.00 - 101.00*3% = 97.97`. Фактическая дистанция
`C2 = 101.00 - 97.97 = 3.03` (плановая была 3.00;
`stop_sizing_deviation = 0.03/3.00 = 1%`). Внутри C2 от проскальзывания
только `1.00 * 3% = 0.03` (доля = стоп-процент) — оставшиеся 0.97 в
расстоянии НЕ содержатся (доказательство ошибки ред. 2.3, §2).
OPEN ESTIMATED RISK: `exit_comm_est = 97.97 * 0.0004 = 0.039188`;
`open_per_share_risk = 3.03 + 0.0404 + 0.039188 + 0 = 3.109588`;
`open_risk_total = 31.09588 <= risk_budget 31.80` (RISK_BUDGET_EXCEEDED
нет). Если бы резерв был сконфигурирован (ГИПОТЕТИЧЕСКОЕ значение
0.10 руб./акцию только для демонстрации члена — НЕ параметр):
`open_per_share_risk = 3.209588`, `open_risk_total = 32.09588 > 31.80`
→ событие `RISK_BUDGET_EXCEEDED` (реакция v1 — журналирование, D-15).

**Шаг 5 — анти-двойной-учёт (DC-2).** Ошибочная сумма
«3.109588 + entry_slippage 1.00 = 4.109588» НЕ имеет экономического
смысла: убыток при продаже по стопу складывается из цен входа (101.00)
и выхода (97.97), а не из цен входа, выхода и «ещё раз входа».
Поля публикуются раздельно: `entry_slippage_ps=1.00`,
`actual_stop_dist_ps=3.03`, `open_per_share_risk=3.109588`.

**Шаг 6 — фактический выход (стоповый инцидент, исполнение хуже
стоп-цены).** Решение закрытия при `close_price_before_order = 97.90`
(цена детекции ниже стопа: `breach_depth_at_trigger = 97.97 - 97.90 =
0.07`; это же значение — `exit_decision_price` для защитного
срабатывания); исполнение `exit_exec_price = 96.80` (одна заявка,
полное исполнение). Тогда:
`stop_price_deviation_ps = 97.97 - 96.80 = 1.17` (знаковое);
`stop_execution_slippage_ps = max(0, 1.17) = 1.17` (неблагоприятное);
`exit_slippage_ps = 97.90 - 96.80 = 1.10`; разложение знакового
отклонения: `1.17 = 0.07 + 1.10` (глубина пробоя + проскальзывание
заявки). Для СРАВНЕНИЯ (КОРРЕКЦИЯ №3): если бы закрытие произошло по
TP/BE/TRAIL или стратегическому выходу с той же ценой исполнения 96.80,
то публикуются только `exit_exec_price = 96.80` и `exit_slippage_ps =
1.10`, а `stop_execution_slippage_ps = NOT_APPLICABLE` (не стоповый
инцидент — цену стопа сравнивать с исполнением НЕ имеет смысла).
Комиссия выхода фактическая: `96.80 * 10 * 0.0004 = 0.3872` итого →
`0.03872` руб./акцию.

**Шаг 7 — REALIZED LOSS.** `realized_loss_per_share =
(101.00 - 96.80) + 0.0404 + 0.03872 = 4.27912`;
`realized_loss_total = 42.7912`.

**Шаг 8 — декомпозиция расхождений (проверка согласованности моделей;
DC-7 — поля проскальзывания НЕ добавляются к realized_loss).
`realized - open = 4.27912 - 3.109588 = 1.169532 = stop_price_deviation_ps
1.17 - дельта баз выходной комиссии (0.039188 - 0.03872 = 0.000468)`.
`realized - estimated = 4.27912 - 3.0788 = 1.20032 = (3.03 - 3.00)
[эффект входного проскальзывания через стоп-процент] + 1.17 [исполнение
хуже стопа] + 0.0004 - 0.00008 [дельты комиссий]`. Каждая разность
объясняется СООТВЕТСТВУЮЩЕЙ составляющей §4 — ни одна не «теряется» и
не учитывается дважды. Контроль DC-7: ошибочная сумма «4.27912 +
stop_execution_slippage_ps 1.17 = 5.44912» НЕ имеет экономического
смысла — отклонение стоп-исполнения уже внутри realized через
exit_exec_price (совпадает с демонстрацией DC-2, шаг 5).

## 9. Краевые случаи (fail-safe; регистрация не блокируется)

| Случай | Поведение |
|---|---|
| sl/tp не рассчитаны (RECOVERY-позиция: main.py:4068-4088) | контроль риска НЕ применяется; событие RISK_CONTROL_NOT_APPLICABLE {cause:"no_sl_tp"}; регистрация НЕ блокируется |

| NaN/±Inf в любом члене | член трактуется как отсутствующий (прецедент execution.py:1276-1285) → модельная оценка; при невозможности расчёта → RISK_CONTROL_NOT_APPLICABLE; NaN в журнал не попадает |
