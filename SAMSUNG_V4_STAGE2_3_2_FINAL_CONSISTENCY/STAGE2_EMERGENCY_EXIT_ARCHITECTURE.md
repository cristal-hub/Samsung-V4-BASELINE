## 1. Цель и границы

**Цель:** ни одна закрывающая заявка позиции не отправляется в обход
единого контролируемого маршрута; любое подтверждённое срабатывание
Stop Loss (и любое другое решение закрытия) обрабатывается ОДНИМ
Exit Incident ОДНИМ контроллером — от обнаружения до брокерского
подтверждения закрытия, с reconciliation перед каждой отправкой,
контролем частичных исполнений и эскалацией к рыночной заявке по
утверждённой политике.

**Границы компонента:**

- `EmergencyExitController` владеет ИСПОЛНЕНИЕМ закрытия УЖЕ ОТКРЫТОЙ
  позиции: получение решения закрытия (защитного или стратегического),
  reconciliation, контролируемая попытка, эскалация, подтверждение;
- он НЕ генерирует торговые сигналы и НЕ меняет стратегию (входы
  запрещены на весь период инцидента);
- он НЕ является трейлинг-логикой и НЕ «улучшает» решения: что закрывать
  (решение) и когда закрывать (защитное обнаружение) — слои стратегии и
  защиты; КАК закрывать (какие заявки, в каком порядке, на какой остаток)
  — контроллер;
- он НЕ отменяет и НЕ ослабляет защитные обнаружения SL/TP: приоритет
  защиты сохраняется; объединение причин — в один инцидент (§9);
- Stage 2.3.1 НЕ реализует компонент: никакой торговой логики, никаких
  заявок, никакой торговли (мандаты в шапке).

## 2. Замечание аудита и фактическая последовательность исходного кода (FACT)

Аудит Stage 2.3 (коррекция №1 ТЗ Stage 2.3.1): «EmergencyExitController
описан как механизм, который запускается после существующего защитного
выхода check_all(). Это архитектурная ошибка». Фактическая
последовательность подтверждена по исходному коду commit `884cefd`:

1. `check_all()` обнаруживает `price <= sl_price` для BUY
   (execution.py:1007); позиция помечается `CLOSING`,
   `close_reason`, `close_price_before_order` (execution.py:1017-1020)
   и попадает в возвращаемый список. `check_all()` НЕ отправляет заявок —
   он ТОЛЬКО обнаруживает и возвращает список (execution.py:986-1022).
2. Торговый цикл получает список: `to_close = await monitor.check_all(...)`
   (main.py:5144).
3. Цикл для каждой позиции сразу вызывает закрытие:
   `await close_position(client, pos, price)` (main.py:5152; при
   невалидной цене — UNCERTAIN без заявки, main.py:5147-5151).
4. `close_position()` отправляет РЫНОЧНУЮ SELL:
   `post_market_order(...)` (main.py:2315), после INTENT-before-send
   (main.py:2254-2280) и защиты от повторной SELL
   (`_sell_block_reason`, main.py:738-767, 2235).

Следствие (аудит): если контроллер включается ПОСЛЕ этого шага (как было
запроектировано в ред. 2.3 — M-7 «после шага защитных выходов»),
первая рыночная заявка УЖЕ отправлена, и гибридная последовательность
«лимитная попытка → рыночная эскалация» для обычного срабатывания стопа
НЕ выполняется никогда. Контроллер ред. 2.3 мог сработать только в зазоре
«частичное исполнение/неизвестный статус уже отправленной SELL» — то есть
механизм не покрывал свой главный сценарий.

Дополнительные подтверждённые факты, существенные для проектирования:

- SL/TP — ПРОГРАММНЫЙ, а не биржевой: никакого стоп-ордера у брокера не
  существует (grep `ORDER_TYPE_LIMIT|post_limit|LIMIT_ORDER|stop_order` по
  main.py, execution.py, risk_manager.py, tinkoff_client.py,
  order_ledger.py — 0 совпадений, F-22); между двумя опросами цена может
  уйти далеко за стоп; исполнение «по цене стопа» НЕ гарантировано;
- рыночная заявка исполняется по НАИЛУЧШЕЙ ДОСТУПНОЙ цене рынка в момент
  исполнения — при гэпе, низкой ликвидности или остановке торгов это может
  быть значительно хуже стопа; заявка может исполниться частично или быть
  отклонена;
- при частичном исполнении защитной SELL или неизвестном её статусе
  существующая защита БЛОКИРУЕТ новую SELL (`_sell_block_reason`,
  main.py:738-767) — правильно с точки зрения дублей, но без контроллера
  остаток позиции оставался без активного завершающего механизма.

## 3. Новое место компонента: единый маршрут выхода (обязательное архитектурное изменение)

**ПРОЕКТ.** Отдельный компонент `EmergencyExitController` (новый модуль
`emergency_exit.py`; FILE_CHANGE_MAP §3.8; roadmap этап H). Контроллер
интегрируется в торговый цикл ДО точки отправки первой закрывающей
заявки и становится ЕДИНСТВЕННЫМ владельцем отправки закрывающих заявок.

**Единый маршрут обработки выхода:**

```
Protective Stop Detection (check_all — ТОЛЬКО обнаружение)
        │
        ▼
Exit Decision (стратегические выходы — ТОЛЬКО обнаружение/решение)
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Exit Router шага 2 цикла: объединение причин (INV-1),        │
│ создание ОДНОГО Exit Incident на позицию, INTENT персистится │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
EmergencyExitController.process_incidents()   ← ЕДИНСТВЕННАЯ точка
  │                                              отправки закрывающих
  ├─ Reconciliation                              заявок
  ├─ Контролируемая лимитная попытка (SL-инцидент)
  ├─ Эскалация к рыночной заявке (по политике)
  └─ Подтверждение закрытия сверкой
        │
        ▼
Exit Execution (заявки инцидента; рыночная нога — через
close_position как ИСПОЛНИТЕЛЬ внутри контроллера)
```

**Новый порядок шагов торгового цикла (ред. 2.3.1; замена §6.2 шага 2г
blueprint):**

```
# 2а. ЗАЩИТНЫЕ обнаружения SL/TP/BE/TRAIL — check_all БЕЗ ИЗМЕНЕНИЙ
#     (контракт execution.py:978-1022 сохранён: обнаружение + маркировка
#     CLOSING, НИКАКИХ заявок).
protective = await monitor.check_all(prices, extremes=..., atrs=...)

# 2б. СТРАТЕГИЧЕСКИЕ решения — для позиций, оставшихся OPEN, после
#     шлюза валидности цены (_valid_price, EP-1..EP-6) — БЕЗ ИЗМЕНЕНИЙ
#     ред. 2.2/2.3; позиция помечается CLOSING + close_reason, заявки НЕТ.
strategic = [...evaluate_exit...]

# 2в. ОБЪЕДИНЕНИЕ — добавлением списков; INV-1 (без дублирования);
#     ВСЕ причины сохраняются: pos.merged_close_reasons =
#     [защитные ...] + [стратегические ...] — защитное событие НЕ теряется.
to_close = protective + [p for p in strategic if p.state == CLOSING]

# 2г. (ЗАМЕНА: прямой close_position УДАЛЁН из цикла) — отправка Intent:
#     для каждой позиции to_close контроллер принимает решение закрытия
#     и создаёт ОДИН Exit Incident:
controller.submit_exit_incident(pos, reasons=pos.merged_close_reasons,
                                prices=prices)
#     Заявок на этом шаге НЕТ — только INTENT-before-send (персистенция).

# 2д. (НОВЫЙ шаг) — продвижение ВСЕХ активных инцидентов:
#     reconciliation → первая попытка (по политике порядка попыток) →
#     контроль исполнения → отмена/переустановка → эскалация →
#     подтверждение. ВСЕ закрывающие заявки отправляются ТОЛЬКО здесь.
controller.process_incidents(prices=prices)

# далее — существующие шаги цикла: process_closing, poll_open_orders,
# promote_recovery_positions, reconcile, входы (порядок сохранён, B-6).
```

Противоречие ред. 2.3.1, устраняемое этим разделом: одновременно
утверждалось «все закрывающие заявки отправляются только через
контроллер» (§3) и «close_position может использоваться для
операторских закрытий вне инцидентов» (§3 п.5 ред. 2.3.1 — см. выше).
Разделение ниже делает маршрут отправки ОДНОЗНАЧНЫМ для каждого
сценария и фиксирует инвариант:

```
ALL_BOT_SELL_SUBMISSIONS ⊆ EmergencyExitController.process_incidents()
```

(множество всех программных отправок SELL ботом — подмножество
отправок, выполненных единственной точкой process_incidents().
Внешние брокерские действия оператора НЕ являются отправками бота.)

**Сценарий A — автоматическое закрытие ботом.** Любая программная
SELL, инициированная движком: Stop Loss; Take Profit; Break Even;
Trailing Stop; стратегический выход; аварийный выход; внутренняя
команда закрытия позиции (включая команду оператора из интерфейса
бота — см. сценарий C) — ОБЯЗАНА создать новый или использовать
существующий Exit Incident. Единственная точка отправки закрывающих
заявок — `process_incidents()`. `close_position()` может оставаться
низкоуровневым исполнителем рыночной ноги ВНУТРИ контроллера, но НЕ
самостоятельным маршрутом отправки. Причина закрытия фиксируется в
атрибутах инцидента (merged_close_reasons), а НЕ выбором маршрута.

**Сценарий B — ручная продажа оператором через брокера.** Оператор
может самостоятельно закрыть позицию через приложение или терминал
брокера. Это ВНЕШНЕЕ действие, а не внутренний маршрут отправки заявки
ботом: в этом сценарии бот НИКАКИХ заявок не отправляет (0 отправок —
подмножество пусто, инвариант выполнен тривиально). Бот ОБЯЗАН
обнаружить результат через reconciliation (существующий механизм В3 —
FACT main.py:1932-2011):

- уменьшение количества позиции (частичная внешняя продажа);
- полное закрытие позиции (позиция отсутствует у брокера);
- наличие внешней заявки, не принадлежащей боту;
- частичное исполнение внешней заявки;
- несоответствие локального и брокерского состояния.

При неизвестном результате — UNCERTAIN и reconciliation (семантика
main.py:5147-5151; fail-closed контракт клиента None=неизвестно).
Двойное подтверждение В3 (два снимка с разносом
RECONCILE_CONFIRM_MIN_AGE_SECONDS) обязательно до закрытия учёта —
ручная продажа НЕ считается подтверждённой до reconciliation (запрет
№10 §3). При активном инциденте конфликт разрешается reconciliation:
подтверждённый нулевой остаток → T-07 EXIT_CONFIRMED без новых заявок
(ручная продажа не дублируется ботом). Бот НЕ должен автоматически
дублировать ручную продажу: никакая ветка не «дозакрывает» внешнее
действие повторной SELL.

**Сценарий C — операторская команда из Telegram или интерфейса самого
бота.** Если оператор инициирует закрытие через интерфейс бота, это
считается ПРОГРАММНЫМ действием бота. Оно ОБЯЗАНО проходить через
Exit Incident и `process_incidents()` (сценарий A): обработчик команды
вызывает `controller.submit_exit_incident(pos, reasons=["OPERATOR_CLOSE"],
prices=...)`; отправку выполняет ТОЛЬКО process_incidents(). Прямой
вызов close_position или post-вызов из обработчика ЗАПРЕЩЕН (запреты
№8-9 §3).

FACT-основание сценария C (commit 884cefd): текущий Telegram-интерфейс
команд закрытия НЕ содержит — только /start /stop /status, управляющие
trading.flag (telegram_bot.py:52-107); команд закрытия позиций в
существующем коде НЕТ (grep — 0 совпадений). Требование сценария C —
ПРОЕКТ для этапа H: ЕСЛИ такой команда будет добавлена, её обработчик
обязан создавать инцидент; прямой маршрут отправки запрещён матрицей
приёмки (тесты EE-21…EE-27, STAGE2_TEST_MATRIX.md §8 ред. 2.3.2).

**Сводная таблица сценариев:**

| Сценарий | Инициатор | Кто отправляет SELL | Что видит учёт | Тесты |
|---|---|---|---|---|
| A — автоматическое закрытие ботом | SL / TP / BE / TRAIL / стратегический выход / аварийный выход / внутренняя команда закрытия | ТОЛЬКО process_incidents() (close_position — исполнитель рыночной ноги внутри) | Exit Incident: INTENT → попытка/попытки → подтверждение сверкой; reason_code причины в CSV | EE-21, EE-22, EE-23, EE-24, EE-27 |

## 4. Единый контракт обработки Stop Loss (§3.3 ТЗ Stage 2.3.1)

Контракт обязателен для ВСЕХ пяти рыночных сценариев. **Не создавать два
независимых контура выхода**: различие сценариев — АТРИБУТЫ инцидента,
а НЕ разные маршруты, заявки или контроллеры.

**Архитектурный принцип:** любое подтверждённое срабатывание Stop Loss
создаёт ОДИН Exit Incident, который обрабатывается единым контроллером.
Гэп является характеристикой рыночного события и влияет на цену и риск
исполнения (атрибуты инцидента + риск-модель), но НЕ создаёт отдельную
конкурирующую заявку.

| # | Сценарий | Обработка (единый маршрут) | Инцидент-атрибуты |
|---|---|---|---|
| 1 | Обычное пересечение стопа: предыдущая валидная цена была выше стопа, текущая валидная цена `<= sl_price` (для BUY; семантика check_all — execution.py:1007) | ОДИН Exit Incident; гибридная последовательность §7 (лимитная попытка → эскалация) | `breach_kind=INTRADAY_CROSS`; `breach_depth = sl_price - price` |
| 2 | Гэп ниже стопа: первая валидная цена после перерыва/отсутствия котировок уже `<= sl_price` | ТОТ ЖЕ маршрут, тот же инцидент | `breach_kind=OPEN_GAP` (критерий: ни одного валидного наблюдения цены на «безопасной» стороне в текущей сессии/после перерыва данных; источник — серия валидных опросов + флаг начала потока цен) |
| 3 | Резкое движение цены через несколько уровней (глубокий пробой за один опрос) | ТОТ ЖЕ маршрут | `breach_depth` фиксируется фактом (без порога); глубина — ТОЛЬКО атрибут для наблюдаемости и для опционального условия эскалации D-20 «по глубине пробоя», если владелец её выберет (число устанавливает ВЛАДЕЛЕЦ — не изобретается) |
| 4 | Повторное получение цены ниже стопа при активном инциденте | ИДЕМПОТЕНТНОСТЬ: НЕ создаёт второй инцидент и вторую заявку; событие `STOP_BREACH_REPEATED` пишется в СУЩЕСТВУЮЩИЙ инцидент (§8, EE-15) | обновляется `breach_depth_max` |
| 5 | Восстановление цены выше стопа после первоначального пробоя | Инцидент ПРОДОЛЖАЕТСЯ (защитное обнаружение не отменяется задним числом — отмена triggered-стопа по восстановлению цены была бы НОВЫМ торговым решением, не утверждённым владельцем); событие `STOP_BREACH_PRICE_RECOVERED` пишется; лимитная попытка следует цене по политике D-18; автоматической отмены инцидента НЕТ. Поведение «отменить попытку до эскалации и вернуть позицию в OPEN» — НЕ проектируется без решения владельца (D-27) | `price_recovered=true`, макс. наблюдаемая цена после пробоя |

**Различение «обычное срабатывание vs гэп» — критерии и источник данных
(обязательство §3.3 ТЗ):** различие определяется ТОЛЬКО из наблюдаемых
данных движка — серии валидных опросов цен (шлюз `_valid_price`) и
флагов возобновления потока котировок: `OPEN_GAP` — валидная цена при
возобновлении потока/первом валидном опросе позиции уже за стопом;
`INTRADAY_CROSS` — между двумя последовательными валидными опросами
(предыдущая — за стопом на безопасной стороне). ЧИСЛОВОЙ ПОРОГ ГЭПА НЕ
ИЗОБРЕТАЕТСЯ: глубина пробоя фиксируется фактом (`breach_depth`), порог
глубины — только опциональная конфигурация владельца (D-20). Движок НЕ
может отличить «быстрое движение между опросами» от «гэпа между
опросами» по своим данным — и НЕ ДОЛЖЕН: оба сценария идут одним
маршрутом, различие — атрибут журнала.

**Несколько причин закрытия одновременно:** защитные SL/TP и
стратегические выходы НЕ конкурируют за одну позицию. Если в одном цикле
возникли несколько причин закрытия, они объединяются в ОДИН контролируемый
Exit Incident со сохранением ВСЕХ причин в журнале
(`merged_close_reasons` — защитные причины сохраняются ПЕРВЫМИ,
priority защитного слоя; инвариант INV-1 исключает дублирование позиции).
Не допускать потери защитного события при объединении списков выхода —
тест EE-05.

## 6. Конечный автомат Exit Incident (§3.5 ТЗ)

Каждый инцидент — экземпляр конечного автомата. Состояния инцидента
персистятся ДО каждого действия (атомарная запись state.json —
main.py:1165-1167 паттерн). Список состояний — минимум из ТЗ
(STOP_DETECTED … UNCERTAIN) + одно дополнительное состояние
`EXIT_DECIDED` для не-стоповых причин закрытия (TP/BE/TRAIL/
стратегические), чтобы один FSM обслуживал ВСЕ инциденты без второго
контура.

### 6.1. Состояния

| Состояние | Смысл | Позиция (монитор) |
|---|---|---|
| `STOP_DETECTED` | защитное срабатывание SL подтверждено валидной ценой; инцидент создан | CLOSING |
| `EXIT_DECIDED` | не-стоповое решение закрытия (TP/BE/TRAIL/стратегическое) принято и объединено в инцидент | CLOSING |
| `EXIT_INTENT_PERSISTED` | намерение закрытия (инцидент: причины, остаток, политика) записано в персистентное хранилище ДО любого действия | CLOSING |
| `RECONCILING` | идёт сверка: брокерская позиция, активные заявки, подтверждённые исполнения, подтверждённый остаток | CLOSING |
| `LIMIT_EXIT_PENDING` | лимитная заявка отправлена (INTENT записан ДО отправки); ОЖИДАНИЕ СТАТУСА — НЕ подтверждение исполнения | CLOSING |
| `LIMIT_EXIT_PARTIAL` | лимитная заявка исполнена частично; проданная часть зафиксирована; остаток продолжается | CLOSING |
| `LIMIT_EXIT_CANCEL_PENDING` | запрошена контролируемая отмена лимитной заявки; исход НЕ подтверждён | CLOSING |
| `ESCALATION_READY` | лимитный путь исчерпан по политике; reconciliation выполнен; подтверждённый остаток известен; активных заявок, способных исполниться, НЕТ; эскалация разрешена политикой (D-20) | CLOSING |
| `MARKET_EXIT_PENDING` | рыночная заявка отправлена (INTENT записан ДО отправки); ОЖИДАНИЕ СТАТУСА — НЕ подтверждение исполнения | CLOSING |
| `MARKET_EXIT_PARTIAL` | рыночная заявка исполнена частично; продолжается контроль | CLOSING |
| `EXIT_CONFIRMED` | полное закрытие подтверждено БРОКЕРОМ (сумма исполнений == подтверждённый остаток И get_positions: ноль по FIGI) | CLOSED |
| `EXIT_FAILED` | автоматическое завершение инцидента отказом (политика исчерпана — напр., D-21); позиция НЕ объявлена закрытой; требуется оператор/политика | CLOSING (без автозаявки) |
| `UNCERTAIN` | состояние недостоверно (брокер недоступен / неизвестный статус / неизвестный результат отправки / positions=None); восстановление и сверка продолжаются; НОВЫЕ ЗАЯВКИ ЗАПРЕЩЕНЫ до разрешения | UNCERTAIN |

### 6.3. Запрещённые переходы

1. `STOP_DETECTED`/`EXIT_DECIDED` → `LIMIT_EXIT_PENDING`/`MARKET_EXIT_PENDING` напрямую (БЕЗ `EXIT_INTENT_PERSISTED` и `RECONCILING`) — ЗАПРЕЩЕНО.
2. `EXIT_INTENT_PERSISTED` → любое состояние отправки без `RECONCILING` — ЗАПРЕЩЕНО.
3. `LIMIT_EXIT_*` → `MARKET_EXIT_PENDING` напрямую (эскалация без отмены/разрешения судьбы лимитной заявки, reconciliation и `ESCALATION_READY`) — ЗАПРЕЩЕНО.
4. Любое состояние → `EXIT_CONFIRMED` без брокерского доказательства (сумма исполнений == остаток И позиции-сверка ноль) — ЗАПРЕЩЕНО. Отправка заявки — НЕ подтверждение.
5. `UNCERTAIN` → любое состояние отправки напрямую (только через `RECONCILING`) — ЗАПРЕЩЕНО.
6. `EXIT_CONFIRMED` → любое состояние — терминальное, выходов НЕТ.
7. Из любого состояния: отправка заявки на количество больше подтверждённого остатка — ЗАПРЕЩЕНО (жёсткая проверка при формировании INTENT).
8. Две одновременно активные закрывающие заявки одного инцидента (и одной позиции) — ЗАПРЕЩЕНО (одна активная заявка на инцидент в каждый момент; проверка перед каждой отправкой).
9. `EXIT_FAILED` → состояния отправки автоматически — ЗАПРЕЩЕНО (только T-25 через оператора/политику).
10. Переходы, меняющие количество уже зафиксированных исполнений задним числом — ЗАПРЕЩЕНО (append-only учёт).

### 6.4. Правило перезапуска (R-9)

После перезапуска процесса ВСЕ активные инциденты (любое
нетерминальное состояние) переходят в `RECONCILING` и НЕ совершают
никаких сетевых действий до завершения reconciliation (EE-16).
Невозможно достоверно проверить состояние → `UNCERTAIN`
(семантика main.py:5147-5151; execution.py:1024-1246). Повторный SELL
после перезапуска возможен ТОЛЬКО после подтверждённого остатка и
отсутствия активных заявок (защита от повторного SELL после рестарта —
EE-16).

## 7. Последовательность гибридного выхода — этапы A–E (§3.4 ТЗ)

### Этап A. Обнаружение

- Получить валидную цену: только через шлюз `_valid_price` (§6.2
  blueprint; EP-1…EP-6 не фиксируют пробой по недействительной цене —
  поведение D-22).
- Обнаружить срабатывание Stop Loss: для BUY `price <= sl_price`
  (семантика check_all — execution.py:1007); для не-стоповых причин —
  решение выхода.
- Создать уникальный Exit Incident (incident_id = uuid4, создаётся ДО
  первого действия); записать намерение обработки ДО отправки заявки
  (EXIT_INTENT_PERSISTED — INTENT-BEFORE-SEND уровня инцидента).
- Сохранить атрибуты: breach_kind, breach_depth, причины, sl_price,
  цену фиксации, config_hash, время.
- НЕ создавать новую позицию и НЕ менять стратегию: входы по FIGI
  инцидента запрещены на весь период инцидента (совместимо с
  существующей блокировкой входов main.py:5186-5225).

### Этап B. Reconciliation (перед ЛЮБОЙ новой заявкой)

Проверяется перед первой отправкой инцидента, перед КАЖДОЙ последующей
заявкой и после КАЖДОГО неопределённого результата:

1. брокерская позиция: `get_positions` (tinkoff_client.py:315-330;
   None → UNCERTAIN, F-26);
2. существующие закрывающие заявки: `get_sandbox_orders`
   (tinkoff_client.py:437-456) + реестр + `get_sandbox_order_state`
   (статус + lots_executed; tinkoff_client.py:601);
3. подтверждённые исполнения (FILL с executed > 0; частичные —
   PARTIALLYFILL / lots_executed > 0 при нетерминальном статусе);
4. подтверждённый остаток = брокерская позиция, сведённая с локальным
   учётом (несходимость → UNCERTAIN, не «наименьшее из двух»);
5. исключить дублирующий SELL: переиспользуется `_sell_block_reason`
   (main.py:738-767) — при блокировке фиксируется событие (аналог
   SELL_DUPLICATE_BLOCKED main.py:2244), НОВАЯ заявка НЕ отправляется.

Если закрывающая заявка уже в процессе исполнения — СНАЧАЛА разрешить её
судьбу (reconcile-механики execution.py:1024-1246 сохраняются), потом
решение. **ЗАПРЕЩЕНО отправлять дублирующий SELL только потому, что цена
продолжает снижаться.**

### Этап C. Контролируемая попытка (лимитная заявка; SL-инциденты)

Первоначально — ЛИМИТНАЯ заявка на ПОДТВЕРЖДЁННЫЙ остаток (требуется
расширение адаптера — §5). Архитектура предусматривает:

- **цену заявки** — только из политики D-18 (начальная цена и правила
  переустановки: шаг к текущей цене / рыночная граница минус N тиков /
  без переустановки); цена заявки НЕ выдумывается архитектурой;
- **срок ожидания** — только D-17 (N циклов движка / абсолютное время /
  до конца сессии);
- **контроль статуса и частичных исполнений** — по lots_executed после
  каждого опроса; исполненная часть немедленно фиксируется (этап E);
- **контроль оставшегося количества** — остаток = подтверждённый остаток
  минус исполненное; заявка на количество больше подтверждённого остатка
  ЗАПРЕЩЕНА (проверка при INTENT);
- **контролируемую отмену / изменение цены** — cancel_order с проверкой
  результата (неизвестный исход → UNCERTAIN + reconciliation, БЕЗ новой
  заявки до сверки — EE-09); счётчик попыток D-19; каждая попытка —
  новая запись INTENT-before-send с тем же incident_id.

**Нельзя ждать бесконечно:** срок ограничен D-17/D-19; исчерпание →
этап D (через `ESCALATION_READY`).

**Не-стоповые причины (TP/BE/TRAIL/стратегические):** по умолчанию —
рыночная заявка ПЕРВЫМ действием инцидента (сохраняет фактическое
поведение исполнения существующего движка; рыночная нога — через
`close_position` внутри контроллера), затем те же частичные исполнения /
неизвестные статусы / reconciliation, что и у SL-инцидентов. Расширение
лимит-первой последовательности на не-стоповые причины — решение владельца
D-24 (не принимается архитектурой).

### Этап D. Эскалация к рыночной заявке

Если лимитная попытка не закрыла позицию в установленном порядке
(истечение D-17 / исчерпание D-19 / условие D-20):

1. выполнить reconciliation;
2. подтвердить остаток (get_positions + учёт; None → UNCERTAIN, не
   эскалация «вслепую»);
3. исключить наличие активной заявки, которая ещё может исполниться
   (get_sandbox_orders + реестр; при активной — сначала разрешить её
   судьбу, не эскалировать поверх);
4. эскалировать закрытие остатка к РЫНОЧНОЙ заявке на ПОДТВЕРЖДЁННЫЙ
   остаток (событие `EMERGENCY_EXIT_ESCALATED` → `EMERGENCY_EXIT_MARKET_SENT`).

Рыночная заявка — попытка максимально БЫСТРОГО выхода, а НЕ гарантия
исполнения по определённой цене. После отправки — продолжение контроля
исполнения и сверки (тот же цикл опроса, что у существующих заявок);
повторная попытка при отказе — ТОЛЬКО по правилам D-21 и ТОЛЬКО после
reconciliation (T-20 → RECONCILING).

### Этап E. Подтверждение

- Продолжать контроль частичных исполнений после КАЖДОЙ отправки;
- НЕ закрывать повторно уже исполненное количество (residual-механики
  main.py:128-290 распространяются на заявки инцидента);
- Считать позицию закрытой ТОЛЬКО после подтверждения полного закрытия
  брокером: сумма исполнений всех частей инцидента == подтверждённый
  остаток И `get_positions`: нулевой остаток по FIGI (None → UNCERTAIN);
- Событие `EMERGENCY_EXIT_CONFIRMED` пишется ТОЛЬКО после сверки.
  **Отправка заявки НЕ считается подтверждением продажи.**
- CSV-строка закрытия создаётся штатным process_closing (main.py:2835)
  с reason_code инцидента (первая причина merged-списка — защитная
  причина имеет приоритет в reason_code, все причины сохранены в событиях).

## 11. Ограничения (ОБЯЗАТЕЛЬНОЕ описание)

**Даже единый контролируемый маршрут НЕ гарантирует ограничение убытка
стоп-ценой.** Программный механизм НЕ может гарантировать продажу, если
рынок не позволяет исполнить заявку. Возможны:

- отсутствие покупателей (нет встречного предложения на любом уровне);
- остановка торгов (дискретный аукцион, технический сбой, делистинг);
- отсутствие ликвидности (спред уходит, глубина рынка пуста);
- резкий гэп (исполнение существенно хуже стопа);
- отказ или недоступность брокера (API не отвечает — D-23: UNCERTAIN,
  программное закрытие невозможно);
- задержка получения котировок (пробой фиксируется с опозданием);
- частичное исполнение (остаток продолжает нести риск);
- отказ рыночной заявки (REJECTED — повтор по D-21 или оператор).

Расчётный риск с резервом (§7.4 blueprint, STAGE2_RISK_MODEL_FORMULAS.md)
— ПРОГНОЗ и лимит наблюдения, НЕ гарантированный предел убытка:
превышение плановой оценки возможно и обязательно журналируется
(open_risk_total > budget → RISK_BUDGET_EXCEEDED; фактический пробой
глубже стопа → PROTECTIVE_STOP_DETECTED с breach_depth). Единственный
последний слой при недоступности программного механизма — внешняя защита
оператора (ограничения брокера, ручное вмешательство), которая
архитектурой НЕ замещается.

Дополнительное ограничение ред. 2.3.1 (честность модели): резерв
STOP_SLIPPAGE_RESERVE до решения владельца (D-16) НЕ сконфигурирован —
расчётный риск НЕ является полным прогнозом гэп-риска (§4.7 ТЗ;
STAGE2_RISK_MODEL_FORMULAS.md §7).
