## 6. Какие риски остаются

1. **Рыночные риски выхода:** даже единый контролируемый маршрут НЕ
   гарантирует ограничение убытка стоп-ценой (нет покупателей,
   остановка торгов, гэп, отказ брокера, частичное исполнение) — EEA
   §11; внешний слой — оператор.
2. **Неподтверждённое поведение биржи/SDK:** V-1 (сырые статусы), V-10
   (лимитные/рыночные заявки в граничных режимах) — проверяются в
   sandbox-прогоне этапа H по явной процедуре владельца.
3. **Реализация этапа H:** контроллер + лимитная заявка + конфигурационная
   защита решений — НОВЫЙ код; приёмка по EE-01…EE-27 + CD-01…CD-06
   обязательна; до реализации — архитектурные гарантии (документация)
   не исполняются автоматически.
4. **Условная природа приёмки:** тестовая матрица — требования; её
   выполнение станет доказательством только на этапах D/H после
   реализации.

## 7. Можно ли переходить к реализации

**ДА — с ограничениями (условия):**

1. Архитектура зафиксирована комплектом версии 2.3.2 (ACCEPTED WITH
   OPEN DECISIONS); этапы A–G могут начинаться по ROADMAP без ожидания
   решений D-16…D-28 (они блокируют ТОЛЬКО этап H и жёсткие части
   этапа D).
2. ОБЯЗАТЕЛЬНО до этапа H: письменно принятые D-16…D-23 и варианты
   D-24/D-26/D-27 (UNCONFIGURED блокирует активацию — конфигурационная
   защита §3а; тесты CD-01…CD-06); никакая реализация аварийного выхода
   без них не начинается.
3. Реализация этапа H ОБЯЗАНА пройти приёмку по TEST_MATRIX §8
   (EE-01…EE-27, включая «НЕТ ни одной закрывающей заявки вне
   process_incidents») и §10 (CD-01…CD-06); этап D — с RM-01…RM-17.
4. Инвариант ALL_BOT_SELL_SUBMISSIONS ⊆ process_incidents() действует
   для ВСЕХ будущих этапов и компонентов; прямой SELL из торгового
   цикла / check_all / Telegram-обработчика и второй исполнитель
   запрещены.
5. Сохраняются все маркеры и ограничения ТЗ: никакой оптимизации
   порогов, никакой торговли, никаких брокерских заявок до явных
   процедур владельца (sandbox-прогон — по RUNBOOK); GitHub READ-ONLY.
