# KNOWN LIMITATIONS — STAGE D

SAMSUNG V4 NEW STRATEGY ENGINE — STRATEGY-SPECIFIC RISK SIZING

---

1. **LONG-only.** Текущий движок поддерживает только длинные позиции по
   акциям. TradeSide.SHORT явно отклоняется (UNSUPPORTED_SIDE);
   короткое масштабирование и геометрия «стоп выше входа» не
   реализуются. Если будущий этап добавит SHORT — расширение пойдёт
   через новую явную поддержку, не через молчаливую интерпретацию.

2. **Чистый расчёт, не исполнение.** SizingResult — теоретический
   объём, а не ордер/команда. Трансформация результата в заявку,
   модификации позиций и взаимодействие с брокером — вне Stage D и
   запрещены ТЗ §9. Слой не создаёт второй системы хранения и не имеет
   состояния.

3. **Свежесть цен не входит в Stage D.** Модуль валидирует
   корректность значений цен (>0, конечность), FIGI-согласованность
   котировок PriceData и геометрию стопа, но НЕ проверяет возраст
   котировок: проверка устаревания — зона ответственности price gate
   Stage C (check_price). Если вызывающий код передаёт устаревшие, но
   структурно корректные цены, Stage D выполнит расчёт на этих данных.
   Ограничение задокументировано осознанно: дублирование price gate
   создало бы вторую точку правды о «свежести».

4. **Консервативная модель покупательной способности.** На единицу
   расходуется entry_price*multiplier + entry_cost_per_unit. Если
   стоп-выходные затраты также должны учитываться в потребности
   покупательной способности — текущая модель их НЕ включает (риск-
   лимит их включает). Возможен чуть более «щедрый» объём по bp-каналу,
   чем предельная модель с учётом обоих сборов; риск- и notional-каналы
   консервативны в любом случае, итог = минимум трёх каналов.

5. **Float-зеркала денег — отображение.** Денежные поля результата
   (risk_budget, risk_per_unit, total_position_risk, position_notional,
   notional_cap, buying_power_cap) — float-представления точных
   десятичных величин. При экстремальных входах отдельное значение
   может быть непредставимо float (risk_per_unit в ZERO_SIZE с
   price_risk > 1.8e308) — поле None, ТОЧНОЕ значение всегда в
   diagnostics (строка Decimal). Потребители, которым нужна точность,
   должны читать diagnostics; float-зеркала — для логирования/отображения.

6. **Ноль затрат — данные, не «неизвестно».** Явно переданный
   entry_cost_per_unit=0 трактуется как нулевая комиссия (реальный
   сценарий). «Неизвестно» передаётся ТОЛЬКО None и блокирует расчёт.
   Отрицательные затраты отклоняются (ребейтов нет).

7. **Портфельные лимиты вне области.** Слой применяет ТОЛЬКО доли
   риск-политики (риск/сделка, notional/позиция) и доступную
   покупательную способность. Общие лимиты портфеля (MAX_TOTAL_EXPOSURE,
   лимиты на количество инструментов, дневные лимиты сделок) —
   ответственность других слоёв; в Stage D не дублируются.

8. **price_required-семантики Stage C здесь нет.** Stage D всегда
   требует ЯВНЫЕ цены входа/стопа (None -> блокировка): это sizing-контракт,
   а не exit-evaluation контракт; переиспользование check_price Stage C
   сделало бы sizing зависимым от exit-семантики staleness (см. п. 3).

9. **Отсутствие интеграции с runtime.** По ТЗ §9 Stage D не подключается
   к main.py/execution.py; интеграция расчёта в торговый цикл —
   предмет ОТДЕЛЬНОГО будущего этапа с собственным ТЗ (не начинается
   в Stage D).

10. **Многопоточность.** calculate_position_size — чистая функция без
    разделяемого состояния: безопасна для параллельных вызовов.
    Типизированные объекты — frozen, но object.__setattr__ технически
    обходит frozen (у Python нет абсолютной защиты); компенсация —
    verify_policy_hash (перехват tamper политики) и валидатор результата.
