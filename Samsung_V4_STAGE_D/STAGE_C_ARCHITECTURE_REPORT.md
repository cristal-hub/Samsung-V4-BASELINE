## 1. Место Stage C в архитектуре движка

```
               Stage A.2.1 (принято, неизменно)
  StrategyConfig | AttributionContext | Signal | EntrySignalInput | Strategy ABC
               \                                        |
                \                                       v
                 \            +-------------------------------------+
                  \           | Stage C: strategy_contracts.py      |
                   \          |                                     |
  рынок (цена) ---->  PriceData -> check_price  (fail-closed gate)
                               |                                     |
  StrategyStateManager (Stage B.1) --------> ExitDecisionCoordinator
                               |        1. проверка атрибуции (Stage A.2.1 recheck)
                               |        2. чтение состояния пары (изоляция ключа)
                               |        3. price gate (ДО оценщиков)
                               |        4. стратегический оценщик  -> ExitEvaluation
                               |        5. защитный оценщик        -> ExitEvaluation
                               |        6. merge_exit_evaluations  -> ExitMergeResult
                               |        7. запись в состояние ТОЛЬКО через
                               |           manager.update_state (атомарный RMW)
                               +-------------------------------------+
                                                |
                                                v
                                   ExitDecisionReport (типизированный
                                   отчёт; НЕ команда исполнения)
```

Stage C — контрактный слой: он НИЧЕГО не исполняет. Выход отчёта —
типизированное решение для последующих этапов (Stage D — risk sizing,
Stage E — симулятор). Заявок нет, брокера нет, исполнения нет.

## 3. Ключевые архитектурные решения

### 3.1 Единая точка проверки цены ДО оценщиков
Ценовая защита — не обязанность стратегий, а свойство контрактного
слоя: `ExitDecisionCoordinator.evaluate_and_record` выполняет
`check_price` ДО вызова любого оценщика. При провале — отчёт
INCOMPLETE_PRICE_EVALUATION с `evaluators_called=False`, состояние не
трогается. Это исключает целый класс ошибок «стратегия получила
фиктивную цену»: такой путь архитектурно невозможен.

### 3.2 Проверка результата, а не типа оценщика
Оценщики — произвольные объекты с методом `evaluate_exit(request)`.
Граница безопасности — строгая проверка ВОЗВРАЩЁННОГО значения
(точный тип ExitEvaluation + совпадение атрибуции с запросом):
подкласс/подделка не проходит; исключение конвертируется в
EVALUATION_BLOCKED источника. Так нельзя обойти контракт ни подклассом
оценщика, ни подделкой результата.

### 3.3 Merge — чистая функция
`merge_exit_evaluations` детерминирован по построению: нет времени,
случайности, обращения к состоянию; результат — frozen dataclass с
равенством по содержимому. Одинаковые входы всегда дают одинаковый
итог (тест §6.7). Правила зафиксированы версией
`EXIT_MERGE_RULES_VERSION = "exit_merge_rules_v1"` и включены в
diagnostics итога — решение самодокументировано.

### 3.4 Защитный приоритет как таблица истинности
Правила объединения — явная таблица (см. IMPLEMENTATION_REPORT_STAGE_C.md
§4), а не порядок аргументов или «кто последний». Защитный выход
побеждает ВСЕГДА; стратегический — только при защитном NO_EXIT;
незавершённая оценка любого слоя делает итог неисполнимым
(INCOMPLETE_*), сохраняя информацию обоих слоёв. Это предотвращает и
потерю защитного решения, и «тихое» продолжение по неполным данным.

### 3.5 Состояние — только через атомарный API Stage B.1
Координатор не хранит состояния сам и не пишет напрямую в StateStore:
только `manager.get_state` / `manager.update_state(updater=...)`.
Запись выполняется под замком хранилища Stage B.1 — конкурентные
циклы координаторов (в т.ч. разных менеджеров на разных экземплярах
StateStore того же пути) сериализуются корректно (тест §6.17: 80
RMW-обновлений без потерь). Ошибки состояния (StateConfigMismatchError,
StateCorruptionError, StateValidationError) пробрасываются как есть.

### 3.6 Запись состояния только при исполнимом итоге
- PROTECTIVE_EXIT / STRATEGIC_EXIT / NO_EXIT -> запись
  `last_exit_evaluation` (сводка: outcome, source, reason_code,
  exit_type, версия правил, полная атрибуция, decided_at).
- INCOMPLETE_* -> состояние НЕ изменяется вовсе: нельзя менять
  состояние «как будто выход состоялся» (ТЗ §3.4) — и нельзя менять
  состояние «как будто решение вынесено», когда оно не вынесено.

### 3.7 Точные типы на всех границах (анти-обход)
`type(x) is X` применяется ко ВСЕМ контрактным объектам на границах
потребителей (merge, координатор, валидаторы, отчёт). Frozen dataclass
защищает от мутаций; точные типы — от ослабленных подклассов. Атрибуция
перепроверяется на каждой границе; config_hash перепроверяется исходным
алгоритмом Stage A.2.1 через AttributionContext.from_config.

## 4. Границы и не-цели (ТЗ §4)

Реализовано: контракты, валидация, merge, price gate, интеграция
состояния. НЕ реализовано (и не требуется): симулятор, загрузчик
исторических данных, Sandbox adapter, заявки/отмены, брокерское
исполнение, risk sizing, EmergencyExitController, гибрид
LIMIT→reconcile→MARKET, новая торговая стратегия, оптимизация
параметров, Force Trade, изменения legacy_samsung_v4 (остаётся
REGRESSION_ONLY). Смысл принятых контрактов Stage A.2.1 и Stage B.1
не изменён (база побайтово неизменна).

## 5. Ограничения дизайна

* Многопроцессность: гарантия атомарности наследуется от Stage B.1 и
  действует в пределах ОДНОГО процесса (см. KNOWN_LIMITATIONS_STAGE_C.md).
* Гарантии исполнения решений Stage C не предоставляет: отчёт — не
  команда; исполнение — предмет последующих этапов.
* Стратегический/защитный оценщики в Stage C — интерфейсы без
  конкретной торговой логики: конкретные правила (стоп-лосс и т.п.)
  вводятся в последующих этапах; тесты используют эталонные
  тестовые оценщики.
