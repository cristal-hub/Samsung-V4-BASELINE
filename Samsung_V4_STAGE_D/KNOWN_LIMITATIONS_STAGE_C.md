# KNOWN_LIMITATIONS_STAGE_C.md
# SAMSUNG V4 — NEW STRATEGY ENGINE. STAGE C — ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ

Дата: 2026-11-28. Полный честный перечень ограничений Stage C.

## 1. Границы гарантий атомарности состояния (наследуется от Stage B.1)

* Атомарность read-modify-write состояния (включая записи Stage C через
  `manager.update_state`) действует В ПРЕДЕЛАХ ОДНОГО ПРОЦЕССА:
  все потоки процесса сериализуются общим RLock хранилища (для
  persistent-режима — общий RLock по realpath каталога, для memory —
  RLock экземпляра).
* НЕСКОЛЬКО ПРОЦЕССОВ НЕ ПОДДЕРЖИВАЮТСЯ: межпроцессной блокировки в
  Stage B.1 нет, Stage C её не добавлял. Если один и тот же каталог
  состояния используется несколькими процессами одновременно,
  атомарность не гарантируется. Это документированное ограничение
  Stage B.1, честно перенесённое в Stage C.
* updater (включая внутренний updater Stage C) вызывается под замком
  хранилища и обязан быть чистой быстрой функцией; повторный вход в то
  же хранилище из updater разрешён (RLock реентерабелен), ожидание
  других потоков внутри updater — запрещено (риск взаимного ожидания).

## 2. Ограничения контрактного слоя Stage C

* Stage C НЕ исполняет решения: `ExitDecisionReport` — типизированный
  отчёт, а не команда на брокер/ордер. Исполнение (и вообще любые
  брокерские действия) — предмет последующих этапов; в Stage C путь от
  отчёта к заявке отсутствует.
* `INCOMPLETE_*` итоги означают «решение не вынесено»: при защите
  fail-closed блокировка оценки (цена/ошибка слоя) подавляет исполнимый
  итог. Это осознанное решение: лучше не вынести решение, чем вынести
  его по неполным данным. Обратная сторона: при длительной
  неработоспособности источника цены координатор будет возвращать
  INCOMPLETE_PRICE_EVALUATION, не вынося решений (позиция продолжает
  существовать в состоянии как есть). Обработка этого режима на уровне
  движка — предмет последующих этапов.
* Правило «незавершённая стратегическая оценка + защитный NO_EXIT ->
  INCOMPLETE_STRATEGIC_EVALUATION» может withholding-ить NO_EXIT-итог
  при деградации стратегического слоя. Это задокументированное правило
  таблицы истинности (не скрытый приоритет), покрытое тестами.
* Порог устаревания цены (`price_max_age_seconds`) — ЯВНЫЙ параметр
  вызывающего кода; Stage C не задаёт рыночно-осмысленного порога по
  умолчанию (скрытые умолчания для торговых решений запрещены ТЗ §5).
  None отключает проверку устаревания — это должно быть явным решением.
* `check_price` проверяет: тип, положительность/конечность, figi,
  читаемость и часовой пояс метки, будущее время, устаревание. Он НЕ
  проверяет: соответствие цены рыночным диапазонам (например,
  «цена не могла упасть в 100 раз за секунду»), дубликаты/пропуски
  потока цен, валюту инструмента. Такие проверки — предмет
  последующих этапов или источника данных.
* `PriceData` не содержит идентификатора биржи/актуальности
  (например, аукцион vs основные торги); источник — произвольная
  непустая строка без реестра допустимых значений.
* Entry-контракт не интегрирован с состоянием в Stage C: рантайм входа
  (`EntryEvaluationRunner`) чистый (без записи состояния) — запись
  контекстов входа в состояние не требуется ТЗ §3.5 и не выполнялась.
* Метка `decided_at` у контрактов и записей — время координатора
  (инъекционный clock); синхронизация часов между узлами не входит в
  гарантию.
* Обход проверки через подклассы закрыт точными типами на границах
  потребителей контрактов; в рамках ОДНОГО процесса вызов внутренних
  обходных путей Python (object.__setattr__ и т.п.) остаётся
  теоретически возможен для кода, который сознательно ломает
  инварианты — защита рассчитана на честных потребителей и на
  случайные нарушения.

## 3. Ограничения тестового покрытия

* Тесты Stage C выполняются в одном процессе (многопоточность —
  ThreadPoolExecutor). Межпроцессные сценарии не тестируются в силу
  п. 1.
* Оценщики в тестах — эталонные тестовые объекты; конкретных торговых
  правил (стоп-лосс, трейлинг и т.п.) в Stage C нет — их появление
  ожидается в последующих этапах.
* Тесты не проверяют производительность (lock contention при очень
  высоких частотах вызовов не измерялась).

  действуют и в Stage C.
