## 1. Цель и границы

**Цель (§6 ТЗ Stage 2.3):** не допустить ситуации, когда цена прошла ниже
стопа, защитный выход не исполнился, а робот продолжает бесконтрольно
удерживать позицию. Владелец выбрал третий вариант аварийного выхода —
**ГИБРИДНЫЙ МЕХАНИЗМ: КОНТРОЛИРУЕМАЯ ПОПЫТКА ВЫХОДА → ЭСКАЛАЦИЯ К
РЫНОЧНОЙ ЗАЯВКЕ**.

**Границы компонента:**

- `EmergencyExitController` контролирует завершение защитного выхода из
  УЖЕ ОТКРЫТОЙ позиции, если обычный механизм выхода не обеспечил полное
  закрытие;
- он НЕ генерирует торговые сигналы и НЕ меняет стратегию (входы
  запрещены на весь период инцидента);
- он НЕ является трейдинговой логикой: решение «что купить/когда войти»
  ему недоступно; его решения — ТОЛЬКО «чем и как завершить закрытие
  позиции, чей защитный выход не завершился»;
- Stage 2.3 НЕ реализует компонент: никакой торговой логики, никаких
  заявок, никакой торговли (мандаты в шапке).

## 2. Проблема, которую необходимо решить (§6.1 ТЗ)

**Пример (из ТЗ):** позиция куплена по 100; установлен стоп на 97; рынок
открывается гэпом по 93; защитный выход не исполняется по 97; цена
продолжает снижаться. Плановый убыток по стопу уже не соответствует
реальному риску: фактическая цена далеко за стопом, а движок всё ещё
«владеет» позицией.

**Почему это возможно (FACT — подтверждено кодом):**

1. SL/TP — ПРОГРАММНЫЙ, а не биржевой: `check_all` сравнивает текущую
   цену со стопом по поллингу (execution.py:995-1022: для BUY
   `hit_sl = price <= pos.sl_price`; никакого стоп-ордера у брокера не
   существует — grep по пяти файлам: 0 совпадений, F-22). Между
   двумя опросами цена может уйти далеко за стоп; исполнение «по цене
   стопа» НЕ гарантировано даже при срабатывании.
2. Программный Stop Loss НЕ гарантирует исполнение по цене стопа:
   после фиксации `hit_sl` отправляется рыночная SELL
   (close_position, main.py:2224-2376), а рыночная заявка исполняется
   по НАИЛУЧШЕЙ ДОСТУПНОЙ цене рынка в момент исполнения — при гэпе,
   низкой ликвидности или остановке торгов это может быть значительно
   хуже стопа; заявка может исполниться частично или быть отклонена.
3. Предполагать наличие биржевого стоп-ордера ЗАПРЕЩЕНО: его
   использование не подтверждено исходным кодом и возможностями
   адаптера T-Invest (§4 этого документа).
4. При частичном исполнении защитной SELL или при неизвестном её
   статусе существующая защита БЛОКИРУЕТ новую SELL
   (`_sell_block_reason`, main.py:738-767) — правильно с точки зрения
   дублей, но оставляет остаток позиции без активного завершающего
   механизма, пока судьба заявки не разрешена. Именно этот зазор
   закрывает `EmergencyExitController`.

Движок должен обнаружить пробой стопа и запустить аварийный сценарий;
нельзя считать, что наличие программного Stop Loss гарантирует
ограничение убытка.

## 3. Место компонента в архитектуре (§6.2 ТЗ)

**ПРОЕКТ.** Отдельный компонент `EmergencyExitController`
(новый модуль `emergency_exit.py`; FILE_CHANGE_MAP §3.8; интеграция —
M-7 в торговом цикле ПОСЛЕ шага защитных выходов, без изменения самого
шага; roadmap этап H).

| Свойство | Значение |
|---|---|
| Уровень | Execution Layer (§3 blueprint) — вместе с защитными SL/TP, НЕ в Strategy Layer |
| Вход | валидный снимок цен (шлюз `_valid_price` §6.2 blueprint — классы EP-1…EP-6 не доходят до контроллера как «цены»), состояние позиций монитора, состояние заявок реестра, политика (конфигурация D-17…D-23) |
| Выход | управляющие действия по заявкам (лимитная/рыночная на ЗАКРЫТИЕ), события, записи инцидента |
| Запрещено | создавать новые позиции; менять стратегию; отменять/изменять защитные SL/TP-решения других слоёв; отправлять заявки на что-либо кроме закрытия остатка позиции инцидента |
| Отключение | `emergency_exit_enabled=false` — конвейер идентичен до-H (защитные SL/TP остаются); FAIL-флаг в roadmap этап H |
| Восстановление | инциденты персистятся (state.json, раздел `emergency_incidents` — M-5); после перезапуска контроллер СНАЧАЛА выполняет reconciliation активных инцидентов, потом продолжает сценарий |

Контроллер — «дожиматель» незавершённого защитного выхода. Он не
подменяет ни check_all (SL/TP остаются первым защитным слоем), ни
close_position (полное закрытие штатным путём), ни reconcile/В2/В3
(сверка остаётся источником истины).

## 5. Логика гибридного выхода — этапы A–F (§6.3 ТЗ)

**ПРОЕКТ.** Конечный автомат инцидента: `DETECTED -> CHECKING ->
LIMIT_ATTEMPT -> (PARTIAL) -> (ESCALATED) -> CONFIRMED / FAILED /
UNCERTAIN`. Переходы фиксируются событиями (§8); каждый инцидент
уникален (`incident_id` = uuid4, создаётся ДО первого действия,
аналог close_order_request_id main.py:2258-2260).

### Этап A. Обнаружение пробоя стопа

- Получить АКТУАЛЬНУЮ ВАЛИДНУЮ рыночную цену: только через шлюз
  `_valid_price` (§6.2 blueprint; классы EP-1…EP-6 — цена отсутствует
  или невалидна: пробой НЕ фиксируется по недействительной цене, D-22
  определяет поведение ожидания/эскалации состояния).
- Обнаружить пересечение установленного стоп-уровня: для BUY
  `price <= sl_price` (та же семантика срабатывания, что check_all —
  execution.py:1010); событие `STOP_GAP_BREACH` фиксирует: время,
  figi, sl_price, фактическую цену, разрыв.
- Запустить аварийный сценарий: создать инцидент (incident_id), событие
  `EMERGENCY_EXIT_STARTED`.
- НЕ создавать новую позицию и НЕ менять торговую стратегию: входы по
  FIGI инцидента запрещены на весь период инцидента (совместимо с
  существующей блокировкой входов 5186-5225).

### Этап B. Проверка состояния заявки и позиции (перед любой новой заявкой)

Проверяется ДО отправки каждой заявки инцидента (и после каждого
неопределённого результата):

1. состояние уже существующей заявки на закрытие
   (get_sandbox_order_state — статус + lots_executed);
2. подтверждённые исполнения (FILL с executed > 0);
3. частичные исполнения (PARTIALLYFILL / lots_executed > 0 при
   нетерминальном статусе);
4. фактический остаток позиции (локальный учёт минус подтверждённые
   исполнения);
5. состояние брокерской позиции (get_positions — единственный источник
   истины по остатку; None -> UNCERTAIN, F-26);
6. исключить повторную отправку уже существующей заявки: переиспользуется
   `_sell_block_reason` (main.py:738-767: неразрешённая предыдущая
   SELL, нетерминальные записи close_orders, незавершённые SELL реестра
   по FIGI) — блокировка фиксируется событием (аналог
   SELL_DUPLICATE_BLOCKED main.py:2244), НОВАЯ заявка не отправляется.

Если закрывающая заявка уже находится в процессе исполнения — СНАЧАЛА
reconciliation (В2/В3/resolve-механики main.py:2018-2223 сохраняются),
потом решение. **ЗАПРЕЩЕНО отправлять дублирующий SELL только потому,
что цена продолжает снижаться.**

### Этап C. Контролируемая попытка выхода (лимитная заявка)

Первоначально — ЛИМИТНАЯ заявка для контролируемого закрытия
(требуется расширение адаптера — §4). Архитектура предусматривает:

- **цену заявки** — только из политики D-18 (варианты: шаг к текущей
  цене / рыночная граница минус N тиков / без переустановки); цена
  заявки НЕ выдумывается архитектурой;
- **срок ожидания исполнения** — только D-17 (N циклов движка /
  абсолютное время / до конца сессии);
- **проверку частичного исполнения** — по lots_executed после каждого
  опроса; исполненная часть немедленно фиксируется (этап E);
- **проверку оставшегося количества** — остаток = подтверждённый остаток
  позиции минус исполненное;
- **возможность контролируемой отмены** — cancel_order с проверкой
  результата; неизвестный исход отмены -> UNCERTAIN + reconciliation,
  БЕЗ новой заявки до сверки (EE-06);
- **возможность повторного выставления или изменения цены в пределах
  политики** — счётчик попыток D-19; каждая попытка — новая запись
  INTENT-before-send в реестре с тем же incident_id.

**Нельзя бесконечно ждать исполнения лимитной заявки:** срок ограничен
D-17/D-19; исчерпание -> этап D. INTENT-before-send обязателен для
каждой заявки (запись в реестр ДО сетевого вызова — паттерн
main.py:2254-2280).

### Этап D. Эскалация к рыночной заявке

Если контролируемая попытка не привела к полному закрытию за
установленное время (D-17) или лимитная заявка не может быть исполнена:

1. выполнить reconciliation;
2. определить подтверждённый остаток позиции (get_positions + учёт;
   None -> UNCERTAIN, не эскалация «вслепую»);
3. проверить отсутствие активной заявки, которая ещё может исполниться
   (get_sandbox_orders + реестр; при активной — сначала разрешить её
   судьбу, не эскалировать поверх);
4. эскалировать выход к РЫНОЧНОЙ заявке на ПОДТВЕРЖДЁННЫЙ остаток
   (событие `EMERGENCY_EXIT_ESCALATED` -> `EMERGENCY_EXIT_MARKET_SENT`).

Рыночная заявка — попытка максимально БЫСТРОГО выхода, а НЕ гарантия
исполнения по определённой цене. После отправки — продолжение контроля
исполнения и сверки (тот же цикл опроса, что у существующих заявок —
poll_open_orders 4254-4537 остаётся источником статусов; повторная
попытка при отказе — ТОЛЬКО по правилам D-21 после reconciliation).

### Этап E. Частичное исполнение

Если лимитная или рыночная заявка исполнена частично:

1. зафиксировать исполненное количество (lots_executed; событие
   `EMERGENCY_EXIT_PARTIAL {executed, remaining}`);
2. определить оставшееся количество;
3. НЕ закрывать уже проданную часть повторно (защита residual-исполнений
   существующих механик — main.py:128-290 — сохраняется и
   распространяется на заявки инцидента);
4. НЕ отправлять заявку на количество больше подтверждённого остатка
   (остаток пересчитывается после каждого исполнения);
5. продолжать аварийный сценарий для остатка позиции.

### Этап F. Подтверждение закрытия

Позиция считается закрытой ТОЛЬКО после:

1. подтверждения полного исполнения заявки (статус FILL с
   lots_executed == запрошенному остатку, либо сумма исполнений всех
   частей инцидента == остатку);
2. сверки фактической позиции у брокера (get_positions: нулевой остаток
   по FIGI; None -> UNCERTAIN).

Событие `EMERGENCY_EXIT_CONFIRMED` пишется ТОЛЬКО после сверки.
**Отправка заявки НЕ считается подтверждением продажи** (мандат §6.3
ТЗ; неписание этого правила — точный аналог запрета фиктивного P&L).
CSV-строка закрытия создаётся штатным process_closing (main.py:2835)
с reason_code инцидента.

## 7. Ограничения (§6.5 ТЗ — ОБЯЗАТЕЛЬНОЕ описание)

**Даже гибридный выход НЕ гарантирует ограничение убытка стоп-ценой.**
Программный механизм НЕ может гарантировать продажу, если рынок не
позволяет исполнить заявку. Возможны:

- отсутствие покупателей (нет встречного предложения на любом уровне);
- остановка торгов (дискретный аукцион, технический сбой, делистинг);
- отсутствие ликвидности (спред уходит, глубина рынка пуста);
- резкий гэп (исполнение рыночной заявки существенно хуже стопа);
- отказ или недоступность брокера (API не отвечает — D-23: UNCERTAIN,
  программное закрытие невозможно);
- задержка получения котировок (пробой фиксируется с опозданием);
- частичное исполнение (остаток продолжает нести риск);
- отказ рыночной заявки (REJECTED — повтор по D-21 или оператор).

Расчётный риск с резервом (§7.4 blueprint) — ПРОГНОЗ и лимит наблюдения,
НЕ гарантированный предел убытка: превышение плановой оценки возможно и
обязательно журналируется (open_risk_total > budget -> RISK_BUDGET_EXCEEDED;
фактический пробой глубже стопа -> STOP_GAP_BREACH). Единственный
последний слой при недоступности программного механизма — внешняя защита
оператора (ограничения брокера, ручное вмешательство), которая
архитектурой НЕ замещается.

## 8. События и журналирование (§6.8 ТЗ)

Названия могут уточняться при реализации; обязательное свойство — по
событиям восстанавливается ПОЛНАЯ хронология аварийного выхода
(кто/когда/что/по какой цене/на каком остатке).

| Событие | Момент | Ключевые поля |
|---|---|---|
| `STOP_GAP_BREACH` | зафиксировано пересечение стопа валидной ценой | incident_id, figi, strategy_id, sl_price, price, breach_depth, config_hash |
| `EMERGENCY_EXIT_STARTED` | запущен инцидент | incident_id, confirmed_balance (остаток на старте) |
| `EMERGENCY_EXIT_LIMIT_SENT` | отправлена лимитная попытка (после INTENT) | incident_id, order_request_id, limit_price, qty |
| `EMERGENCY_EXIT_PARTIAL` | частичное исполнение | incident_id, executed, remaining, avg_exec_price |
| `EMERGENCY_EXIT_LIMIT_CANCELLED` | контролируемая отмена попытки | incident_id, executed_so_far, cancel_confirmed |
| `EMERGENCY_EXIT_ESCALATED` | решение об эскалации (после reconciliation) | incident_id, confirmed_balance, cause (D-20) |
| `EMERGENCY_EXIT_MARKET_SENT` | отправлена рыночная заявка (после INTENT) | incident_id, order_request_id, qty |

## 9. Тест-матрица аварийного выхода (§6.9 ТЗ; детализация — STAGE2_TEST_MATRIX.md §8)

17 сценариев EE-01…EE-17; для каждого определено ожидаемое состояние
позиции, заявки, журнала и системы (четыре проверки на сценарий):

1. Обычное пересечение стопа (аварийный путь НЕ запускается).
2. Гэп ниже стопа (STOP_GAP_BREACH -> инцидент).
3. Лимитная заявка исполнена полностью.
4. Лимитная заявка исполнена частично.
5. Лимитная заявка не исполнена (тайм-аут D-17).
6. Отмена лимитной заявки (включая неизвестный исход отмены).
7. Эскалация к рыночной заявке (после reconciliation).
8. Частичное исполнение рыночной заявки.
9. Отказ рыночной заявки (REJECTED; повтор — D-21).
10. Неизвестный статус заявки.
11. Потеря связи с брокером.
12. Отсутствие актуальной котировки (пробой НЕ фиксируется по
    недействительной цене).
13. Перезапуск во время аварийного выхода (resume + reconciliation).
14. Повторная обработка одного и того же события (идемпотентность).
15. Попытка повторного SELL при существующей активной заявке
    (блокировка — F-27).
16. Подтверждение полного закрытия через reconciliation (get_positions).
17. Отсутствие покупателей / невозможность исполнения (ограничения §7).

Полная таблица с ожиданиями — STAGE2_TEST_MATRIX.md §8. Все тесты — на
мок-adapter (без брокера); этап реализации — H.
