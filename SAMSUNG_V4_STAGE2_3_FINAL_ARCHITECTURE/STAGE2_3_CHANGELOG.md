## 2. Коррекция №1 аудита — единые правила валидации конфигурации

**Суть коррекции (§3 ТЗ Stage 2.3).** В комплекте Stage 2.2 правила
валидации противоречили друг другу: N-04 требовал `RSI_OVERSOLD >=
RSI_OVERBOUGHT` -> отказ (равенство отвергалось), N-12/T-16 принимали
равенство (строгие неравенства strategy.py:355/371 — подтверждено кодом);
правило `MIN_CANDLES_FOR_SIGNAL >= TREND_FILTER_MA_PERIOD`
(§10.1/T-16/N-04) объявляло ошибкой конфигурации работоспособную
конфигурацию с более длинным прогревом индикатора (60/100), смешивая
«допуск сигнала» с «прогревом фильтра».

**Исправление (Blueprint §10.1 переработан; TEST_MATRIX T-16/T-17/N-04;
OPEN_DECISIONS P-14, F-28 — нет, F-20 остаётся):**

- противоречие N-04↔N-12 устранено: N-04 приведён к строгому
  неравенству (отвергается ТОЛЬКО инверсия OS > OB и мёртвые границы);
  равенство порогов принимается во всех документах единообразно —
  явное объяснение: при равных порогах ветки BUY (`rsi < OS`) и SELL
  (`rsi > OB`) не пересекаются — конфигурация работоспособна; при
  инверсии семантика перевёрнута (покупка при высоком RSI); при
  OS <= 0 / OB >= 100 соответствующая ветка мертва;
- правило `MIN_CANDLES >= TREND_FILTER_MA_PERIOD` ОТМЕНЕНО как правило
  валидации (строка таблицы §10.1 заменена строкой «ПРАВИЛО
  ОТМЕНЕНО»): период прогрева фильтра (strategy.py:231-232 — при
  дефиците свечей фильтр ШТАТНО возвращает False, сигнал HOLD, сигнал
  возможен после накопления ленты) — режимная готовность данных, а не
  допуск сигнала; эффект V-46 продолжает документироваться без
  «оптимизации»;
- введено разделение четырёх понятий (§10.1 п. 7): минимальная
  готовность данных / минимальное количество свечей для допуска сигнала
  (MIN_CANDLES_FOR_SIGNAL) / период прогрева индикатора (TREND_FILTER_MA_PERIOD
  и периоды всех индикаторов) / фактическая доступность конкретного
  индикатора;
- установлен единый контракт готовности (§10.1 п. 8): стратегия НЕ
  выдаёт сигнал, пока все необходимые ей данные и индикаторы не готовы;
  движок не признаёт конфигурацию некорректной ТОЛЬКО из-за длинного
  прогрева; в существующей стратегии все блоки самозащищены (HOLD при
  дефиците — strategy.py:197-198, 231-232, 258, 317, 58, 81-88);

## 3. Коррекция №2 аудита — модель риска и проскальзывание при исполнении стопа

**Суть коррекции (§4 ТЗ Stage 2.3).** Формулировка Stage 2.2 «разница
между ценой исполнения входа и стоп-ценой уже учитывает проскальзывание
при выходе» некорректна: разница `|exec_price - sl|` отражает входное
смещение и плановый убыток сценария «исполнение по стоп-цене», но НЕ
является резервом на неблагоприятное исполнение стопа (перескок цены
через стоп, исполнение хуже стоп-цены, частичное исполнение,
неисполнение).

**Исправление (Blueprint §7.4 переработан; TEST_MATRIX T-15;
OPEN_DECISIONS P-12, D-16; FILE_CHANGE_MAP M-4; ROADMAP этап D):**

- модель разделяет ТРИ величины в ТРИ момента времени: ESTIMATED RISK
  (до входа: planned_stop + плановые комиссии обеих сторон + ОТДЕЛЬНЫЙ
  резерв stop_slippage_reserve_ps), OPEN ESTIMATED RISK (после
  регистрации: `|exec_price - sl|` + фактическая/оценочная комиссия
  входа + оценочная комиссия выхода + ОТДЕЛЬНЫЙ резерв), REALIZED LOSS
  (после выхода: фактические цены всех частей и фактические комиссии —
  существующий учёт main.py:2464-2489);
- терминология: прогноз НЕ называется «actual risk»; термин
  `actual_per_share_risk` выведен из употребления (поля
  estimated_risk_*/open_risk_*/realized_loss_*); предполагаемое
  проскальзывание НЕ выдаётся за гарантированный предел убытка (прямая
  ссылка на §7 STAGE2_EMERGENCY_EXIT_ARCHITECTURE.md);
- правила недопущения двойного учёта: входное проскальзывание — член
  SLIPPAGE_PERCENT планового friction (risk_manager.py:125), в открытый
  риск вторым членом НЕ добавляется (оно уже внутри `|exec_price -
  sl|`); выходное проскальзывание — член STOP_SLIPPAGE_RESERVE;
  расстояние до стопа и резерв — РАЗНЫЕ члены; SLIPPAGE_PERCENT и
  STOP_SLIPPAGE_RESERVE — независимые величины (вход/выход);
- резерв — отдельная конфигурационная величина: форма и значение —
  решение владельца (D-16); до решения член = 0 с пометкой
  slippage_reserve_source="unconfigured"; НИКАКОГО процента не
  придумано (мандат NO THRESHOLD IS OPTIMIZED);
- формула на акцию и на позицию: явные члены (цена входа, стоп-цена,
  расстояние, резерв, комиссии, итог) — §7.4 blueprint;
- краевые случаи дополнены («резерв не сконфигурирован»); fail-safe
  режимы сохранены.

**Исправление (НОВЫЙ документ STAGE2_EMERGENCY_EXIT_ARCHITECTURE.md;
