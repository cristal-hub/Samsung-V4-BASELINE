# STAGE E — АРХИТЕКТУРНЫЙ ОТЧЁТ

Детерминированный исторический симулятор (event-driven backtest) для
проверки торговых стратегий на исторических данных MOEX. STRICT RESEARCH
ONLY: виртуальная симуляция на истории, без брокера, без сети, без
изменения принятых этапов.

## 1. Компоненты и ответственности (ТЗ Stage E §3)

```
BacktestEngine (engine.py)                 — фасад, компоновка прогонов
 ├─ HistoricalDataFeed (data_feed.py)      — хронологические закрытые свечи
 │   └─ CandleSeries / Candle (models.py) — валидированные неизменяемые данные
 ├─ EventEngine (event_engine.py)          — детерминированные фазы обработки
 │   ├─ StrategyRunner (strategy_runner.py)
 │   │   ├─ EntryEvaluationRunner      (Stage C, принят)
 │   │   ├─ ExitDecisionCoordinator    (Stage C, принят)
 │   │   │   ├─ SignalExitEvaluator             (движок: стратегический слой)
 │   │   │   ├─ StopLevelsProtectiveEvaluator   (движок: защитный слой)
 │   │   │   └─ StrategyStateManager (Stage B.1, принят, memory-режим)
 │   │   └─ EntrySignalInput / Signal  (Stage A, принят)
 │   └─ HistoricalExecutionSimulator (execution.py)
 │       ├─ RiskIntegration (risk_integration.py)

 │       └─ PortfolioLedger (ledger.py)
 └─ BacktestReportBuilder (report.py)     — отчёт + SHA-256
```

## 2. Модель исполнения (ТЗ §5) — задокументированные правила

**Моменты времени строго разделены:**

| Момент | Когда | Что происходит |
|---|---|---|
| Формирование сигнала | закрытие свечи i | стратегия получает срез [0..i] и close(i) |
| Принятие решения | закрытие свечи i | контракты Stage C (entry / exit merge) |
| Виртуальное исполнение | открытие свечи i+1 | вход/выход по open(i+1) с издержками |

**Правила цены исполнения:**
* исполнение по Close сигнальной свечи ЗАПРЕЩЕНО (цена, недоступная на
  момент решения, не может использоваться задним числом);
* цена входа: `open(i+1) * (1 + slippage_rate)`, ограничена сверху
  `high(i+1)`; цена выхода: `open(i+1) * (1 - slippage_rate)`, ограничена
  снизу `low(i+1)` (исполнение всегда внутри диапазона свечи);
* **гэп**: если open(i+1) уже за уровнем стопа — выход по open (ХУЖЕ
  стопа), задним числом по стопу не исполняется
  (`SL_GAP_THROUGH_STOP`);
* **SL/TP внутри одной свечи**: если low/high позволяют предположить
  достижение обоих уровней, а последовательность движения цены неизвестна —
  КОНСЕРВАТИВНАЯ модель: исполняется СТОП ЛОСС; факт неоднозначности
  фиксируется флагом `SL_TP_SAME_CANDLE_SL_PRIORITIZED` (в сделке и в
  `ambiguity_incidents` отчёта). Более выгодный сценарий автоматически
  НЕ выбирается;
* эмуляция стопов активна с момента входа (включая свечу входа: позиция
  открыта по открытию, остальная свеча идёт ПОСЛЕ входа).

**Фиксированный порядок фаз на каждой свече (ТЗ §7):**

```
ФАЗА 1 — исполнение на открытии:  1a. отложенный ВЫХОД; 1b. отложенный ВХОД
ФАЗА 2 — защита позиции внутри свечи: гэп-стоп -> SL -> TP (консервативно)
ФАЗА 3 — решения на закрытии:     3a. позиция есть -> ExitDecision (Stage C)
                                  3b. позиции нет -> EntryDecision (Stage C)
```

Решение ФАЗЫ 3 становится отложенным и исполняется в ФАЗЕ 1 следующей
свечи. Решение на закрытии последней свечи сегмента остаётся
НЕИСПОЛНЕННЫМ и фиксируется в отчёте (`unresolved_decisions`) — задним
числом не исполняется.

## 3. Защита от look-ahead bias (ТЗ §4)

* единственный канал данных к стратегии — `feed.view_upto(i)` /
  `entry_dataframe_upto(i)`: свечи [0..i] включительно; у кормушки НЕТ
  метода, выдающего серию целиком в путь решений; DataFrame — защитная
  копия (мутации стратегии не влияют на данные);
* индикаторы считает сама стратегия на полученном срезе — будущие свечи
  физически не попадают в вызов;
* решение на закрытии i исполняется не ранее открытия i+1: в тестах
  зафиксировано, что вход НЕ происходит по цене сигнальной свечи;
* отсутствующие данные не подменяются: пропуски свечей обнаруживаются
  (по явному `expected_candle_interval_seconds`), интерполяция и
  заполнение будущими значениями отсутствуют; политики `REPORT`/`STRICT`;
* PriceData для price gate несёт метку времени свечи; проверка
  `check_price` (Stage C) выполняется координатором до оценщиков.

Тесты: `test_strategy_never_sees_future_candles`,
`test_signal_after_close_executes_next_open_not_signal_close`,
`test_no_execution_on_decision_candle_close`,
`test_view_upto_never_returns_future_candles`,
`test_entry_dataframe_upto_is_defensive_copy`, гэп-тесты и др.

## 4. Использование Stage D (ТЗ §6) — без дублирования

`RiskIntegration.size_entry` готовит SizingInput из ФАКТИЧЕСКИХ данных
исполнения и вызывает принятый `calculate_position_size`:

| Поле SizingInput | Источник в симуляции |
|---|---|
| attribution | `AttributionContext.from_config(strategy_config)` |
| figi | EngineConfig.figi |
| side | TradeSide.LONG (единственный; SHORT Stage D отклоняет UNSUPPORTED_SIDE) |
| available_equity | кэш портфеля на момент исполнения |
| buying_power_limit | кэш (резерв под комиссию входа выполняет сама формула Stage D: per-unit BP-стоимость включает entry_cost_per_unit) |
| entry_price | ФАКТИЧЕСКАЯ цена исполнения (next open со slippage, cap по high) |
| protective_stop_price | `entry_price * (1 - stop_loss_fraction)` — строго ниже входа |
| lot_size / contract_multiplier | EngineConfig |
| entry_cost_per_unit | `commission_rate * entry_price` (согласовано с исполнителем) |
| stop_exit_cost_per_unit | `commission_rate * stop_price` |

* формула риска, округление лотов (только вниз до целого лота),
  проверки входных данных, config_hash и атрибуция — НЕ дублируются и
  НЕ изменяются: это код Stage D как есть;
* исход SIZED — единственный источник положительного объёма; любые
  блокирующие исходы (ZERO_SIZE, MISSING_REQUIRED_DATA,
  ATTRIBUTION_MISMATCH, UNSUPPORTED_SIDE, POLICY_INVALID, ...)
  переносятся в журнал как блокировка входа с сохранением reason_code;
* несовместимости интерфейса Stage D НЕ обнаружено — отдельный отчёт о
  несовместимости не требуется;
* следствие контракта Stage D: формула требует protective_stop_price,
  поэтому EngineConfig делает stop_loss_fraction обязательной (TP —
  опциональной), fail-closed на уровне конфигурации.

## 5. Детерминизм (ТЗ §7)

* фиксированный порядок фаз и событий; стабильные сортировки (гистограммы
  — словари с детерминированным пополнением; JSON — sort_keys);
* НЕТ системного времени (все метки — из данных свечей), случайности,
  переменных окружения, uuid; идентификатор прогона — SHA-256 от
  канонического набора {data_sha256, engine_config_sha256,
  strategy_config_hash, segment, границы, версия движка};
* SHA-256 входных данных: `CandleSeries.data_sha256` (repr float, канон.
  JSON); SHA-256 конфигурации: `EngineConfig.config_sha256`;
* часы Stage B.1/Stage C ИНЪЕЦИРОВАНЫ (метка текущей свечи) — состояние
  прогона детерминировано;
* повторный запуск даёт идентичные байты отчёта и одинаковый
  `report_sha256` (тесты: `test_rerun_produces_identical_report_and_hash`,
  `test_report_json_is_canonical_and_hash_stable`, legacy-прогон).

## 6. IS / VALIDATION / OOS (ТЗ §8)

* `SegmentSpec(label, start_index, end_index)`; `run_segments` выполняет
  КАЖДЫЙ сегмент как независимый прогон: свежие PortfolioLedger /
  StrategyStateManager / решение — позиции и состояние не переносятся
  через границу (тест: отчёт сегмента из бандла == отчёт сегмента
  отдельно);
* НЕ выполняется никакая оптимизация параметров: отчёты не содержат
  полей оптимизации, фасад не имеет методов подстройки
  (`test_oos_results_cannot_change_parameters_structural`); параметры
  прогона задаются ДО запуска и одинаковы для всех сегментов.

## 7. Учёт денег и издержек

* комиссия: `commission_rate * notional` на КАЖДУЮ сторону; списывается
  при входе (кэш -= notional + комиссия), при выходе (кэш += notional −
  комиссия);
* проскальзывание: неблагоприятная доля от open на каждую сторону,
  стоимость фиксируется в операциях и отчёте;
* плечо отсутствует: вход разрешён только при полном покрытии
  (notional + комиссия) кэшем; Stage D дополнительно ограничивает объём
  покупательной способностью (per-unit BP-стоимость включает комиссию);
* инвариант сохранения денег проверяется при каждой операции:
  `cash == initial + realized(закрытых) − стоимость_открытой_позиции`
  (допуск 1e-9 — только на порядок float-операций; содержательные
  дефекты дают расхождение на порядки больше);
* нереализованный PnL: рыночная стоимость позиции по закрытию − полная
  стоимость входа; кривая капитала — по закрытию каждой свечи;
  просадка — peak-to-trough на кривой.

## 8. Отчёт (ТЗ §3.7)

`report` (JSON-совместимый словарь + `report_sha256`): metadata (версии,
run_id, SHA-256 данных/конфигураций, атрибуция стратегии и риск-политики),
execution_model (эхо правил из §2), risk_integration (эхо параметров
Stage D), account (кэш/equity/доходность/просадка/buy-hold-бенчмарк/
открытая позиция), statistics (число сделок, wins/losses, Win Rate,
Profit Factor с ЧЕСТНЫМИ пометками об неопределённости, gross/avg
прибыль и убыток), costs (комиссии/проскальзывание), reasons
(гистограммы причин входов/блокировок/выходов), ambiguity_incidents,
gaps, unresolved_decisions, trades (полная атрибуция каждой сделки),
ledger_operations (история операций), equity_curve.

Profit Factor: gross_profit / gross_loss; если убытков нет — `None` с
пометкой `PROFIT_FACTOR_UNDEFINED_NO_LOSSING_TRADES` (не «бесконечная
красивость»).

## 9. Ключевые решения и обоснования

| Решение | Обоснование |
|---|---|
| Использование ExitDecisionCoordinator с memory-режимом Stage B.1 | единый контрактный путь решений с production; режим memory задокументирован Stage B (без файлов, оффлайн); часы инъекцированы |
| Стратегический выход = отображение сигнала Stage A | у legacy-стратегии исторически SELL — сигнал выхода (long-only); логика НЕ копируется: вызывается тот же контракт evaluate_entry, срез данных тот же |
| SL обязателен в EngineConfig | формула Stage D требует protective_stop_price; вход без определённого риска был бы либо блокировкой (MISSING_REQUIRED_DATA), либо подменой данных; выбор — явный fail-closed на уровне конфигурации |
| Защитный оценщик на закрытии (слой-страховка) | при включённой внутри-свечной эмуляции обычно предвосхищается исполнителем (стоп исполняется ВНУТРИ свечи по стопу); слой остаётся активной fail-closed защитой и покрыт юнит-тестами |
| Плечо запрещено, частичных закрытий нет | long-only кэш-модель; объём позиции целиком задаёт Stage D; частичные закрытия потребовали бы новую риск-логику (вне границ Stage E) |
