# STAGE2_IMPLEMENTATION_ROADMAP.md

## SAMSUNG V4 — STAGE 2: последовательность разработки (проект)

**Статус:** `STAGE 2 — DESIGN ONLY / SOURCE CODE: UNCHANGED`. Ни один этап
не выполнялся; документ — план будущей реализации.

Общие принципы (унаследованы от Stage 1 IMPLEMENTATION_ROADMAP §0):

1. Все работы — в отдельной ветке/копии сборки; рабочий робот не
   затрагивается (docs/ROLLBACK_RU.md).
2. Каждый этап завершается полным прогоном pytest и фиксацией SHA256
   изменённых файлов (практика candidate/SHA256SUMS*.txt).
3. После любого этапа система работоспособна; «торговая логика не
   менялась» проверяется golden-тестами.
4. Существующие 789 тестов (docs/INSTALLATION_RU.md §4) остаются зелёными;
   тесты добавляются, не заменяются.

### Обоснование порядка (§8 ТЗ: «если порядок изменить — обосновать»)

Порядок A–G ТЗ сохранён. Внутри этапов две перестановки относительно
Stage 1 roadmap, обе обоснованы:

1. **Атрибуция (strategy_id) включена в Этап A** (а не отдельный R2 после
   R1): атрибуция — предпосылка маршрутизации exit-политики (C) и
   INHERIT-режима (F), при этом не меняет поведения и по рискам сопоставима
   с конфигурационными работами A.
2. **Этап B (изоляция состояния) поставлен ПЕРЕД C (контракт выхода)**:
   `evaluate_exit` использует `state` пары (id, figi) — проектировать
   exit-контракт до изоляции состояния означало бы принять зависимость от
   ещё не устранённого общего состояния (Stage 1.1 §1). Этапы E/F идут
   после D, потому что backtest и sandbox-прогоны обязаны использовать
   уже согласованный контракт стоп-дистанции (иначе результаты
   несопоставимы). G — последний: интеграция поверх всех контрактов.
