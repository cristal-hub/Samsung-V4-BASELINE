## Изолированное состояние стратегии по ключу (strategy_id, FIGI)

Дата: 2026-11-28.
База: принятая реализация Stage A.2.1
(коммит `103d22d34d483fbb7179d1fef07dd0e24b51dfcd` от
cristal-hub/Samsung-V4-BASELINE), baseline `884cefd6f12a99f6adc14b5ed4c9eeda21d32e04`.

## 1. Цель и границы

Stage B реализует независимое состояние каждой стратегии для каждого
инструмента с ключом изоляции **(strategy_id, FIGI)**:

* состояние стратегии A не влияет на стратегию B;
* состояние инструмента X не влияет на инструмент Y;
* параллельная обработка не приводит к перекрёстному изменению состояния;
* изменение состояния одной пары не меняет состояние других пар;
* после перезапуска состояние восстанавливается из сохранённых данных;
* некорректное/несовместимое состояние не позволяет незаметно продолжить
  работу с неверными данными (fail-closed).

Границы Stage B соблюдены: торговая логика, параметры стратегий, сигналы,
риск-менеджмент и исполнение ордеров не затронуты; `evaluate_exit`
(Stage C) не реализован; исторический симулятор и Sandbox-адаптер не
реализованы; подключений к брокеру и заявок нет; `FORCE_TRADE` не
добавлялся; legacy Samsung V4 остаётся `REGRESSION_ONLY`.

## 3. StrategyState — модель состояния (ТЗ §3.1)

Неизменяемая типизированная модель одной пары (strategy_id, FIGI):

* **Привязка**: `strategy_id`, `figi`, `config_hash` — обязательные поля;
  каждое состояние однозначно связано с конфигурацией, для которой оно
  создано (config_hash проверяется форматом Stage A.2 — SHA-256, 64 hex).
* **Версия схемы**: `schema_version` (текущая `STATE_SCHEMA_VERSION = 1`)
  входит в сериализованный payload; чтение записи неизвестной версии даёт
  `StateSchemaError` — требуется явное решение о совместимости/сбросе,
  автоматической миграции нет.
* **Типизированные данные**: `data` — глубоко неизменяемое
  `ImmutableMapping` (та же защита, что у `params` конфигурации Stage A.1)
  поверх ПРОВЕРЕННЫХ JSON-совместимых значений (None/bool/int/float/str/
  Mapping/list/tuple/set). NaN/Infinity и произвольные объекты отклоняются
  `StateValidationError` — та же политика, что и в config_hash Stage A.2.
  Множества нормализуются в отсортированные списки (детерминизм).
* **Контролируемая сериализация**: `to_payload()` / `to_json()` —
  канонический JSON (сортированные ключи, без пробелов, `allow_nan=False`);
  одинаковое содержимое всегда даёт побайтово одинаковую строку.
  `from_payload()` проверяет ВСЁ: структуру, типы полей, версию схемы,
  ключи, формат config_hash, метки времени, данные; ошибки классифицированы
  (`StateCorruptionError` — повреждение, `StateSchemaError` — схема,
  `StateValidationError` — семантика). Повреждённая запись НЕ подменяется
  пустым состоянием.
* **Отсутствие общих изменяемых объектов**: `data` глубоко копируется при
  создании и эволюции; объекты состояния никогда не переиспользуются между
  ключами; источник, изменённый после создания, не влияет на содержимое.
* **Неизменяемость**: frozen dataclass; `setattr`/`delattr` отклоняются;
  эволюция — только через `with_data()`, возвращающее НОВЫЙ объект
  (created_at сохраняется, updated_at обновляется).
* Метки времени — ISO-8601 UTC фиксированного формата, проверяются при
  создании и десериализации; для детерминированных тестов передаются явно.

## 4. StateStore — хранилище (ТЗ §3.2)

### 4.1 Режимы

* **persistent** — ЯВНО переданный `path` (каталог): по одной JSON-записи
  на ключ (`<strategy_id>__<figi>.json`), атомарная запись
  (`tempfile.mkstemp` в том же каталоге → `os.replace` → fsync файла и
  каталога), детерминированное содержимое.
* **memory** — `path=None`: явный, документированный режим без файла
  (для тестов и процессов без persistent-истории). Скрытого файлового
  пути по умолчанию НЕ существует; состояние не записывается в старые
  файлы Samsung (state.json и др.).

Путь persistent-режима разрешается функцией `resolve_state_store_path()`
из ЯВНОГО ключа `STATE_STORE_PATH` переданной конфигурации: отсутствие
ключа, None, не-строка или пустая строка дают `StateStoreConfigError`
(никакого fallback на env/каталог процесса/старые файлы Samsung).
`engine.json` Stage B сознательно не изменяет: ключ добавляется владельцем
на этапе интеграции Stage C (это конфигурация Stage A — менять её без
прямой необходимости запрещено).

### 4.2 Интерфейс (названия ТЗ сохранены)

* `get_state(strategy_id, figi, *, config_hash=None)` → `StrategyState`
  или `None` (отсутствие записи — нормальная ситуация);
* `save_state(strategy_id, figi, state)` — сохранение изменений
  СУЩЕСТВУЮЩЕЙ записи (записи нет → `StateNotFoundError`: создание
  только через `create_state`);
* `create_state(strategy_id, figi, config_hash, data=None)` — создание
  независимого состояния; существующая запись → `StateAlreadyExistsError`
  (без перезаписи и скрытого сброса);
* `reset_state(strategy_id, figi) → bool` — ЯВНЫЙ сброс одной пары
  (True — была и удалена; False — не было); другие пары не затрагиваются;
* `list_states()` — все записи в детерминированном порядке
  (сортировка по (strategy_id, figi)).

### 4.3 Гарантии

* **Изоляция по ключу**: каждой паре соответствует отдельная запись
  (отдельный файл); любая операция работает ровно с одной записью под
  `RLock` хранилища.
* **Наружу не выдаются внутренние изменяемые ссылки**: состояния
  неизменяемы (frozen + ImmutableMapping); изменение возвращённого объекта
  невозможно в принципе (тесты §4.13), `to_payload()` отдаёт копии.
* **Проверка версии схемы и ключей при каждом чтении**: повреждённые
  записи (битый JSON, отсутствующие поля, неверные типы, рассинхрон
  имени файла и содержимого) → `StateCorruptionError`; неизвестная
  версия схемы → `StateSchemaError`; семантически невалидные значения →
  `StateValidationError`. Ничего не маскируется пустым состоянием.
* **Несовпадение config_hash**: `get_state(..., config_hash=...)` и
  `save_state` при расхождении сохранённого и ожидаемого хеша дают
  `StateConfigMismatchError` — контролируемая ошибка с указанием,
  что требуется ЯВНОЕ решение (`reset_state` или отдельная совместимая
  обработка). Старое состояние НЕ переносится на новую конфигурацию
  автоматически, файл записи при ошибке не изменяется.
* **Точный тип**: `save_state` принимает только `type(state) is
  StrategyState` (то же решение, что Stage A.2.1 для StrategyConfig —
  подкласс не может ослабить проверку); ключи записи обязаны совпадать
  с аргументами.
* **Безопасность имён файлов**: strategy_id и figi проверяются регулярным
  выражением `^[A-Za-z0-9][A-Za-z0-9._-]*$` (+ лимиты длины 128/64):
  исключены разделители пути, нулевой байт, `..`, ведущие точки,
  управляющие символы и юникод-обходы. Invalid → `StateValidationError`
  ДО любого обращения к файловой системе.

## 5. StrategyStateManager — менеджер (ТЗ §3.3)

* **Выдаёт стратегии только её собственное состояние**: `get_state`
  работает строго по паре (strategy_id, figi); одно состояние на все
  инструменты не хранится; глобального mutable context нет — все
  зависимости (`StateStore`, часы) внедрены явно через конструктор.
* **Создаёт независимое состояние при отсутствии записи** (`get_state`),
  привязанное к переданной конфигурации.
* **Сохраняет изменения**: `update_state(..., data=|updater=)` —
  get-or-create + эволюция `with_data` + `save_state` под замком
  менеджера; исключение из updater прерывает операцию БЕЗ записи.
* **Корректность при параллельных обращениях**: `RLock` менеджера на
  составные операции + `RLock` хранилища на атомарные; гонка get/create
  обрабатывается внутренне (повторное чтение после
  `StateAlreadyExistsError`). Тесты: 8 потоков × 25 обновлений по
  изолированным парам; 16 потоков get-or-create одной пары; 40 параллельных
  инкрементов одной пары без потери обновлений; смешанная нагрузка.
* **Привязка к конфигурации Stage A**: ровно один источник (или оба
  согласованных): `config` — ТОЛЬКО точный тип `StrategyConfig`
  (`type(config) is StrategyConfig`, решение Stage A.2.1 сохранено и
  задокументировано: подкласс не может ослабить привязку состояния к
  конфигурации; `config.strategy_id` обязан совпадать с ключом), либо
  `config_hash` — строка формата Stage A.2. Противоречие источника →
  `StateValidationError`. Ни конфигурации, ни хеша → `StateValidationError`
  (фиктивные значения и автоподстановка запрещены).
* **Интеграция с атрибуцией Stage A.2.1**: `get_state_for_context()` /
  `update_state_for_context()` принимают ТОЛЬКО проверенный
  `AttributionContext` — через `attribution._resolve_context` (тот же
  вход проверки маркера проверенного создания, что у factory/stamp/CSV/
  JSONL; это усиление проверки, не обход; точный `StrategyConfig` также
  принимается — та же нормализация, что и в Stage A).

## 6. Интеграция с контрактом Stage A (ТЗ §3.4)

* Использованы существующие контракты: `Strategy`, `StrategyConfig`,
  `strategy_id`, `config_hash`, `AttributionContext`, `ActivationMode`.
* Публичные интерфейсы Stage A НЕ сломаны: Stage B не изменяет ни одного
  существующего файла; `config_hash` Stage A не меняется (атрибутные
  тесты Stage A проходят без изменений); атрибуция Stage A остаётся
  корректной.
* Legacy Samsung V4 остаётся `REGRESSION_ONLY` (проверено тестом
  `test_legacy_strategy_remains_regression_only`).
* Точка интеграции в торговый цикл — Stage C: менеджер внедряется в
  стратегию явно (dependency injection) при вызове контракта стратегии;
  сейчас торговая логика не затронута, и это сознательная граница Stage B.

## 9. Почему «одно состояние на все инструменты» невозможно архитектурно

1. Ключ записи — кортеж (strategy_id, figi) на уровне модели, имени файла
   и всех операций API: обращение без обоих компонентов невозможно.
2. Хранилище не имеет состояния «по умолчанию»: `get_state` без ключа не
   существует в интерфейсе; Manager-фабрика тоже требует пару.
3. Данные одного ключа хранятся в отдельном объекте/файле; общего
   изменяемого словаря, куда пишутся «все подряд», нет — есть только
   `dict` записей memory-режима, и он не выдаётся наружу.
4. Перекрёстное загрязнение проверяется негативно: тесты §4.3/§4.12
   читают записи чужих пар ПОСЛЕ изменений целевой и сравнивают их
   побайтово с сохранёнными до изменений.
