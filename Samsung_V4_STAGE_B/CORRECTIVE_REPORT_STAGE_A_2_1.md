## 1. ИСХОДНЫЕ ДАННЫЕ И ПОСТАНОВКА

Репозиторий: cristal-hub/Samsung-V4-BASELINE. Работала ТОЛЬКО изолированная
копия пакета Stage A.2 (`Samsung_V4_STAGE_A_2`); исходные пакеты Stage A,
Stage A.1 и Stage A.2 сохранены без изменений; baseline не изменялся.

Цель — закрыть три оставшихся ограничения, обнаруженных независимой
проверкой Stage A.2, в границах атрибуции нового движка:

**Дефект №1. Прямое создание AttributionContext.** Публичный конструктор
`AttributionContext(strategy_id, config_hash)` выпускал произвольный
контекст без проверки соответствия `config_hash` реальной `StrategyConfig`;
`_resolve_context()` принимал такой объект непосредственно, и
`AttributionFactory` мог штамповать им новые объекты — обход проверки
Stage A.2.

**Дефект №2. Наследование StrategyConfig.** `AttributionContext.from_config()`
использовал `isinstance(config, StrategyConfig)` и перепроверку через
переопределяемый `config.recompute_config_hash()`: подкласс мог
переопределить `recompute_config_hash()` (и даже `__post_init__()`) и
ослабить проверку, получив контекст с несоответствующим хешем.

**Дефект №3. Изменяемый Enum.value.** Enum рассматривался как скаляр («уже
неизменяем»), но его `.value` мог содержать изменяемый объект (dict, list,
set, bytearray): фактическое содержимое параметра менялось ПОСЛЕ вычисления
`config_hash` — глубокая неизменяемость конфигурации обходилась через
вложенное значение Enum (и содержимое хеша не совпадало с фактическим).

## 2. ВЫПОЛНЕННЫЕ ИСПРАВЛЕНИЯ

### 2.1. Дефект №1 — контекст создаётся ТОЛЬКО из проверенной StrategyConfig

`candidate/attribution.py`:

* публичный конструктор `AttributionContext.__init__` теперь требует
  внутренний приватный билет создания `_CONTEXT_CREATION_TICKET`
  (класс-свидетель, закрытое имя модуля; проверка оператором `is`);
  любое обычное публичное создание с произвольной парой строк
  (позиальное, именованное, с «правдоподобным» чужим хешем, с пустыми
  полями) отклоняется `AttributionError` — fail-closed;
* единственный обычный путь получения контекста —
  `AttributionContext.from_config(проверенная StrategyConfig)`; контекст
  создаётся ТОЛЬКО на основании конфигурации, чей `config_hash` проверенно
  соответствует фактическим параметрам;
* формат `config_hash` контекста дополнительно перепроверяется
  `validate_config_hash_format` (64 hex-символа SHA-256 hexdigest);
* отсутствие подтверждённой конфигурации — fail-closed ошибка
  (`AttributionError` / `AttributionRequiredError`); никаких фиктивных
  значений и автоматической замены хеша НЕ введено;
* ВСЕ пути использования проходят через `_resolve_context()`, который
  принимает только: (а) контекст точного типа `AttributionContext`
  с маркером проверенного создания `_VERIFIED_MARKER` (выставляется
  исключительно охраняемым конструктором), либо (б) `StrategyConfig`
  (через `from_config`). Экземпляр, собранный в обход конструктора и не
  имеющий маркера, отклоняется на границе использования
  (`AttributionFactory`, `stamp`, `append_attributed_csv_row`,
  `append_attributed_jsonl_row`);
* `AttributionContext.__reduce__` определён явно: deepcopy/pickle
  восстанавливаются через тот же охраняемый конструктор и не теряют
  статус проверенности (билет — класс, deepcopy/pickle сохраняют
  тождество типов);
* `@dataclass(frozen=True, init=False)`: неизменяемость сохранена
  (setattr/delattr отклоняются FrozenInstanceError; `dataclasses.replace`
  тоже отклоняется — билет не передаётся); маркер не является полем
  dataclass и не участвует в `__eq__`/`__repr__`/`as_dict`/`hash`.

Граница защиты (честно, по условию задачи): Python-интроспекция уровня
`object.__new__` + `object.__setattr__` (полная сборка объекта мимо
конструктора с подделкой всех атрибутов, включая маркер) сознательно НЕ
является целью абсолютной защиты; обычный публичный API обход не позволяет,
а «наивная» сборка через `object.__new__` (без восстановления маркера)
отсекается на границе `_resolve_context` (проверено тестами).

### 2.2. Дефект №2 — точный тип StrategyConfig и исходный алгоритм хеша

`candidate/attribution.py`, `AttributionContext.from_config`. РЕШЕНИЕ
ДОКУМЕНТИРУЕТСЯ (требование задания):

* **Принято: наследование StrategyConfig НЕ поддерживается.** Обоснованной
  необходимости поддерживать наследование нет: подкласс может
  переопределить `recompute_config_hash()` и даже `__post_init__()` и
  ослабить проверку, при этом невозможно отличить «честный» подкласс от
  обходного по самому факту наследования. Поэтому `from_config` принимает
  ТОЛЬКО точный тип `StrategyConfig` (`type(config) is StrategyConfig`);
  экземпляр любого подкласса отклоняется `AttributionError` независимо от
  содержимого (fail-closed);
* соответствие хеша перепроверяется **ИСХОДНЫМ алгоритмом** — модульной
  функцией `strategy_api.compute_config_hash(...)` по фактическим полям
  `strategy_id` / `strategy_version` / `params` / `config_hash`;
  переопределяемые методы объекта (в первую очередь
  `recompute_config_hash()`) НЕ используются как источник проверки;
  несовпадение ЛЮБОГО из четырёх полей -> `AttributionError`;
* формат `config_hash` перепроверяется `validate_config_hash_format`
  (defense-in-depth);
* решение документировано в шапке модуля `attribution.py`, docstring
  `from_config` и docstring `StrategyConfig.recompute_config_hash`.

### 2.3. Дефект №3 — рекурсивный запрет изменяемых Enum.value

`candidate/strategy_api.py`:

* добавлена `_validate_enum_value()` — рекурсивная проверка значения Enum
  (fail-closed). Допустимы ТОЛЬКО безопасные неизменяемые скаляры:
  `None / bool / int / float / str` (float с NaN/Infinity отклоняется), а
  также Enum, значение которого рекурсивно сводится к такому скаляру
  (раскрытие цепочки Enum->Enum ограничено константой
  `_ENUM_UNWRAP_LIMIT = 8` — защита от искусственной циклической цепочки
  через переопределённый `value`);
* Enum с изменяемым значением (dict, list, set, bytearray и любые другие
  изменяемые/нескалярные объекты) отклоняется `StrategyConfigError`;
* проверка выполняется рекурсивно и на ВСЕХ путях:
  - при каждом создании `StrategyConfig` (через `deep_freeze` и через
    `_normalize_for_json` в расчёте хеша — `__post_init__`);
  - при ПРЯМОМ внешнем вызове `compute_config_hash` /
    `canonical_config_payload` / `_normalize_for_json` (в том числе без
    создания конфигурации);
  - в `deep_freeze` (defense-in-depth: замороженная структура не может
    содержать Enum с изменяемым значением даже транзитивно);
* смысл существующих параметров и golden fixtures НЕ изменён: обычные Enum
  со строковыми и числовыми значениями работают как прежде, нормализация
  безопасных значений не менялась — хеши корректных существующих
  конфигураций совпадают с эталонными значениями, вычисленными кодом
  Stage A.2 ДО изменений (см. раздел 3, тест 14).

Консервативное решение (документировано): нескалярные, но неизменяемые
значения Enum (например, tuple/frozenset) ТОЖЕ отклоняются — white-list
ограничен скалярами по формулировке задания («безопасные неизменяемые
скалярные значения»); расширение списка возможно явным решением следующих
этапов.

## 7. ОСТАВШИЕСЯ ОГРАНИЧЕНИЯ (честный перечень)

1. **Python-интроспекция.** Защита закрывает обычный публичный API.
   Полная интроспекция (`object.__new__(AttributionContext)` +
   `object.__setattr__` для ВСЕХ атрибутов, включая приватный маркер;
   аналогично для `StrategyConfig`; monkeypatch модульных функций) может
   собрать объекты мимо проверок — по условию Stage A.2.1 это сознательно
   НЕ цель абсолютной защиты. «Наивная» сборка `object.__new__` без
   восстановления маркера отсекается на границе `_resolve_context`
   (проверено тестами).
2. **Производственный поток.** Атрибуция остаётся самостоятельным
   интерфейсом нового движка: встраивание в production-поток baseline
   (`main.py`/`execution.py`/`logger.py`/`order_ledger.py`) по-прежнему
   НЕ выполнялось (граница Этапа A, зафиксирована в Stage A.1 и
   переносится на Этап B; предложение — добавить два поля в конец
   TRADE_FIELDS, механизм авто-миграции шапки сохранит старый журнал).
3. **Наследование StrategyConfig не поддерживается** (принятое решение,
   см. 2.2). Если в будущих этапах потребуется наследование — потребуется
   явный пересмотр границы доверия с сохранением исходного алгоритма
   проверки.
4. **Enum.value — только скаляры.** Нескалярные неизменяемые значения
   (tuple/frozenset/custom immutable) отклоняются консервативно
   (white-list по заданию); расширение — явное решение будущих этапов.
5. **Одноразовые «сырые» пары атрибуции.** Механизм «взять произвольную
   пару (strategy_id, config_hash) без конфигурации» не существует и не
   должен появляться: любая будущая функциональность атрибуции обязана
   идти через проверенную StrategyConfig/from_config.
6. **Границы этапа.** Stage B (изоляция состояния по (strategy_id, FIGI),
   новый контракт выхода, риск-менеджмент, симулятор, Sandbox-адаптер) не
   начинался; торговые подключения не выполнялись; торговая логика,
   параметры, сигналы, риск-менеджмент и исполнение не изменялись.

## 8. КРИТЕРИЙ ЗАВЕРШЕНИЯ (раздел 9 задания)

Stage A.2.1 завершён, поскольку:

* обычный API не позволяет создать неподтверждённый AttributionContext:
  прямое создание с произвольной парой строк отклоняется
  (AttributionError), единственный путь — `from_config` проверенной
  `StrategyConfig`; все потребители (factory/stamp/CSV/JSONL) принимают
  только подтверждённый контекст;
* наследование не обходит проверку config_hash: `from_config` принимает
  ТОЛЬКО точный тип `StrategyConfig` и перепроверяет хеш ИСХОДНЫМ
  алгоритмом по фактическим полям; подкласс с переопределённым
  `recompute_config_hash` (и даже с ослабленным `__post_init__`) не
  получает контекст ни одним путём;
* изменяемые Enum.value не могут нарушить целостность конфигурации:
  рекурсивная проверка отклоняет их при создании, при прямом
  `compute_config_hash` и в `deep_freeze`; безопасные Enum работают,
  прежние хеши сохранены (эталонные значения Stage A.2 подтверждены);
* все прежние тесты проходят без регрессий: 1037 существующих тестов
  Stage A.2 (включая 980 Stage A.1) — PASS; новые 76 — PASS; суммарно
  **1113 passed**, 0 failed, 0 skipped; пропуски/ослабления утверждений
  отсутствуют; golden fixtures не перегенерировались.
